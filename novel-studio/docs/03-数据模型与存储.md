## 1. 存储分层

```
┌──────────────────────────────────────────────────────────────┐
│ SQLite（结构化、可查询、需事务）                                │
│  books / chapters / canvas_lines / characters / voice_actors  │
│  recording_sessions / voice_segments / takes / arrangement    │
│  embeddings / tasks / settings / audit                        │
└──────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────┐
│ 文件系统（大二进制、流式读写）                                  │
│  projects/{id}/recordings/*.wav      原始录音会话             │
│  projects/{id}/segments/*.wav        绑定画本行的片段          │
│  projects/{id}/processed/*.wav       处理后的派生文件          │
│  projects/{id}/music/*                BGM / SFX 素材          │
│  projects/{id}/exports/*              导出成品                │
│  projects/{id}/cache/peaks/*.bin      波形峰值缓存            │
└──────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────┐
│ 缓存（可删除，重建成本低）                                      │
│  embeddings 缓存 / 波形峰值 / 转码中间文件 / ASR 结果           │
└──────────────────────────────────────────────────────────────┘
```

**分界规则**
- 需要「查询、排序、筛选、关联、事务」→ SQLite
- 需要「流式读、随机 seek、交给 ffmpeg」→ 文件
- **禁止**把音频放进 BLOB（会让备份、迁移、外部修复全部变难）
- **禁止**把业务状态只存在内存或 JSON 文件里（任务、录音会话必须入库）

## 2. 文件系统布局

```
{userData}/
├── novel-studio.db               主库
├── novel-studio.db-wal           WAL
├── logs/
│   └── 2026-02-14.log
├── backups/
│   ├── novel-studio-2026-02-14T03-00-00.db
│   └── index.json                备份清单（时间/大小/schema_version）
├── cache/
│   ├── embeddings/               （当前未用；向量直接入库，此处留给大模型缓存）
│   ├── asr/                      whisper 输出 JSON，按音频 SHA-256 命名
│   └── tmp/                      全局临时（启动清理）
└── projects/
    └── {projectId}/
        ├── project.json          项目元信息快照（冗余，便于外部识别与恢复）
        ├── recordings/           原始录音会话 WAV（永不自动删）
        │   └── {sessionId}.wav
        ├── takes/                试录版本（每行多次）
        │   └── {lineId}/{takeId}.wav
        ├── segments/             绑定画本行的成品片段
        │   └── {segmentId}.wav
        ├── processed/            处理链派生
        │   └── {segmentId}.{presetHash}.wav
        ├── music/                BGM / SFX（用户导入，原始文件复制一份托管）
        │   ├── bgm/
        │   └── sfx/
        ├── exports/
        │   └── {bookTitle}/
        │       ├── 001_第1章.mp3
        │       ├── ...
        │       └── {bookTitle}.m4b
        ├── packages/             导出/导入的 .nsp/.nst 落地
        └── .tmp/                 本项目临时（原子写的落点）
```

**相对路径原则**：数据库中**只存相对于 `projects/{projectId}/` 的路径**（如 `segments/abc.wav`），项目整体迁移或换机器时不会失效。绝对路径只在运行时由 `infra/fs/paths.ts` 拼接，禁止入库。

**命名原则**：音频文件名使用不可变 ID（UUID/nanoid），**不使用中文标题**（跨平台编码、长文件名、特殊字符问题）。人类友好名称存库，导出时再套命名模板。

## 3. 实体关系

```
book 1──n chapter 1──n canvas_line n──1 character
                          │                    │
                          │                    └──n character_alias
                          │                    └──n character_voice (绑定 voice_actor)
                          │
                          ├──1 line_embedding（向量）
                          ├──n take（试录版本）
                          ├──1 voice_segment（成品片段，指向某个 take 的区间）
                          └──1 arrangement_item（在某个 arrangement 中的时间线位置）

recording_session 1──n take / voice_segment
voice_actor 1──n voice_profile
arrangement 1──n arrangement_item
track 1──n arrangement_item（轨道 = 说话人）
task（后台任务）不属于业务域，独立表
```

**关键关系约束**
1. `canvas_line.speaker_type` ∈ {`narration`,`character`}；为 `character` 时 `character_id` 必填，且必须属于同一 `book`（用触发器或在 repository 层强制）。
2. `voice_segment.line_id` **唯一**（一行画本对应一个成品片段）；多次录制体现为多个 `take`，而非多个 segment。
3. `line_embedding` 与 `canvas_line` 一对一，但带 `model_id` 与 `content_hash`——文本或模型变了就要重算。
4. `arrangement_item` 是「片段 + 方案」的联合，同一 segment 可在多个 arrangement 中有不同位置。

## 4. 画本行：为什么它是主轴

`canvas_lines` 表是整套设计的核心。它的字段设计直接决定后续所有模块能否工作。

```ts
interface CanvasLine {
  id: string                    // UUID，稳定标识（任务包/回传全靠它）
  chapterId: string
  bookId: string                // 冗余，避免频繁 join（大查询提速）
  seq: number                   // 章内顺序（1 起），允许重排
  speakerType: 'narration' | 'character'
  characterId: string | null
  text: string                  // 实际要录的文本（已清洗，可被人工编辑）
  sourceText: string            // 原文对应片段（保留，便于对照与重算）
  charStart: number             // 原文偏移（章内）
  charEnd: number
  kind: 'dialogue' | 'narration' | 'inner' | 'sfx_note'   // 台词/旁白/内心独白/音效提示
  emotion: string | null        // 情绪标记
  emotionIntensity: number | null  // 1..5
  speed: 'slow' | 'normal' | 'fast' | null
  gainDb: number | null
  pauseAfterMs: number          // 句末留白（对轨直接消费）
  pauseInline: number[] | null  // 句内停顿插入点（字符索引）
  pronunciation: string | null  // 读音提示
  note: string | null           // 给配音员的备注
  state: 'draft' | 'assigned' | 'recorded' | 'aligned'
  confidence: number | null     // 说话人判定置信度 0..1
  candidates: string | null     // Top-3 候选 JSON: [{characterId,score}]
  decidedBy: 'rule' | 'vector' | 'llm' | 'human' | null
  needsReview: 0 | 1            // 低置信 / 质检标记
  flags: string | null          // JSON 数组：['too_long','quote_unmatched','no_pause','duplicate']
  isTitle: 0 | 1                // 章首标题念白行（见 15 §7）
  deletedAt: number | null      // 软删除（音频相关实体禁物理删除）
  rev: number                   // 乐观锁版本号
  createdAt: number
  updatedAt: number
}
```

**设计要点与理由**

| 要点 | 理由 |
|------|------|
| `text` 与 `sourceText` 分离 | 人工可能改文本（错别字、断句），但重算判定/对齐时需要原文 |
| `charStart/charEnd` 保留 | 支撑「双视图对照」「点画本行高亮原文」「重新分句」 |
| `confidence` + `candidates` + `decidedBy` | 让判定**可解释**：UI 能显示「为什么判给他」，重算时能只处理低置信 |
| `needsReview` 独立于 `state` | 状态表示流程，质量表示问题；混在一起会状态爆炸 |
| `pauseAfterMs` 存**毫秒**而非秒 | 避免浮点累积误差；对轨计算全是整数毫秒 |
| `decidedBy='human'` 保护 | 重算时跳过人工确认行（FR-2.1.6） |
| 冗余 `bookId` | 召回全书统计（每配音员行数）时避免 join 三张表 |

## 5. 向量存储策略

### 5.1 为什么不用向量数据库

单个项目的角色数量典型为 **5~200** 个，单个章节的画本行数为 **50~2000** 行。判定需求是「一行 vs N 个角色原型向量」的余弦相似度：
- N ≤ 200、维度 512 → 单次判定 20 万次浮点乘加，**在 Node 里约 0.05 ms**。
- 一章 2000 行 → **约 0.1 秒**（不含 embedding 推理，推理才是瓶颈）。

**结论**：暴力计算完全够用。引入 HNSW/FAISS 只会带来原生依赖与索引一致性问题。

### 5.2 存储形式

| 表 | 存什么 | 形态 |
|----|--------|------|
| `line_embeddings` | 每行的向量 | `vector BLOB`（Float32Array 的 Buffer）+ `dim` |
| `character_centroids` | 每个角色的原型向量 | 同上 + `sample_count` + `model_id` |

```ts
// 写入
const f32 = new Float32Array(dim)               // 已 L2 归一化
stmt.run(lineId, modelId, dim, Buffer.from(f32.buffer), hash)

// 读取（一次性载入当前章节所有角色原型，常驻内存）
const centroids = new Map<string, Float32Array>()
for (const row of rows) {
  const f = new Float32Array(row.vector.buffer, row.vector.byteOffset, row.dim)
  centroids.set(row.characterId, f)
}
```

**三条必须遵守的规则**

1. **写入前 L2 归一化**：归一化后余弦相似度退化为点积，省掉除法，且比较更稳定。
2. **必须记录 `model_id`**：不同模型的向量空间不可比。换模型 = 全部重算。
3. **必须记录 `content_hash`**：`sha256(text + contextScope)`。文本改了但 hash 没变 → 可复用；hash 变了 → 重算。这能省掉大量重复推理。

### 5.3 原型向量的计算与更新

```
centroid(c) = normalize( mean( normalize(e(line_i)) for line_i ∈ lines(c, 人工确认优先) ) )
```

- **剔除离群**：先算均值，再剔除与均值余弦 < 0.3 的样本（这些多半是判定错误的行），重算一次。
- **增量更新**：人工修改某行说话人后，只把该行的向量从旧角色累加器中减去、加到新角色累加器中，避免全量重算。需要 `character_centroids.sample_count` 与 `sum_vector`（未归一化的累加和）来支持可逆的增量更新。
- **冷启动**：新角色没有样本时，用「角色名 + 别名 + 性格描述 + 首次出现的上下文」构造一条合成文本作为初始原型；首轮判定后立刻用判定结果迭代一次。

```sql
-- 支持增量更新需要额外存累加和
character_centroids(
  character_id, model_id, dim,
  sum_vector BLOB,     -- 未归一化的 Σ(归一化向量)
  sample_count INTEGER,
  centroid BLOB        -- 归一化后的 sum/count，读取时直接用
)
```

## 6. 非破坏性编辑的落地

**原则**：任何音频处理都不覆盖原始文件，只写新文件并在库里改指针。

| 层 | 文件 | 库字段 | 说明 |
|----|------|--------|------|
| 原始采集 | `recordings/{sessionId}.wav` | `recording_sessions.file_path` | 永久保留，除非用户显式删除项目 |
| 试录 | `takes/{lineId}/{takeId}.wav` | `takes.file_path` | 每次录制一个新 take；替换成品不删旧 take |
| 成品片段 | `segments/{segmentId}.wav` | `voice_segments.file_path` | 由某个 take 按 `src_in/src_out` 裁切而来 |
| 处理后 | `processed/{segmentId}.{presetHash}.wav` | `voice_segments.processed_path` + `preset_hash` | 换预设 = 换文件，旧文件保留直到清理 |
| 对轨 | 无新文件 | `arrangement_items.timeline_start_ms/src_in_ms/src_out_ms` | 纯参数，随时可还原 |
| 导出 | `exports/...` | `export_jobs` | 成品，可重生成 |

**消费优先级**（混音时的取音顺序）：
```
processed_path 存在且 preset_hash 与当前方案一致 → 用它
否则 → segments 的 file_path
再否则 → 从 take 现切（并缓存为 segment）
```

**磁盘清理策略**（用户可控，默认保守）
| 类型 | 默认 | 可配置 |
|------|------|--------|
| `recordings/` 原始会话 | 永不自动删 | 用户手动「清理未使用会话」（且会话被 take 引用时禁止） |
| 非选中的 takes | 保留 30 天 | 可设「立即清理 / 永久保留」 |
| 过期 `processed/`（preset_hash 已不在任何方案中） | 保留 7 天 | 同上 |
| `cache/` | 保留 3 天 | 可清空 |
| `exports/` | 永不自动删 | — |

## 7. 迁移与版本化

### 7.1 迁移机制

- 采用**版本号递增 + 有序 SQL 脚本**，不用 diff 工具。
- `schema_version` 存于 `meta` 表；启动时比较并依次执行未应用的迁移。
- 每个迁移在**单个事务**内执行；失败则回滚并拒绝启动（进入只读模式）。
- 迁移脚本**一旦发布不可修改**（校验其 SHA-256），只增不改。
- 大表变更（加列除外）策略：建新表 → 分批拷数据（每批 1000 行，让出事件循环）→ 原子改名。

```ts
// infra/db/migrate.ts 骨架
const MIGRATIONS = [
  { version: 1, name: 'init', hash: '...', sql: initSql },
  { version: 2, name: 'add_line_candidates', hash: '...', sql: `ALTER TABLE canvas_lines ADD COLUMN candidates TEXT` },
  // ...
]
```

### 7.2 迁移前备份

任何 `version` 跨越（尤其 > 1 个版本）时，**先自动备份**数据库到 `backups/pre-migrate-{from}-{to}-{ts}.db`，失败可从该文件恢复。

### 7.3 兼容策略

| 变更类型 | 处理 |
|----------|------|
| 加列 | 允许，给默认值；旧版本应用打开新库时提示「库版本过新，请升级应用」 |
| 删列/改类型 | 走新表 + 拷贝；保留旧列一个版本周期 |
| 改枚举值 | 永不删除旧值，只新增；旧值映射在应用层做 |
| 改文件布局 | 写迁移脚本同时移动文件；移动失败则回滚（用「先复制后删」） |

## 8. `.nsp` 项目包格式

**用途**：整项目迁移/归档/换机。

```
{projectName}.nsp            （本质是 zip）
├── manifest.json            格式版本、导出时间、应用版本、内容清单、校验和
├── project.json             项目元信息
├── database.sqlite          业务库快照（VACUUM INTO 生成，非主库直接拷贝）
├── audio/
│   ├── recordings/          按需包含（可选「仅含成品片段」以缩小体积）
│   ├── takes/
│   ├── segments/
│   ├── processed/
│   └── music/
├── exports/                 可选包含
└── checksums.sha256         每个文件的哈希
```

```jsonc
// manifest.json
{
  "format": "nsp",
  "formatVersion": 1,
  "app": { "name": "Novel Studio", "version": "1.0.0" },
  "schemaVersion": 12,
  "exportedAt": "2026-02-14T10:00:00Z",
  "project": { "id": "uuid", "name": "斗破苍穹", "totalDurationMs": 12345678 },
  "contents": {
    "database": true,
    "recordings": true,
    "takes": false,
    "segments": true,
    "processed": false,
    "exports": false,
    "music": true
  },
  "counts": { "chapters": 120, "lines": 4820, "segments": 3900 },
  "files": 4211,
  "uncompressedBytes": 3221225472,
  "checksums": "checksums.sha256"
}
```

**导入规则**
1. 校验 `formatVersion`（低于支持范围 → 尝试迁移；高于 → 拒绝并提示升级应用）。
2. 逐文件校验 `checksums.sha256`；不匹配的文件**跳过并在报告中列出**，不整体失败。
3. **ID 冲突处理**：导入时给项目分配**新 projectId**；内部 ID 默认**保留原值**（这样任务包回传才能对得上），若与已有数据冲突则整体重映射并记录映射表（`id_map.json` 存于导入结果目录，供任务包回传时二次翻译）。
4. 音频文件按 `projectId` 重写到新目录；数据库中的相对路径不变（这是相对路径设计的收益）。
5. 解压防护：限制总解压大小（可配置上限，默认 50 GB）、条目数（默认 50000）、拒绝路径穿越（`..`、绝对路径、符号链接）。

**体积估算**（给用户提示用）
| 内容 | 1 章 15 min 的估算 |
|------|-------------------|
| 原始录音 WAV 48k/24bit 单声道 | ≈ 130 MB |
| 片段（同内容，裁切后） | ≈ 120 MB |
| 处理后 WAV | ≈ 120 MB |
| 导出 MP3 192kbps | ≈ 21 MB |
| 导出 M4B 96kbps | ≈ 11 MB |

> 因此 `.nsp` 默认**不含 recordings、不含 takes、不含 processed**，只带「片段 + 库 + 画本」，体积可控。

## 9. `.nst` 任务包格式

**用途**：把某个配音员的活儿打包发出去，录完收回来。

```
{actorName}-{bookTitle}.nst
├── manifest.json
├── task.json                该配音员的全部画本行（只读快照）+ 角色信息 + 录音建议
├── reference/               可选的参考音频（对手戏片段，便于对词）
├── slots/                   空白（导出时为空目录；回传时被填充）
│   └── {lineId}/*.wav
└── checksums.sha256
```

```jsonc
// task.json
{
  "format": "nst",
  "formatVersion": 1,
  "packageId": "uuid",
  "source": { "projectId": "uuid", "bookId": "uuid", "exportedAt": "..." },
  "assignee": { "voiceActorId": "uuid", "name": "小林", "note": "录音环境：安静卧室" },
  "recordSettings": {
    "sampleRate": 48000, "bitDepth": 24, "channels": 1,
    "fileNameTemplate": "{lineId}_{take}.wav",
    "recommendGainDb": -6, "targetPeakDb": -6
  },
  "characters": [
    { "id": "uuid", "name": "萧炎", "note": "少年，语气倔强", "defaultSpeed": "normal", "defaultEmotion": "平静" }
  ],
  "lines": [
    {
      "id": "uuid", "seq": 12, "chapterTitle": "第1章 陨落的天才",
      "characterId": "uuid", "characterName": "萧炎",
      "text": "我萧炎，从来不会认输。",
      "emotion": "愤怒", "emotionIntensity": 4, "speed": "fast",
      "pauseAfterMs": 600, "pronunciation": "行(háng)",
      "note": "这里是情绪爆发点，不要喊破音",
      "prevLine": "（旁白）他缓缓抬起头。",      // 上下文，帮助配音员找感觉
      "nextLine": "（药老）小子，别冲动。",
      "hasReference": true
    }
  ],
  "linesHash": "sha256-of-lines"     // 回传时校验画本是否已变更
}
```

**回传包（`.nst` 的变体或同一格式的 filled 版本）**
- `slots/{lineId}/{takeId}.wav` 填充音频
- 新增 `takes.json`：`[{lineId, takeId, fileName, durationMs, peakDb, recordedAt, device}]`
- 保留原始 `task.json` 与 `linesHash` 用于比对

**合并规则**（导演侧回收，FR-7.5）
| 情况 | 处理 |
|------|------|
| `linesHash` 不一致 | 提示「画本已变更」，列出增删改的行；音频按 `lineId` 尽力归位，无法归位的进「待处理」列表 |
| 同 line 多 take | 全部入库为 takes，标记来源包；不自动选为成品，进 A/B 对比队列 |
| 缺漏 | 报告列出「未回传的行」 |
| 未知 lineId | 拒绝入库，写入报告（可能是画本已被删除的行） |
| 音质异常（削波/超短/静音） | 入库但标记 `flags`，进质检报告 |

## 10. 备份与恢复

| 机制 | 触发 | 内容 | 保留 |
|------|------|------|------|
| 自动备份 | 每日首次启动（可配置为每周） | `VACUUM INTO backups/novel-studio-{ts}.db` | 最近 7 份 |
| 迁移前备份 | schema 版本跨越 | `backups/pre-migrate-*.db` | 永久（体积小） |
| 手动备份 | 用户点击 | 同自动 | 用户自管 |
| 项目级导出 | 用户点击 | `.nsp` | 用户自管 |

**恢复流程**：设置页选择备份 → 校验 `integrity_check` → 关闭数据库连接 → 替换文件（先把当前库改名保留） → 重开 → 校验 → 提示「已恢复至 {时间}，音频文件未被修改」。

**注意**：备份只含数据库。**音频文件不在备份内**（体积原因）。因此 `.nsp` 是唯一的完整归档方案，UI 里必须把这点讲清楚，避免用户以为有备份就安全。

## 11. 数据一致性的边界情况

| 场景 | 处理 |
|------|------|
| 用户手动删除了项目目录下的音频文件 | 启动时抽样校验 + 首次使用时校验；缺失 → 标记 `file_missing` 并提示「重新录制或指向新文件」 |
| 用户手动改了音频文件名 | 视为缺失（因入库为相对路径 + 固定命名），引导重新关联 |
| 画本行被删除但片段还在 | 禁止直接删除已有 segment 的行；改为软删除（`deleted_at`）以便恢复与回收 |
| 角色被删除但画本还在引用 | 禁止物理删除；角色改 `archived` 状态，引用保留 |
| 章节重排后 `seq` 冲突 | `seq` 允许非连续，重排时整章重写（事务内） |
| 同一行两个 take 都被选为成品 | 数据库唯一约束 `voice_segments(line_id)` 保证只有一个 |
| 并发写入（UI 连点） | repository 层串行 + 乐观版本号（`updated_at` 或 `rev`）冲突时提示重载 |
