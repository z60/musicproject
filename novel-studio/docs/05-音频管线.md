# 05 · 音频管线

> 上游：`01-系统架构.md`、`03-数据模型与存储.md`
> 这是全项目**技术风险最集中**的一份文档。音频链路上任何一处设计失误，代价都是「用户录了两小时的素材坏掉」。

---

## 1. 全链路一览

```
① 采集（渲染进程）
   getUserMedia → MediaStreamAudioSourceNode → AudioWorklet(float32 128帧/块)
   → 聚合为 50 ms 包 → MessagePort → 主进程

② 落盘（主进程 infra/media/wav-writer）
   预置 WAV 头 + 追加写 PCM + 每 1 s fsync + 每 5 s 更新 .meta.json
   → 正常停止：定稿头 → recording_sessions
   → 崩溃：启动恢复（见 §3）

③ 切片
   逐行模式：停止即生成 segment（整段即片段）
   连续模式：VAD 检测静音 → 切成 K 段 → 与画本行匹配（§4）

④ 片段裁剪
   voice_segment = take 的 [src_in_ms, src_out_ms] + 静音修剪 + 首尾 5 ms 淡化

⑤ 对轨（§5）
   arrangement = 每轨的 segment 序列 + offset_ms → 时间线

⑥ 处理（§6）
   ffmpeg 滤镜链（高通→降噪→去齿音→EQ→压缩→限幅）→ processed 派生文件

⑦ 混音（§7）
   每 item 抽取到绝对时间 → 分批 amix → 人声/音乐/音效总线 → ducking → 限幅

⑧ 响度（§8）
   两遍法：measure(JSON) → 计算增益 → 施加 gain + alimiter 真峰兜底

⑨ 导出（§9）
   分章 MP3/M4A/WAV → concat + chapter metadata → M4B

⑩ 质检（§10）
   重新测量成品：LUFS 偏差、真峰、静音异常、时长一致性
```

## 2. 采集与落盘

### 2.1 采样格式与协商（必须统一）

| 项 | 决策 | 理由 |
|----|------|------|
| 采集格式 | **float32（Web Audio 原生）** | 不做转换，零损耗；动态范围足够 |
| 工程采样率 | 设置项，默认 **48000 Hz** | 与视频/常见设备一致；44.1k 会与设备驱动反复重采样 |
| 落盘格式 | **WAV（RIFF）**，默认 24-bit PCM 单声道 | 无损、可随机 seek、ffmpeg 与所有工具通吃 |
| 声道 | 默认单声道；人声不需要立体声，且省一半空间 | 立体声可选（如需保留房间感） |
| 真实设备采样率 | 由 `AudioContext({ sampleRate })` 尝试；若不支持则用设备原生，再在采集后重采样 | 强行高采样率会导致浏览器做隐藏重采样，且延迟上升 |

> **踩坑点**：`AudioContext` 的 `sampleRate` 只是「请求值」。必须在创建后读 `ctx.sampleRate` 确认，并把**实际值**写入 `.meta.json`，否则会算出错误的时长与时间线偏移。

### 2.2 AudioWorklet 采集器

```ts
// renderer/src/shared/audio/pcm-capture-worklet.ts
class PcmCaptureProcessor extends AudioWorkletProcessor {
  private acc: Float32Array[] = []
  private accFrames = 0
  private readonly packFrames: number   // 目标包大小：sampleRate * 0.05（50 ms）

  constructor(options) {
    super()
    this.packFrames = Math.round(sampleRate * (options.processorOptions.packMs / 1000))
  }

  process(inputs: Float32Array[][], _outputs: Float32Array[][]) {
    const ch = inputs[0]?.[0]
    if (!ch || ch.length === 0) return true          // 无输入（静默期）也不能 return false
    // 关键：必须 copy，inputs 的 buffer 会被复用
    this.acc.push(new Float32Array(ch))
    this.accFrames += ch.length
    if (this.accFrames >= this.packFrames) {
      this.flush()
    }
    return true                                       // 永远返回 true，除非要销毁
  }

  private flush() {
    const total = new Float32Array(this.accFrames)
    let off = 0
    for (const b of this.acc) { total.set(b, off); off += b.length }
    this.acc = []; this.accFrames = 0
    this.port.postMessage({ type: 'pcm', frames: total.length, data: total.buffer }, [total.buffer])
  }
}
registerProcessor('pcm-capture', PcmCaptureProcessor)
```

**四条硬性约束**
1. **必须复制样本**：`inputs[0][0]` 的底层 buffer 会被引擎复用，直接 post 会拿到被覆盖的数据。
2. **`postMessage` 必须转移 `ArrayBuffer`**（第二个参数 `[buffer]`），否则是结构化克隆拷贝。
3. **包大小 50 ms**：128 帧/块太小（每块一次 IPC 会打满消息队列）；50 ms 是延迟与开销的平衡点。
4. **采集处理器绝不做重活**：重采样、增益、VAD 全部放主进程或独立 Worker。

### 2.3 渲染进程 → 主进程 的传输

```ts
// renderer：建立直连端口
const channel = new MessageChannel()
window.api.record.attachPort(channel.port2)     // preload 内部再转到主进程
workletNode.port.postMessage({ type: 'connect' })
// 实际实现：worklet.port → 渲染主线程聚合 → channel.port1.postMessage(packet, [packet.data])
// 主进程通过 MessageChannelMain 持有另一端，on('message') 直接拿到 ArrayBuffer
```

**为什么不用 `ipcRenderer.invoke`**：invoke 是请求-响应语义且有返回值开销；音频样本是**单向高频流**，走 MessagePort 零拷贝更稳。控制指令（开始/停止/暂停）仍走 invoke，二者分工明确。

### 2.4 主进程写入器（`infra/media/wav-writer.ts`）

**策略：预置头 + 追加写 + 定期 sync + 伴生元数据**

```ts
class WavAppendWriter {
  private fd: number
  private framesWritten = 0
  private metaPath: string
  private lastMetaFlush = 0
  private lastFsync = 0
  private readonly headerBytes = 44

  static async create(path: string, fmt: AudioFormat) {
    const fd = await fsp.open(path, 'w')                 // 注意：写 .wav.tmp
    await fd.write(Buffer.alloc(44))                     // 占位头（写入时就知道最终格式）
    // 同时写 {sessionId}.meta.json（见 04 §7）
  }

  async append(pcm: Buffer, frames: number) {
    await this.fd.write(pcm)                             // 顺序追加
    this.framesWritten += frames
    const now = Date.now()
    if (now - this.lastMetaFlush > 5000) { await this.flushMeta(); this.lastMetaFlush = now }
    if (now - this.lastFsync > 1000) { await this.fd.sync(); this.lastFsync = now }
  }

  async finalize(): Promise<WavFinalizeResult> {
    const dataBytes = this.framesWritten * this.bytesPerFrame
    await this.writeHeader(0, dataBytes)                 // pwrite 到偏移 0，覆盖占位头
    await this.fd.sync(); await this.fd.close()
    await fsp.rename(this.tmpPath, this.finalPath)       // 原子改名
    await this.flushMeta({ finalized: true })
    return { durationMs: Math.round(this.framesWritten / this.sampleRate * 1000), peakDb: this.peakDb }
  }
}
```

**为什么这样设计**

| 问题 | 对策 |
|------|------|
| WAV 头需要「总长度」，但录音开始时不知道长度 | 先占位 44 字节，结束时 `pwrite` 覆盖。中途文件头是错的（长度 0），但**数据是完整的** |
| 崩溃时头仍然是错的 | 靠 `.meta.json` 里的 `framesWritten` 重建头；若 meta 也丢了，用 `fileSize - 44` 反推帧数（向下取整到帧边界） |
| 补头本身可能崩 | 采用「copy → 修复副本 → 原子改名」，不动原始 tmp 直到成功 |
| 写到一半进程被杀 | 追加写天然安全，已写部分就是完整 PCM（不涉及原子性要求） |
| 掉电导致页缓存丢失 | 每 1 s `fsync`（代价可接受）；元数据每 5 s 一次 |
| 峰值统计 | 写入器顺便算峰值 dBFS（实时），录音结束时直接用，避免二次读盘 |

**性能实测预期**：48 kHz / 单声道 / 24-bit ≈ 144 KB/s ≈ 8.6 MB/min。顺序追加 + 每秒一次 fsync 对 SSD 毫无压力。

### 2.5 输入增益、AGC 与削波

```
采集(float32) ──[数字增益]──▶ 削波检测 ──▶ 写盘
                    ▲
              [AGC（默认关）]
```

- **增益**：写盘前施加（不改设备音量），`gainDb` 记录到 take 元数据，可随时回退（float32 原始素材未削波时无损）。因此**建议落盘 32-bit float**：即便增益加过头也能救回来。默认 24-bit 更省空间，二选一由设置决定，但**默认值建议 32f**（这是可恢复性 vs 空间的取舍，本项目偏向前者）。
- **削波检测**：连续 ≥3 个样本 `|x| >= 0.99` → 计数 +1；单次录音累计 > 20 次 → take 打 `flags:['clip']`，UI 红色标记并建议降低增益重录。
- **AGC**：默认关闭（会引入泵动与噪声抬升）。开启时用慢速 RMS 归一化（时间常数 1 s），并明确告知用户会改变表演动态。

## 3. 崩溃恢复（数据安全核心）

启动时对每个孤儿 `.wav.tmp`：

```
1. 读 {sessionId}.meta.json
   ├─ 存在 → frames = meta.framesWritten
   └─ 缺失 → frames = floor((fileSize - 44) / bytesPerFrame)
2. 实际可用帧数 = floor((fileSize - 44) / bytesPerFrame)
   frames = min(frames, 实际可用帧数)          # 以文件为准，避免头大身子小
3. 校验 bytesPerFrame 与 meta 的 fmt 一致（不一致则按 meta 重算并对齐到帧边界）
4. 生成新文件 {sessionId}.recovered.wav：
   - 复制前 44 + frames*bytesPerFrame 字节（用流式复制，避免大文件读进内存）
   - 写入正确头
5. 校验可播放：用 ffprobe 读时长；失败则保留 tmp 并报告（不要删！）
6. 入库 recording_sessions（status='recovered'）
7. 原子替换原文件名；原 tmp 移入 .tmp/quarantine/ 保留 7 天
```

**放弃恢复的情况**（必须明确报告，而不是静默处理）
- 文件小于 44 字节 → 只有头，没有素材
- `ffprobe` 无法解析且头部字段自相矛盾 → 疑似介质损坏，保留原始文件供人工抢救

**UI 呈现**：「检测到上次异常退出，已恢复 3 段录音（共 47 分 12 秒）。[查看] [播放] [继续录制]」

## 4. 连续录制的 VAD 切片

### 4.1 帧级分析

```
帧长     : 20 ms（960 样本 @48k）
每帧计算 : RMS(dBFS)、峰值(dBFS)、过零率(ZCR)、谱平坦度(可选，用于区分摩擦音)
噪声底   : 滑动 3 秒窗口的 10 分位（比均值更抗语音污染）
门限     : speechThreshold = noiseFloorDb + marginDb（默认 margin = 12 dB）
```

### 4.2 状态机

```
silence ──(连续 ≥ minSpeechMs 帧超阈)──▶ speech
speech  ──(连续 ≥ minSilenceMs 帧低于阈)──▶ 切分点
```
默认参数：`minSpeechMs = 120`、`minSilenceMs = 350`、`marginDb = 12`、`adaptiveNoiseFloor = true`。

### 4.3 边界精修（决定切片好不好用）

| 处理 | 做法 |
|------|------|
| 起点回退 | 从检测到 speech 的帧**向前回退 80 ms**（避免吃掉字头爆破音 `p/b/t/d`） |
| 终点前推 | 向后**保留 200 ms** 静音尾（保留自然收尾，避免听感突兀） |
| 过短丢弃 | 切片 < 180 ms 或 RMS 低于噪声底 + 6 dB → 丢弃（多半是咳嗽、椅子声） |
| 过长拆分 | 切片 > 15 s → 标记 `too_long`，进人工确认（可能是漏检静音） |
| 静音桥接 | 两段间隔 < 250 ms → 合并为一段（句内停顿被误切） |

### 4.4 切片与画本行的匹配

```
对每个切片 k（按时序）与画本行 l：
  cost(k, l) = w1 * |normalize(dur_k) - normalize(expectedDur_l)|
             + w2 * (1 - textSim(ASR(k), text_l))          # ASR 可用时
             + w3 * |k - l| / N                            # 顺序偏移惩罚
用动态规划（DTW 风格）求全局最优单调匹配
```
- **无 ASR 时**：只用时长 + 顺序 → 准确率不错（因为画本行长度与朗读时长强相关）。
- **有 ASR 时**：文本相似度权重提高，能修正跳行、重复录的情况。
- **输出**：`[{segmentIndex, lineId, confidence}]` + 未匹配项两侧的列表（漏录行 / 多余切片）。

> **注意**：预期时长估算 `expectedDur_l = 字数 / 语速(chars/sec) * 情绪系数`。中文默认 4.2 字/秒，`slow`×0.85、`fast`×1.18。这个系数要可配置，因为它因人和作品差异很大。

## 5. 对轨算法

### 5.1 数据模型

```ts
interface ArrangementItem {
  id: string
  arrangementId: string
  segmentId: string
  lineId: string
  trackId: string            // = speaker（narration 或 characterId）
  timelineStartMs: number    // 在章节时间线上的位置
  srcInMs: number            // 源片段内的起点（默认 0）
  srcOutMs: number           // 源片段内的终点（默认片段全长）
  fadeInMs: number           // 默认 5
  fadeOutMs: number          // 默认 5
  locked: 0 | 1              // 人工锁定后自动排布不再移动它
}
```

### 5.2 自动排布（FR-4.3 / FR-4.4）

```
按 (track, 画本行 seq) 排序
对每条轨道 t：
  cursor = 0
  for line in trackLines(t):
      seg = segment(line)
      if seg == null: continue                  # 缺录，留占位（记为 gap）
      dur = srcOut - srcIn + fade
      start = max(cursor + pauseAfter(prevLine), 0)
      if item.locked: start = item.timelineStartMs
      write item(start)
      cursor = start + dur
章节总时长 = max(所有轨道的 cursor) + tailSilenceMs
```

**留白来源优先级**：`line.pauseAfterMs` > 角色默认 > 章节默认（设置项，默认 500 ms）。

**多轨同时起点的处理**：默认三条语音轨（旁白/角色 A/B）在同一时间轴上并存，因此**跨轨必然重叠**（旁白与台词本就会交错）。所以「重叠」判定必须区分：

| 类型 | 定义 | 默认处理 |
|------|------|----------|
| **同轨重叠** | 同一 `trackId` 内两 item 时间区间相交 | **必须消解**（同一人不该同时说两句）→ 后一段后移 |
| **跨轨重叠（正常对话）** | 不同 track 相交且相交时长 ≤ `maxOverlapMs`（默认 3000 ms） | 保留（更自然） |
| **跨轨重叠（异常）** | 相交时长 > `maxOverlapMs`，或出现「无人说话的空隙 > 5 s」 | 报告 + 建议串行化 |
| **同角色相邻重叠** | 同 recharacter 相邻两句（画本行紧邻）相交 | 串行化 |

**消解策略**（FR-4.5，可全局选，也可逐条改）
| 策略 | 行为 | 适用 |
|------|------|------|
| `serialize` 串行化 | 后一段 `timelineStartMs = 前一段结束 + 最小留白` | 默认 |
| `keep` 保留交叠 | 不动 | 有意做对话交叠 |
| `compress-pause` 压缩留白 | 优先把前一段之后的留白压到 0，仍不够再移动 | 不想改变节奏时 |
| `tighten` 紧贴 | 前一段尾静音修剪到 30 ms 后紧接 | 快节奏 |

### 5.3 静音修剪（FR-4.9）

```
1. 从 srcIn 开始向后扫，找第一个 |x| > trimThreshold（默认 -45 dBFS）的样本 → 实际起点
2. 从 srcOut 开始向前扫，同理 → 实际终点
3. 实际起点向前留 trimPaddingMs（默认 100 ms，但不早于 0）
4. 实际终点向后留 trimPaddingMs（默认 120 ms，但不晚于片段尾）
```
在 PCM 域做（读片段文件，不需 ffmpeg，速度快）。修剪结果写回 `srcInMs/srcOutMs`，**不修改文件**。

### 5.4 手动微调（FR-4.7）

| 操作 | 交互 | 存储影响 |
|------|------|----------|
| 拖动整体 | 水平拖 item | 改 `timelineStartMs` |
| 拖左边缘 | 改起点 | 同时改 `timelineStartMs` 与 `srcInMs`（保持内容对齐） |
| 拖右边缘 | 改终点 | 改 `srcOutMs` |
| 锁定 | 右键/锁图标 | `locked = 1` |
| 吸附 | 拖动时按住 `Alt` 关闭吸附 | 吸附目标：网格（0.1/0.5 s）、相邻 item 边界、画本行边界 |
| 撤销 | `Ctrl+Z` | 对轨操作进独立 undo 栈（至少 50 步） |

**关键**：拖左边缘时如果只改 `timelineStartMs`，音频内容会跟着移动（听起来是位移）；正确语义是「改裁剪点，保持内容绝对位置不变」→ 因此 `timelineStartMs` 与 `srcInMs` 必须**同步反向补偿**：
```
Δ = newTimelineStart - oldTimelineStart
srcInMs' = srcInMs + Δ        # 内容位置不变
timelineStartMs' = newTimelineStart
```
这是最容易写错的一处，必须单测覆盖。

### 5.5 AI 强制对齐（FR-4.12，1.0 只留钩子）

```ts
interface ForcedAlignProvider {
  align(audioFile: string, expectedText: string): Promise<{
    words: Array<{ text: string; startMs: number; endMs: number; prob: number }>
    overallScore: number
    verdict: 'ok' | 'partial' | 'mismatch'
  }>
}
```
数据结构已就绪（`arrangement_items` 与 `takes` 都有足够字段），实现期只需接 whisper.cpp 的 word-level timestamps（`--output-json-full` + `-ml 1` 或 token 级概率）。**已识别的实现要点**（写在这里避免将来踩坑）：
- whisper 的时间戳是 token 级，需要按中文词边界合并；
- 中文标点与画本行可能不一致 → 比对前必须归一化（去标点、繁简统一、数字转中文）；
- 判定「漏读」用「画本行有而识别结果无的关键词比例」，而非整句相似度（整句相似度对短句不敏感）。

## 6. 单片段处理链（FR-5）

### 6.1 滤镜链构建

```ts
interface ProcessChain {
  highpass: { enabled: boolean; freq: number; poles?: 1 | 2 }        // 默认 80 Hz 2 阶
  denoise:  { enabled: boolean; nr: number; nf: number; tn?: boolean } // afftdn: nr=降噪量(dB), nf=噪声底
  deesser:  { enabled: boolean; intensity: number; freq: number }    // deesser i=0.5 f=0.5
  eq: Array<
    | { type: 'lowshelf'; freq: number; gainDb: number }
    | { type: 'highshelf'; freq: number; gainDb: number }
    | { type: 'peak'; freq: number; q: number; gainDb: number }
    | { type: 'lowpass'; freq: number }
    | { type: 'highpass'; freq: number }
  >
  compressor: { enabled: boolean; thresholdDb: number; ratio: number; attackMs: number; releaseMs: number; makeupDb: number }
  limiter: { enabled: boolean; limitDb: number; attackMs: number; releaseMs: number }
}
```

**滤镜字符串生成**（顺序即处理顺序，不可随意调换）
```
highpass=f=80:poles=2,
afftdn=nr=12:nf=-30,
deesser=i=0.5:f=0.5,
equalizer=f=200:t=q:w=1:g=-2,
equalizer=f=3000:t=q:w=1.2:g=2.5,
acompressor=threshold=-18dB:ratio=3:attack=8:release=180:makeup=2,
alimiter=limit=0.891:attack=5:release=80
```
> `limit=0.891` 对应 -1 dBFS（`10^(-1/20) ≈ 0.891`）。`alimiter` 是采样级限幅，**不是真峰限幅**；真峰兜底放在导出阶段的响度处理后（§8）。

**几个必须写进文档的 ffmpeg 细节**
| 细节 | 说明 |
|------|------|
| `afftdn` 的 `nf`（noise floor）单位是 dB，且**必须接近实际噪声底**，否则会「吃字」或没效果 | 提供「采样噪声轮廓」：用户选一段纯噪声 → 用 `astats` 算 RMS → 自动填 `nf` |
| `deesser` 的 `i` 是强度 0~1，`f` 是频率系数 0~1（乘 采样率/2，即 0.5 @48k ≈ 12 kHz） | UI 上要用「嘶声抑制强度/中心频率(kHz)」表达，不要暴露 ffmpeg 参数名 |
| `equalizer` 的 `t=q` 时 `w` 表示 Q 值；`t=o` 时表示带宽（八度） | 统一用 `q`，避免用户困惑 |
| `acompressor` 的 `makeup` 是线性倍数还是 dB 视版本 | **必须实测确认**并封装成 `makeupDbToLinear()`，不要凭记忆 |
| `alimiter` 的 `level` 参数可自动归一化 | 默认关闭（`level_in=1`），避免与响度处理冲突 |
| 声道数 | 处理链统一按单声道做；若片段是立体声，先 `pan=mono|c0=0.5*c0+0.5*c1` 或保留立体声（设置项） |

### 6.2 播放与输出格式一致性

- 处理链的**内部工作格式统一为** `pcm_s32le @ 48 kHz`（若源是 44.1k 则先 `aresample=48000`），避免各片段格式不一导致后续 `amix` 出错。
- 输出文件固定 `.wav`（24-bit PCM，单声道，48 kHz），文件名含 `presetHash`（如 `abc123.a1b2c3d4.wav`），换预设不覆盖。

### 6.3 预设系统（FR-5.9）

```ts
interface ProcessPreset {
  id: string; name: string; builtin: boolean
  chain: ProcessChain
  applyTo: 'segment' | 'character' | 'chapter' | 'book'
  characterIds?: string[]        // applyTo='character' 时的目标
  createdAt: number; updatedAt: number
}
```

**内置预设建议**（这些参数是起点，最终以实听为准）
| 预设 | 高通 | 降噪 | 去齿音 | EQ 要点 | 压缩 | 限幅 |
|------|------|------|--------|---------|------|------|
| 男声·旁白·沉稳 | 70 Hz | nr=10 | 弱 | -2 dB@250（去闷）、+2 dB@3.5k（清晰） | 3:1, -18 dB | -1 dBFS |
| 女声·角色·明亮 | 90 Hz | nr=8 | 中 | +1.5 dB@6k（空气感）、-1.5 dB@400 | 2.5:1, -20 dB | -1 dBFS |
| 广播·有力 | 80 Hz | nr=12 | 中 | -3 dB@200、+3 dB@3k、+1.5 dB@8k | 4:1, -16 dB | -1 dBFS |
| 手机录音·抢救 | 120 Hz | nr=18 | 强 | -4 dB@300、+3 dB@2.5k | 4:1, -15 dB | -1 dBFS |
| 仅修剪（不做处理） | 关 | 关 | 关 | 无 | 关 | -1 dBFS |
| ASMR·贴近 | 100 Hz | nr=6 | 弱 | +2 dB@5k | 2:1, -22 dB | -1 dBFS |

**A/B 试听**：保留原始与处理后两条路径，播放时同一位置切换（`processed_path` 与 `file_path`），这是后期最重要的验证手段。

### 6.4 批量与失败隔离（FR-5.11）

```
for each segment (按 chapter 分组):
    if dedupeKey 已存在且 preset_hash 未变 → skip（幂等）
    run ffmpeg → 成功：更新 processed_path；失败：记录错误继续下一个
汇报：成功 N / 失败 M（列出原因）/ 跳过 K
```
**铁律**：单个失败绝不中断整批；临时文件统一在 `cache/tmp/{taskId}/` 下，任务结束（含取消）无条件清理。

## 7. 混音（FR-6.1 / FR-6.2 / FR-5.13 / FR-5.14）

### 7.1 渲染策略选择（性能关键）

| 方案 | 做法 | 复杂度 | 采用 |
|------|------|--------|------|
| A. 全量 filter_complex | 所有 item 在一个滤镜图里 `adelay` + `amix` | O(N) 个滤镜，N=500 时命令行极长、内存高 | 降级用 |
| **B. 分批 amix + 层级合并** | 每 32 个 item 混一组，再递归合并各组 | O(log N) 层 | **默认** |
| C. 顺序拼装 | 仅适用于单轨串行 | O(N) 但无混音 | 特殊场景（纯旁白） |

### 7.2 分批混音的滤镜图（方案 B 展开）

```
# 第 1 层：每个 item → 独立延迟流
[i:0] atrim=start={srcIn}:end={srcOut}, asetpts=PTS-STARTPTS,
      afade=t=in:st=0:d={fadeIn/1000}, afade=t=out:st={dur-fadeOut/1000}:d={fadeOut/1000},
      adelay={start}|{start}, apad=whole_dur={chapterDur} [a{i}]
# 第 2 层：每组 32 个 → amix
[a0][a1]... [a31] amix=inputs=32:normalize=0:dropout_transition=0 [g0]
# 第 3 层：各组 → 再 amix
[g0][g1]... amix=inputs=K:normalize=0 [voice]
```

**三个必须记住的点**
1. **`normalize=0`**：`amix` 默认会把所有输入按 1/N 衰减，导致音量大跌。混音必须显式关闭它，音量由各 item 自己的增益控制。
2. **`adelay` 的参数是「每声道一个值」**：单声道写 `adelay=1500|1500`（写一个 `1500` 在某些版本会只作用于第一声道）。
3. **`apad=whole_dur`**：让每条流都补齐到章节总长，否则 `amix` 会以最短输入结束（**这是最常见的「混出来只有前几秒」的原因**）。

### 7.3 总线结构

```
旁白轨 ─┐
角色A轨 ─┼─▶ [人声总线 voice] ──┬─▶ [主总线 master] ─▶ 响度 ─▶ 限幅 ─▶ 输出
角色B轨 ─┘   (EQ/压缩可选)      │
                                 └──▶ [侧链源 scrap]（供 ducking 用）
BGM轨 ───▶ [音乐总线 music] ─────┐
SFX轨 ───▶ [音效总线 sfx] ───────┘
```

**轨道级参数**：`gainDb`（-60~+12）、`pan`（-1~1，单声道下仅用于立体声输出时的定位）、`mute`、`solo`、`processPresetId`（轨道级处理链，作用于混音前）。

**Solo 语义**：任一轮轨 solo 时，其他轨静音（但**侧链源始终有效**，否则 ducking 会失效导致 BGM 不降）。

### 7.4 BGM 与音效（FR-5.13）

```ts
interface MusicTrack {
  id: string; bus: 'music' | 'sfx'
  filePath: string
  startMs: number
  endMs: number | null          // null = 到章节结束
  loop: boolean
  gainDb: number
  fadeInMs: number; fadeOutMs: number
  ducking: { enabled: boolean; amountDb: number; thresholdDb: number; attackMs: number; releaseMs: number }
}
```
- **循环**：`aloop=loop=-1:size={frames}` 需先知道样本数 → 用 `aloop` 前先用 `astats` 或 `ffprobe` 取总帧数。
- **淡入淡出**：`afade=t=in:st={startMs/1000}:d=...; afade=t=out:st={endMs/1000 - d}:d=...`（注意 `st` 是**绝对时间**，包含前导静音）。
- **长度不足**：`apad` 补齐；**长度超出**：`atrim` 截断。

### 7.5 自动闪避（ducking，FR-5.14）

```
[music] ─────────────────────────────▶ [ducked] ─▶ master
[voice] ──▶ asplit ─┬─▶ master
                    └─▶ [scrap] ─▶ sidechaincompress 的 sidechain
```

```bash
[music][voice]sidechaincompress=threshold=0.02:ratio=8:attack=20:release=400:makeup=1:level_sc=1
```
| 参数 | 建议 | 说明 |
|------|------|------|
| `threshold` | 0.01~0.05（线性） | 越大越不敏感，BGM 越少下潜 |
| `ratio` | 6~12 | 大 = 说话时压得更狠 |
| `attack` | 10~30 ms | 太快会有抽气感 |
| `release` | 300~600 ms | 太短会「呼吸」，太长会盖住下一句 |
| `makeup` | 1（不加） | 增益统一在轨道级处理 |

**为什么用 `sidechaincompress` 而不是手写包络**：ffmpeg 内置、无需额外依赖、效果可接受。手写包络（按画本行时间算出音乐增益曲线）在 3.0 可作为「精确 ducking」增强——因为画本行的时间是已知的，可以做到**毫秒级精确**且不依赖侧链检测。记在这里作为后续优化点。

## 8. 响度标准化（FR-6.3，两遍法）

### 8.1 流程

```
Pass 1（测量）:
ffmpeg -i in.wav -af loudnorm=I=-16:TP=-1:LRA=11:print_format=json -f null -
  → 解析出 { input_i, input_tp, input_lra, input_thresh, target_offset }

计算施加增益:
  gainDb = target_I - input_i        (线性增益，保持动态)

Pass 2（施加）:
ffmpeg -i in.wav -af volume={gainDb}dB, alimiter=limit=0.891:attack=5:release=80 out.wav

Pass 3（复核，可选但强烈建议）:
再跑一次测量 → 偏差 > 0.5 LU 则微调一次
```

**为什么不用 `loudnorm` 第二遍**：`loudnorm` 的第二遍是**动态**归一化（内部有门限和时变增益），会压缩动态、且逐章结果不够齐。对有声书，**线性增益 + 限幅**更可控、更透明。

**为什么必须两遍**：单遍 `loudnorm` 是单次通过的动态处理，实测与目标偏差常达 ±2 LU，且不同章节偏差方向不一致 → 听众会感觉「这章响那章轻」。

### 8.2 逐章一致性的特别说明

- **逐章处理时每章都独立归一到 -16 LUFS** → 章与章之间响度一致。这是有声书的标准做法。
- **但**：如果某章只有很短的对白（例如 20 秒），它的 `input_i` 会受门限影响而不稳。对策：对该章用「与全书其他章的平均增益」做校正，或提示用户「本章过短，响度可能不准」。
- **真峰上限**：目标是 `TP ≤ -1 dBTP`。`alimiter` 只做采样级，若测量结果显示 `output_tp > -1`，则用 `-af alimiter` 前再降 0.5~1 dB，或使用 `aformat` + `loudnorm` 的真峰模式（更慢但准确）。**验收标准以第三方工具测量为准**（如 `ffmpeg -af ebur128` 或 Audacity 的 Loudness Normalization 报告）。

### 8.3 决策表

| 目标 | 适用 | 参数 |
|------|------|------|
| **-16 LUFS**（默认） | 有声书、播客 | I=-16, TP=-1, LRA=11 |
| -14 LUFS | 流媒体（Spotify/YouTube 会再归一） | I=-14, TP=-1 |
| -23 LUFS | EBU R128 广播 | I=-23, TP=-1, LRA=15 |
| 自定义 | 高级用户 | 直接填 I/TP/LRA |

## 9. 导出（FR-6.5 ~ FR-6.8）

### 9.1 分章导出

**MP3（默认）**
```bash
ffmpeg -i chapter.wav -c:a libmp3lame -b:a 192k -ar 44100 \
  -write_xing 1 -id3v2_version 3 \
  -metadata title="第1章 陨落的天才" -metadata artist="作者" -metadata album="书名" \
  -metadata track="1/120" \
  [-i cover.jpg -map 1 -c:v copy -disposition:v attached_pic] \
  "001_第1章.mp3"
```
| 注意 | 说明 |
|------|------|
| 采样率 | MP3 常见 44.1 kHz；也可 48 kHz（部分老设备兼容性略差）。作为设置项，默认 **44.1 kHz** 用于 MP3 输出 |
| `-write_xing` | 写入 Xing/VBR 头，否则时长显示不准、seek 困难 |
| 码率 | 人声 128 kbps 已足够；默认 **192 kbps** 更保险 |
| 封面 | `attached_pic` 方式嵌入；注意某些播放器对 ID3 版本敏感，用 `id3v2_version 3` 最兼容 |

**WAV**：直接 `-c:a pcm_s24le`，不重编码（若源即 48k/24bit 则 `-c copy` 更快）。
**M4A/AAC**：`-c:a aac -b:a 192k -movflags +faststart`。

### 9.2 整本合并 M4B（FR-6.6）

**步骤 1：生成章节文本文件** `chapters.txt`
```
;FFMETADATA1
title=斗破苍穹
artist=天蚕土豆
album=斗破苍穹
genre=Audiobook
date=2026
[CHAPTER]
TIMEBASE=1/1000
START=0
END=742000
title=第1章 陨落的天才
[CHAPTER]
TIMEBASE=1/1000
START=742000
END=1489000
title=第2章 斗之气
```
> `START/END` 必须是**毫秒整数**，且必须**严格连续无缝隙**（上一章 END = 下一章 START），否则部分播放器章节跳转会错位。生成时用累积时长计算，避免浮点误差。

**步骤 2：concat 列表** `list.txt`
```
file 'C:/.../001_第1章.wav'
file 'C:/.../002_第2章.wav'
```
> 路径中的单引号需转义（`'\''`）；Windows 反斜杠在 concat 文件里是安全的，但**建议统一用正斜杠**避免歧义。

**步骤 3：合并 + 写元数据**
```bash
ffmpeg -f concat -safe 0 -i list.txt -i chapters.txt \
  -map_metadata 1 -map_chapters 1 \
  -c:a aac -b:a 96k -ar 44100 -ac 1 \
  -movflags +faststart \
  "斗破苍穹.m4b"
```
| 注意 | 说明 |
|------|------|
| `-map_chapters 1` | 关键！不加则章节信息丢失 |
| `-movflags +faststart` | moov 前置，边下边播与部分播放器必需 |
| M4B 与 M4A | 容器相同（`ipod`/`mp4`），扩展名 `.m4b` 让播放器识别为有声书 |
| AAC 编码器 | 优先 `aac`（原生）；若追求质量且构建支持，可用 `libfdk_aac`（GPL/非免费，注意许可） |
| 章数上限 | 部分播放器对章节数敏感（>255 章可能异常）→ 超过 200 章时建议按卷分文件，UI 给出提示 |
| 时长 | M4B 单文件建议 ≤ 24 h（超长文件 seek 索引会庞大） |

### 9.3 命名与目录

```ts
// export.fileNameTemplate 默认
'{bookTitle}/{chapterIndex:03}_{chapterTitle}'
// 例：斗破苍穹/001_第1章 陨落的天才.mp3
```
**文件名清洗**：去除 `\ / : * ? " < > |` 与控制字符；长度截断到 120 字符（按 UTF-8 字节数保守截断）；同名冲突自动加 `_2`。

### 9.4 导出任务与断点（FR-6.11）

```
export.book 任务：
  1. 校验条件（QC 预检，§10.2）→ 不通过则返回清单让用户确认
  2. 逐章渲染：
     - 已有成品且参数未变（hash 一致）→ 跳过（断点续传的核心）
     - 渲染 → 响度 → 导出 → 记录 export_jobs
  3. 全部章节完成 → 合并 M4B → 记录报告
  4. 校验成品（§10.3）→ 生成导出报告 JSON
```
`export_jobs` 记录 `chapterId + outputHash + paramsHash + status`，**重跑时按 paramsHash 判断是否需要重渲染**——这是「改了第 30 章，只重渲第 30 章」的基础。

## 10. 质检（FR-6.8 / FR-6.9）

### 10.1 渲染前预检（快速，基于已有数据）

| 检查 | 数据来源 | 严重度 |
|------|----------|--------|
| 缺录行（画本行无 segment） | `canvas_lines` LEFT JOIN `voice_segments` | 阻断 |
| 孤儿片段 | `voice_segments` 的 line 已删除 | 警告 |
| take 削波标记 | `takes.flags` 含 `clip` | 警告（可重录） |
| 片段过短/过长 | `takes.duration_ms` | 警告 |
| 说话人未分配 | `canvas_lines.character_id IS NULL AND speaker_type='character'` | 阻断 |
| 未使用角色 | 角色表 vs 画本引用 | 提示 |
| 全书响度分布 | `audio_metrics` | 警告（极端偏差） |

### 10.2 渲染后质检（实测，可信）

| 检查 | 方法 | 阈值 |
|------|------|------|
| 整体响度 | `ebur128` 或 `loudnorm print_format=json` | \|measured - target\| ≤ 1.0 LU |
| 真峰 | 同上 | ≤ TP 目标（默认 -1 dBTP） |
| 章间响度差 | 逐章测量对比 | ≤ 1.5 LU（超出则整体观感不齐） |
| 整章静音 | 全段 RMS | 若整章 RMS < -60 dBFS → 阻断（说明渲染失败） |
| 异常长静音 | 扫描连续静音 | 单段 > 10 s 且非章头/章尾 → 警告 |
| 时长一致性 | 成品时长 vs 时间线预期 | 偏差 > 1 s → 警告（可能有片段丢失） |
| 削波 | `astats` 的 `Peak_level` / `Flat factor` | 连续削波样本 > 0 → 警告 |

## 11. 试听与监听（渲染进程实时路径）

### 11.1 两套独立的音频图

| 图 | 用途 | 特点 |
|----|------|------|
| **录音图** | 采集 + 监听返送 | 低延迟（`latencyHint: 'interactive'`），监听源 = 已有轨道回放 + 可选节拍器 |
| **试听图** | 对轨/混音时试听 | 高质量、可 seek、多轨混音、无需极低延迟 |

**不能共用**：录音需要低延迟与稳定帧率；试听需要精确 seek 与完整混合。混用会导致「录音时杂音」或「试听时卡顿」。

### 11.2 录音监听返送（FR-3.8）

```
[已录片段/参考音] ─▶ GainNode(监听音量) ─┐
[麦克风直通（防啸叫，默认关）] ──────────┼─▶ MonitorGain ─▶ destination
[节拍器/提示音] ────────────────────────┘
```
| 要点 | 做法 |
|------|------|
| **啸叫风险** | 默认**关闭麦克风直通**（只监听伴奏/参考音），并在 UI 上明确提示「请戴耳机」。若用户坚持开启直通，给出强烈警告 |
| 回声消除 | 开启监听回放时，若麦克风采集里可能混入回放 → 建议打开 `echoCancellation`（但会轻微影响音色）；或在录音时**只监听而不回放麦克风**，避免声学反馈 |
| 延迟 | `AudioContext({ latencyHint: 'interactive' })`；实测方法：`ctx.outputLatency + ctx.baseLatency`，在设备诊断页显示 |
| monitorGainDb | 独立于录音增益，默认 -6 dB |

### 11.3 波形绘制

| 场景 | 策略 |
|------|------|
| 录音中实时波形 | 从采集块直接算 min/max，环形缓冲保留最近 5 s，`requestAnimationFrame` 绘制 |
| 片段波形（对轨） | 用预计算的峰值缓存（`cache/peaks/*.bin`，100 peaks/s），按缩放级别聚合（多级 LOD：100/10/1 peaks/s） |
| 长章节总览 | 用最低 LOD（1 peak/s）先画骨架，放大后再加载细粒度 |
| 绘制线程 | `OffscreenCanvas` + Worker；主线程只负责交互与命中检测 |
| 峰值计算 | 在主进程用 `infra/media/peaks.ts` 流式读取 PCM 计算，避免整文件载入内存 |

### 11.4 命中检测（对轨交互）

时间线可能同时存在数百个 item，用简单的矩形遍历会造成拖动卡顿。采用**空间分区**：
- 按轨道分行，轨内按 `timelineStartMs` 排序 → 二分查找定位候选，再局部线性扫描。
- 拖动时只重绘受影响区域（脏矩形）。
- 1000 个 item 在 1080p 下的拖动目标 ≥ 60 fps（保守目标 30 fps）。
