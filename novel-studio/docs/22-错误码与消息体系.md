> 上游：`01-系统架构.md`（§6 错误边界与降级、§13 错误兜底与消息体系）、`20-IPC契约.md`（§5 错误契约）

## 1. 要解决的问题

系统出错时，最容易犯的三个错误：

| 反面案例 | 后果 |
|----------|------|
| 把 `err.message` 直接弹给用户 | 用户看到 `ffmpeg exited with code 1` 或 `SQLITE_BUSY: database is locked`，完全无法行动 |
| 每个模块自己拼提示文案 | 同一类错误在不同页面文字不同；想改文案要翻遍代码；无法统一走向导/日志 |
| 只管已知错误，未知错误没有兜底 | 出现未预期异常时界面静默卡住、或弹一个空白框、或整个 Vue 树崩掉白屏 |

**本方案的目标**：任何一处抛出的错误，**无论是否已知**，最终都能变成一句用户看得懂的话 + 一个可执行的建议，并且**开发侧能凭编号立刻定位**。

## 2. 双轨编号（已确认口径）

| 轨道 | 形式 | 用途 | 谁看 |
|------|------|------|------|
| **语义键**（主） | `RECORD_DEVICE_LOST` | 代码里的稳定标识；TS 自动补全；枚举可穷举 | 开发 |
| **数字编号**（派生） | `E200005` | 日志、QA 单、用户报障口述（"我报 E200005"） | 运维/支持/用户 |

**关键规则：数字编号不手写，由语义键确定性导出。**

```ts
// 段号 + 段内序号，5 位数字
resolveCode('RECORD_DEVICE_LOST')  // → 'E200005'
```

派生算法（见 `errors.ts` 的 `resolveIndex`）：段号固定，段内序号按 `messages.ts` 中**该段的声明顺序**生成。因此：

> **纪律 1**：**新增消息只能追加在所属段的末尾，禁止在段中间插入或删除条目。**
> 否则该段所有后续条目的编号会整体漂移，历史日志里的 `E200005` 就指向了别的错误。

这条纪律与数据库迁移同性质：**发布即冻结**。若必须删除某条消息，做法是保留其定义但标记 `deprecated: true`，而不是删行。

**段号分配**

| 段号 | 常量名 | 覆盖范围 |
|------|--------|----------|
| `1` | `GENERIC` | 通用（校验、权限、磁盘、未知兜底） |
| `2` | `RECORD` | 录音/设备/切片/片段/处理链 |
| `3` | `BOOK` / `IMPORT` | 书籍导入与解析 |
| `4` | `EXPORT` | 混音与导出 |
| `5` | `CANVAS` | 画本、角色、任务包 |
| `6` | `AI` | Provider、embedding、ASR、TTS |
| `7` | `DATA` | 数据库、项目包、备份、文件系统 |
| `8` | `TASK` / `QUEUE` | 任务队列 |
| `9` | `APP` | 应用生命周期、窗口、更新 |
| `0` | `INTERNAL` | 框架内部（Vue / 未捕获异常兜底） |

## 3. 消息表结构（`src/shared/messages.ts`）

```ts
interface ErrorMessage {
  /** 用户看到的标题，一句话，≤ 24 字，不带句号 */
  title: string
  /** 一句话说明原因或后果，≤ 60 字；未知原因时留空（UI 显示标题即可） */
  detail?: string
  /** 用户可执行的下一步（纯文案，动作由 action 字段决定） */
  hint?: string
  severity: 'info' | 'warning' | 'error' | 'fatal'
  action: 'retry' | 'open_settings' | 'open_folder' | 'reload' | 'contact_support' | 'dismiss' | 'none'
  /** 默认 true：网络抖动、忙、临时不可用 */
  retryable?: boolean
  /** 开发侧补充说明（不进用户界面，只进日志与诊断包） */
  dev?: string
  /** 参数占位符声明（用于校验与文档生成） */
  params?: readonly string[]
  deprecated?: boolean
}
```

**占位符插值**：`title/detail/hint` 中的 `{name}` 会被 `params` 里的值替换。

> **占位符书写规约（重要，踩过坑）**：占位符必须**裸写**，并且用中文书名号包裹以保证中文排版：
> `文件「{name}」可能已被移动。`
>
> **不要**写成 `文件“{name}”可能已被移动。` —— 全角引号会让静态校验与文档生成脚本无法识别占位符
> （正则需匹配 `\{(\w+)\}`，而 `“{name}”` 会让某些写法漏判），结果就是「params 声明了却校验不出使用」。
> 统一用 `「」` 后，`validatePlaceholders()` 与 `scripts/gen-error-docs.ts` 都能正常工作。

```ts
'FILE_TOO_LARGE': {
  title: '文件过大，无法导入',
  detail: '该文件「{size}」，超过上限「{max}」。',
  hint: '可在「设置 → 导入」中调整上限。',
  severity: 'warning', action: 'open_settings',
  params: ['size', 'max'],
  dev: '检查 settings.import.maxFileSizeBytes'
}
```

**文案纪律**
1. **不出现技术名词**：不写 `ffmpeg`、`SQLite`、`EACCES`、`IPC`、`undefined`、堆栈、文件绝对路径（含用户名）。
2. **必须可行动**：能重试就给 `action: 'retry'`；需配置就 `open_settings`；实在没办法才 `contact_support`。
3. **不甩锅**：不写"操作失败"，要写清"哪一步失败、为什么、怎么办"。
4. **英文/路径等原样内容**用参数传入并**加引号**：`无法解析文件“{path}”。`

## 4. 业务异常（`src/shared/errors.ts`）

**唯一异常类型**：`AppError`（别名 `BusinessError`，两者的关系是同一个类，便于业务代码读起来更顺）。

```ts
class AppError extends Error {
  code: string                    // 语义键，如 'RECORD_DEVICE_LOST'
  numericCode: string             // 派生编号，如 'E200005'
  severity: Severity              // 从消息表取，可被构造参数覆盖
  action: ErrorAction
  retryable: boolean
  params: Record<string, string | number>
  details?: Record<string, unknown>   // 结构化附加信息（进日志，不进 UI）
  cause?: unknown                     // 原始错误
  causeChain: string[]                // 被包裹的原始错误摘要链（log-only，UI 永不显示）
}
```

### 4.1 为什么必须"包裹"而不只是"新建"

原始错误带着最有价值的信息（哪个文件、哪个参数、哪个退出码），但它不能给用户看。所以：

```
原始错误（ffmpeg 退出码 1 + stderr）
   ↓ 包裹（wrap）
AppError('FFMPEG_FAILED', { params: { task: '音频降噪' }, cause: raw, details: { cmd, stderr } })
   ↓ 序列化过 IPC
IE<T> { ok: false, error: SerializedAppError }
   ↓ 渲染进程兑现
ElMessage.error(标题) + 「查看详情」展开 hint；开发模式额外显示 causeChain
```

**三层各看各的**：用户看 `title/detail/hint`；支持看 `numericCode` + `causeChain`；开发看 `details.cmd`。

### 4.2 包裹规则（`wrapUnknown`）

```ts
function wrapUnknown(e: unknown, fallback = 'INTERNAL'): AppError {
  if (isAppError(e)) return e                        // 已是业务异常：不重复包裹
  if (e instanceof Error) {
    if (isAbortError(e)) return AppError.of('TASK_CANCELLED')   // 取消不是错误
    return AppError.of(fallback, { cause: e })        // 未知 → 兜底码
  }
  return AppError.of(fallback, { details: { raw: String(e) } })  // 抛了字符串/数字
}
```

**规则**
| 情况 | 处理 |
|------|------|
| 已是 `AppError` | 直接返回（**不重复包裹**，否则用户看到"发生了未知错误"） |
| `AbortError` / 主动取消 | 映射为 `TASK_CANCELLED`，UI **不弹提示**（取消是正常操作） |
| Node 系统错误（`errno`/`code`） | 按映射表转到业务码（见 §4.3），而不是笼统的 `INTERNAL` |
| 抛了非 Error（字符串/对象） | 归入 `INTERNAL`，原值放 `details.raw` |
| 页面/组件渲染异常 | 归入 `INTERNAL`，走 Vue 错误边界（§6） |

### 4.3 系统错误的映射表（提高兜底质量的关键）

不映射的话，90% 的兜底都会退化成 "发生了未知错误"，用户毫无头绪。

| Node `code` | 业务码 | 用户看到 |
|-------------|--------|----------|
| `ENOENT` | `FILE_NOT_FOUND` | 文件不存在或已被移动 |
| `EACCES` / `EPERM` | `PERMISSION_DENIED` | 权限不足，请检查文件夹权限 |
| `ENOSPC` | `DISK_FULL` | 磁盘空间不足，需释放 {need} |
| `EMFILE` / `ENFILE` | `INTERNAL`（附 hint：请重启应用） | 同时打开的文件过多 |
| `EBUSY` | `FILE_BUSY` | 文件被其他程序占用 |
| `EROFS` | `PERMISSION_DENIED` | 目标位置只读 |
| `SQLITE_BUSY` / `SQLITE_LOCKED` | `DB_BUSY` | 数据库繁忙，请稍后重试 |
| `SQLITE_CORRUPT` / `SQLITE_NOTADB` | `DB_CORRUPT` | 数据库损坏（阻断写，引导恢复） |
| `SQLITE_FULL` | `DISK_FULL` | 磁盘空间不足 |
| `ERR_MODULE_NOT_FOUND` | `INTERNAL`（hint：安装可能不完整） | 程序文件缺失，建议重新安装 |
| `ETIMEDOUT` / `ECONNRESET` / `ENOTFOUND` | `PROVIDER_TIMEOUT` / `PROVIDER_ABORTED` | 网络异常 |
| `MEDIA_ERR_*` / `NotAllowedError`（getUserMedia） | `DEVICE_PERMISSION` | 未授权使用麦克风 |

> 映射表集中在 `errors.ts` 的 `SYSTEM_ERRNO_MAP`，**新增系统错误时只改这里**，不改业务代码。

## 5. 三级兜底

```
┌─ 第一级：业务显式抛出 ────────────────────────────────────────────┐
│  业务代码在最清楚上下文的地方抛出精确错误                          │
│  throw AppError.of('RECORD_DEVICE_LOST', { params: { device: 'USB Mic' } }) │
│  → 用户看到最准确的原因与建议                                     │
└──────────────────────────────────────────────────────────────────┘
                            ↓ 未捕获
┌─ 第二级：边界包裹（IPC handler / 任务执行器 / 服务层入口）──────────┐
│  捕获一切，wrapUnknown 转成 AppError，附加 channel/task/chapter 上下文 │
│  → 用户看到按映射表转出的具体错误（多数落到这里也能说得清楚）        │
└──────────────────────────────────────────────────────────────────┘
                            ↓ 仍未处理
┌─ 第三级：全局钩子 + 错误边界 ─────────────────────────────────────┐
│  主进程：uncaughtException / unhandledRejection → 写入日志 + 通知渲染 │
│  渲染进程：app.config.errorHandler / window.onerror /              │
│           unhandledrejection / <ErrorBoundary> → 全局兜底提示        │
│  → 用户看到「发生了未预期的错误」+ 编号 + 建议导出诊断包             │
└──────────────────────────────────────────────────────────────────┘
```

**核心原则**

1. **每一级都必须留下可定位的痕迹**：日志里必须有 `numericCode` + 原始错误 + 上下文（channel/taskId/projectId）。用户报 `E200005` 时，能一眼查出来。
2. **取消不算错误**：`TASK_CANCELLED` 与 `ABORT` 系列**不弹提示**、不写 `error` 级日志（写 `info`）。
3. **同一错误不重复弹**：1.5 秒内相同 `code + params` 的消息合并为一条并累加计数（`ElMessage` 会刷屏，尤其在批量任务里）。见 §7。
4. **兜底也要有编号**：`INTERNAL` 并不是"没有编号"，它就是编号，且日志里有 causeChain。
5. **UI 永不显示堆栈**，开发模式除外（`import.meta.env.DEV`）。

## 6. 各层职责与接线点

| 层 | 文件 | 职责 |
|----|------|------|
| 共享 | `src/shared/messages.ts` | 消息表（唯一文案来源）+ 编号派生 |
| 共享 | `src/shared/errors.ts` | `AppError` / 工厂 / 包裹 / 序列化 / 兑现 |
| 主进程 | `src/main/infra/errors/install.ts` | `uncaughtException`、`unhandledRejection`、崩溃上报 |
| 主进程 | `src/main/ipc/registry.ts` | handler 包裹：校验 → 执行 → `toIpcError`（**不 throw，返回 `{ok:false}`**） |
| 主进程 | `src/main/infra/queue/runner.ts` | 任务包裹：异常 → 任务 `failed` + `error` 落库；单个失败不中断整批 |
| 主进程 | `src/main/ipc/events.ts` | `app:error` 事件：主进程主动抛出的错误推给渲染进程 |
| 渲染 | `src/renderer/src/shared/lib/ipc.ts` | 统一解包 `{ok,data,error}`；**此处兑现消息**（唯一出提示的口子之一） |
| 渲染 | `src/renderer/src/app/error-handler.ts` | `app.config.errorHandler`、`window.onerror`、`unhandledrejection` |
| 渲染 | `src/renderer/src/shared/ui/ErrorBoundary.vue` | 路由级渲染错误兜底（避免白屏） |
| 渲染 | `src/renderer/src/shared/lib/error-bus.ts` | 去重/合并/分级展示（toast / dialog / 阻断页） |

### 6.1 为什么 IPC 用 `{ok, error}` 而不是 `throw`

`ipcMain.handle` 抛出异常会让渲染进程拿到一个被 Electron 序列化过的 `Error`，**丢失自定义字段**（`code`、`retryable` 全没了，只剩 message 字符串）。因此：

- 主进程**永不 throw 出 handler**，而是返回 `{ ok: false, error: SerializedAppError }`；
- 渲染侧的 `ipc.ts` 统一判断 `ok`，失败时构造 `AppError.fromSerialized` 并交给 `error-bus`。

这样错误码、严重度、建议动作一路不丢。

### 6.2 为什么"兑现"只在两处

若每个组件都自己 `ElMessage.error(res.error.message)`，就会出现：
- 同一错误弹两次（组件 + 全局）；
- 文案绕过消息表（直接用了 `message` 字段而不是 `title`）；
- 分级不一致（该弹框的弹成了 toast）。

因此规定：**消息展示只允许走 `error-bus`**（由 `ipc.ts` 与全局钩子调用）。

## 7. 展示策略（`severity` / `action` → UI）

| severity | 展示形式 | 是否阻断 | 出现场景 |
|----------|----------|----------|----------|
| `info` | 轻提示（顶部条） | 否 | 取消、降级告知（如"已改用规则判定"） |
| `warning` | Toast 3 秒 + 可展开详情 | 否 | 文件过大、抓取被拒、模型缺失（非关键路径） |
| `error` | Toast 5 秒 + 重试按钮；**关键流程用 Modal** | 部分 | 导入失败、导出失败、录音设备丢失 |
| `fatal` | **Modal，不可自动关闭** | 是 | 数据库损坏、磁盘满、录音写入失败、主进程异常 |

**action → 按钮映射**

| action | 按钮 | 行为 |
|--------|------|------|
| `retry` | 「重试」 | 重放最后一次请求（由调用方通过 `retryFn` 注入；未注入则不显示按钮） |
| `open_settings` | 「前往设置」 | `router.push('/settings', { query: { focus: code } })`，设置页按 code 高亮相关项 |
| `open_folder` | 「打开文件夹」 | `app:showItemInFolder` |
| `reload` | 「重新加载」 | 渲染进程刷新（或 `app:relaunch` 用于 fatal） |
| `contact_support` | 「导出诊断包」 | `app:diagnostics` → 打开所在目录 |
| `dismiss` / `none` | 无 | — |

**去重与合并**

```ts
// error-bus 内部
const key = `${code}|${stableStringify(params)}`
if (lastShown.get(key) 在 1500ms 内) {
  lastShown.get(key).count++
  // 更新已有 toast 的标题为「<title>（已发生 N 次）」，不新开一条
  return
}
```

**同一错误在批量任务中的典型表现**：124 个片段处理，其中 8 个因同一原因失败 → 用户只看到 **1 条**提示：「有 8 个片段处理失败（E200041）」，点击展开看列表。这比刷 8 条 toast 好得多，也比只报 1 个、实际失败 8 个诚实。

> 因此任务类错误的正确姿势是：**任务内部逐条记录，任务结束时由任务报告统一汇总展示**，而不是每条都走 `error-bus`。`error-bus` 只负责"立刻需要用户知道的事"。

## 8. 日志与诊断

每次记录错误，日志行必须包含：

```jsonc
{
  "event": "ipc.canvas:generate.failed",
  "level": "error",
  "code": "CANVAS_EMBEDDING_UNAVAILABLE",     // 语义键
  "numericCode": "E500003",                   // 数字编号（供报障口述）
  "severity": "warning",
  "retryable": true,
  "params": { "chapter": "第1章" },
  "cause": "Error: Cannot find module 'onnxruntime-node'",
  "causeChain": ["Cannot find module 'onnxruntime-node'"],
  "context": { "channel": "canvas:generate", "taskId": "01H...", "projectId": "uuid", "chapterId": "uuid" },
  "stack": "..."                              // 仅 error/fatal 级别记录
}
```

**脱敏**（复用 `04` §5.2）：API Key、作品正文、用户目录绝对路径、系统用户名一律掩码。诊断包中 `causeChain` 保留（排障必需），但参数值按脱敏规则过滤。

**"报障三步"（写进 UI 帮助页）**
1. 记下提示里的编号（如 `E400012`）；
2. 点「导出诊断包」；
3. 把编号与诊断包一起发给支持。

## 9. 消息条目的组织与维护

| 规则 | 说明 |
|------|------|
| 单文件单来源 | 只有 `messages.ts` 有文案。**禁止**在组件、service、handler 里写用户可见的错误字符串 |
| 段内追加 | 见 §2 纪律 1 |
| 一个码一件事 | `FFMPEG_FAILED` 不区分"降噪失败"和"混音失败"，差异由 `params.task` 表达，避免码爆炸 |
| 值得区分的才分码 | 能给出**不同建议**的才拆成两个码。例如 `MODEL_MISSING`（去放置模型）与 `MODEL_CHECKSUM_MISMATCH`（模型损坏，需重新拷贝）建议不同 → 拆开 |
| 开发说明必填（内部错误） | `dev` 字段写清"去哪里查"，帮助后来者 |
| 文案走查 | 发布前由非开发同学走查一遍：能否看懂、能否行动 |

**码的复用边界**

```ts
// ✔ 正确：同一类问题用一个码，细节走参数
throw AppError.of('FFMPEG_FAILED', { params: { task: '音频降噪' }, cause: e })

// ✗ 错误：为每个滤镜建一个码（码爆炸，文案几乎相同）
throw AppError.of('FFMPEG_AFFTDN_FAILED')
throw AppError.of('FFMPEG_DEESSER_FAILED')
```

## 10. 测试要点

| 测试 | 用例 |
|------|------|
| 编号稳定性 | 快照测试：`listAllCodes()` 的输出必须与已发布版本一致（新增条目只会追加在段尾）。**这条测试能防止 §2 纪律被破坏** |
| 目录完整性 | `assertCatalogIntegrity()` 必须在启动时调用：`MESSAGES` 与 `SEGMENTS` 两处登记必须完全一致（漏登记 → 编号派生失败；多登记 → 虚键） |
| 占位符完整性 | `validatePlaceholders()` 返回空数组：凡文案含 `{x}` 的，`params` 必须声明；凡声明了的，文案必须用到 |
| 占位符写法 | 静态检查：不得出现 `“{x}”` 这类**被全角引号包裹**的占位符（会导致校验脚本漏判）。统一写 `「{x}」` |
| 占位符插值 | 缺参数时不得输出 `{name}` 原文，而是退化为安全文案（`interpolate` 的兜底行为） |
| 包裹不重复 | `wrapUnknown(wrapUnknown(e))` 结果与单次相同 |
| 取消不外显 | `AbortError` → `TASK_CANCELLED`，`error-bus` 不产生任何提示 |
| errno 映射 | 逐一构造 `ENOENT/EACCES/ENOSPC/EBUSY/SQLITE_BUSY/...`，验证映射到预期的业务码 |
| IPC 字段保全 | 主进程抛业务异常 → 渲染进程收到的 `AppError` 的 code/severity/action/retryable/params 全部完整 |
| 不外泄内部信息 | 对 `INTERNAL`/`FFMPEG_FAILED` 等，验证 UI 渲染结果中**不含**文件绝对路径、`ffmpeg`、堆栈、"undefined" |
| 去重合并 | 1.5 秒内触发同一错误 5 次 → 只产生 1 条提示且计数为 5 |
| 批量不刷屏 | 模拟 124 个片段中 8 个同因失败 → 只 1 条汇总提示 |
| 错误边界 | 让某路由组件渲染时抛错 → 显示兜底页而非白屏，且其他路由仍可用 |
| fatal 阻断 | 模拟 `DB_CORRUPT` → Modal 不可自动关闭、写入被禁止、给出恢复入口 |
| 诊断包 | 导出后检查：含 code/numericCode/causeChain，不含 API Key 与作品正文 |

### 12.2 生成器的自检（宁可报错，也不生成错文档）

`scripts/gen-error-docs.ts` 在生成前会跑五项自检，任一项失败即中止且**不覆盖已有文档**：

| # | 自检 | 拦截的问题 |
|---|------|------------|
| 1 | `assertCatalogIntegrity()` | `MESSAGES` 与 `SEGMENTS` 登记不一致（漏登记 / 虚键） |
| 2 | `validatePlaceholders()` | 占位符与 `params` 声明不一致 |
| 3 | 编号唯一性 | 两条消息派生出同一个编号 |
| 4 | `SYSTEM_ERRNO_MAP` 目标键存在 | 映射指向不存在的语义键（文档会渲染成「未定义」） |
| 5 | 标题非空且 ≤ 40 字 | 空标题、超长标题 |

### 12.3 已由测试固化的纪律

`tests/shared/errors.test.ts` 把本文的「规矩」变成了会失败的断言：

| 测试 | 守住的规矩 |
|------|------------|
| 编号快照（22 个关键码） | 已发布编号不得漂移 —— 有人往段中间插消息就会红 |
| 段内编号连续无空洞 | 删除条目会留下空洞，也会红 |
| 全局编号唯一 | 段内序号派生异常 |
| 严重度 / 动作枚举合法 | 拼写错误 |
| `retryable` 必须配重试类动作 | **文案说"可重试"但按钮不是重试** 这类不一致 |
| fatal 必须给出动作与 hint | 阻断型错误却只有"知道了"，用户卡死 |
| 用户可见文案黑名单 | 泄露绝对路径 / 堆栈 / `ffmpeg` / `undefined` 等技术名词 |
| `SYSTEM_ERRNO_MAP` 完整性 | 映射遗漏（会让错误退化成"未预期的错误"） |
| 取消不外显、不重复包裹、未知键不抛错 | §5 §4.2 的核心规则 |
| 序列化往返字段完整 | 过 IPC 后 `code/severity/action/retryable` 丢失 |
| `details` 密钥脱敏 | API Key 进日志或诊断包 |

> 这套测试不只是"防回归"，它还在**开发期就发现设计缺陷**。例如写这份测试时抓出两处真实问题：
> ① `ECONNRESET` 被映射成 `PROVIDER_ABORTED`（当取消静默吞掉，用户永远不知道网络断了）；
> ② 6 条消息声明了 `retryable: true` 却没给重试按钮（按钮与文案互相矛盾）。
> 这两个都不是笔误，而是设计层面的不一致。
