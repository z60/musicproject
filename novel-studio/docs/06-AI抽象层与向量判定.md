# 06 · AI 抽象层与向量判定

> 上游：`00-需求规格.md`（FR-2.1、FR-2.3）、`03-数据模型与存储.md`（§5 向量存储）
> 本文覆盖：Provider 抽象、Dify 适配、本地 embedding、说话人判定算法、Prompt 模板、结构化输出校验、缓存与成本。

---

## 1. 设计目标

用户当前**没有 Dify**，因此这一层的首要目标不是「接上 Dify」，而是：

1. **可替换**：换成 Dify / OpenAI 兼容 / 本地模型，业务代码零改动。
2. **可离线**：核心的说话人判定必须完全本地可跑（向量 + 规则），不依赖任何云服务。
3. **可降级**：任一 Provider 不可用时，功能退化为「规则 + 人工」，而不是报错罢工。
4. **可度量**：每一次 AI 调用都记录耗时、成本、采纳率，用于评估收益。

> **一句话原则**：**AI 是加速器，不是依赖。** 没有 AI，用户仍应能完成全流程（只是慢）。

---

## 2. 三层能力划分

```
┌───────────────────────────────────────────────────────────────┐
│ L1 规则层（纯本地、零依赖、永远可用）                            │
│  引号检测 / 对话引导语 / 分句 / 停顿推断 / 情绪词表 / 角色名抽取    │
└───────────────────────────────────────────────────────────────┘
                          ↑ 增强
┌───────────────────────────────────────────────────────────────┐
│ L2 向量层（本地 ONNX embedding + SQLite，离线可用）              │
│  说话人归属判定 / 相似台词聚类 / 角色名消歧                       │
└───────────────────────────────────────────────────────────────┘
                          ↑ 增强
┌───────────────────────────────────────────────────────────────┐
│ L3 LLM 层（可选，需 Provider；可 Mock / 本地 / 云端）            │
│  低置信行复核 / 情绪与语速标注 / 画本结构化输出 / 长文摘要        │
└───────────────────────────────────────────────────────────────┘
```

**关键约束**：L1 与 L2 必须是无条件可用的。L3 的每一次调用都要能被「跳过」而不破坏流程。

## 3. Provider 抽象

### 3.1 接口定义

```ts
// src/shared/ai-types.ts
export type ProviderKind = 'mock' | 'local' | 'openai-compatible' | 'dify'

export interface ChatMessage {
  role: 'system' | 'user' | 'assistant'
  content: string
}

export interface ChatOptions {
  model?: string
  temperature?: number
  maxTokens?: number
  /** 要求返回严格 JSON；实现方需尽力保证（如 OpenAI 的 response_format） */
  jsonSchema?: JsonSchema
  signal?: AbortSignal
  /** 用于日志与成本归因 */
  purpose?: string
  /** 是否允许把内容发送到云端；false 时必须直接抛出 LOCAL_ONLY 错误 */
  allowCloud: boolean
}

export interface ChatResult {
  text: string
  usage?: { promptTokens: number; completionTokens: number; totalTokens: number }
  model: string
  provider: ProviderKind
  latencyMs: number
}

export interface AIProvider {
  readonly kind: ProviderKind
  /** 健康探测（设置页「测试连接」用） */
  healthCheck(): Promise<{ ok: boolean; message: string; latencyMs?: number }>
  chat(messages: ChatMessage[], opts: ChatOptions): Promise<ChatResult>
  chatStream?(messages: ChatMessage[], opts: ChatOptions): AsyncIterable<string>
}

export interface EmbeddingProvider {
  readonly modelId: string
  readonly dim: number
  embed(texts: string[], signal?: AbortSignal): Promise<Float32Array[]>
  healthCheck(): Promise<{ ok: boolean; message: string }>
}
```

### 3.2 实现清单

| 实现 | 用途 | 依赖 | 状态 |
|------|------|------|------|
| `MockProvider` | 开发/测试/演示；返回可预测的假数据 | 无 | 1.0 实现 |
| `LocalEchoProvider` | 降级占位：返回「无法判定」而非报错 | 无 | 1.0 实现 |
| `OpenAICompatibleProvider` | Ollama / vLLM / LM Studio / 各类兼容网关 | HTTP | 1.0 实现 |
| `DifyProvider` | 用户未来的 Dify 应用 | HTTP | 1.0 实现（接口对齐，未联调） |
| `OnnxEmbeddingProvider` | 本地 ONNX 小模型 | `onnxruntime-node` | 1.0 实现 |
| `CloudEmbeddingProvider` | 云端 embedding（预留） | HTTP | 3.0 |

### 3.3 工厂与降级链

```ts
export async function resolveProvider(settings: AiSettings): Promise<AIProvider> {
  const chain: AIProvider[] = []
  switch (settings.provider) {
    case 'dify': chain.push(new DifyProvider(settings)); break
    case 'openai-compatible': chain.push(new OpenAICompatibleProvider(settings)); break
    case 'local': chain.push(new LocalEchoProvider()); break
    case 'mock': chain.push(new MockProvider()); break
  }
  chain.push(new LocalEchoProvider())      // 永远兜底
  return new FallbackProvider(chain)       // 依序尝试，失败自动下一个
}
```

`FallbackProvider` 的行为：
- 首个 Provider 连续失败 3 次 → 熔断 5 分钟，期间只用兜底。
- **熔断状态要在 UI 上可见**（设置页显示「Dify：已熔断，剩余 3:12」），而不是静默降级。

### 3.4 Dify 适配要点

Dify 的接口形态与 OpenAI 不同，适配时要处理这些差异（写在这里以便实现时不再查文档）：

| 差异 | Dify | OpenAI 兼容 |
|------|------|-------------|
| 对话接口 | `POST /v1/chat-messages`（`query` + `inputs` + `conversation_id` + `user`） | `POST /v1/chat/completions`（`messages`） |
| 应用类型 | Chatflow / Agent / Completion / Workflow 各有不同路径（`/workflows/run`） | 统一 |
| 响应形态 | `answer` 字段；流式是 SSE（`event: message` / `agent_message`） | `choices[0].message.content` |
| 会话 | 需要传 `conversation_id` 维持上下文；也可每次新建 | 无状态，messages 全量传 |
| 阻塞模式 | 请求 `response_mode: 'blocking'` 才是同步返回 | 天然同步 |
| 鉴权 | `Authorization: Bearer {app-xxx}`（应用级 Key，非账号 Key） | `Bearer sk-...` |
| 输入变量 | 需要通过 `inputs` 传入工作流定义的变量 | 无 |

**适配策略**
```ts
class DifyProvider implements AIProvider {
  async chat(messages: ChatMessage[], opts: ChatOptions): Promise<ChatResult> {
    if (!opts.allowCloud) throw new AppError('AI_CLOUD_DISABLED')
    // 把 messages 折叠成单个 query：system → 前缀，其余按角色拼装
    // 或（更推荐）要求后端工作流定义一个 `messages` 数组类型的字符串输入
    const query = messages.map(m => `[${m.role}] ${m.content}`).join('\n\n')
    const res = await http.post(`${this.baseUrl}/chat-messages`, {
      body: {
        query,
        inputs: this.inputs,             // 工作流变量
        response_mode: 'blocking',
        conversation_id: opts.reuseConversation ? this.conversationId : undefined,
        user: this.userId                // 稳定的匿名 ID（不传真实身份）
      }
    })
    return { text: res.answer, model: res.metadata?.model?.name ?? this.model, ... }
  }
}
```

**注意**：Dify 的 `conversation_id` 会累积上下文，用在批量逐行判定时会导致**上下文污染**（第 500 行的判定被第 1 行影响）。因此批量判定必须用「每次新建会话」模式，把上下文显式放进 prompt。

## 4. 本地 Embedding（L2）

### 4.1 模型

| 项 | 值 |
|----|-----|
| 默认模型 | `bge-small-zh-v1.5`（ONNX） |
| 维度 | **512**（以 `config.json` 的 `hidden_size` 为准，运行时校验） |
| 最大长度 | 512 token（超长截断） |
| 池化 | CLS pooling（bge 系列用 `[CLS]`，**不是** mean pooling——用错会导致效果显著下降） |
| 归一化 | 输出后立即 L2 归一化 |
| 量化 | INT8 动态量化（CPU 上快 2~3×，精度损失对相似度任务可忽略） |
| 运行 | `onnxruntime-node`，`intraOpNumThreads = min(4, cores/2)` |

### 4.2 分词

- 优先使用模型自带的 `tokenizer.json`（HuggingFace tokenizers 格式）——但 `onnxruntime-node` 不带分词器。
- 方案：用 `@xenova/transformers` 的 `AutoTokenizer` 做分词（纯 JS/WASM，不引入原生依赖），只取其 tokenizer，推理仍走 `onnxruntime-node`。

```ts
const tokenizer = await AutoTokenizer.from_pretrained(modelDir)
const enc = await tokenizer(texts, { padding: true, truncation: true, max_length: 512 })
const feeds = {
  input_ids: new Tensor('int64', BigInt64Array.from(enc.input_ids.data.map(BigInt)), enc.input_ids.dims),
  attention_mask: new Tensor('int64', BigInt64Array.from(enc.attention_mask.data.map(BigInt)), enc.attention_mask.dims),
  token_type_ids: ...   // 视模型输入而定，读取 config 决定
}
const out = await session.run(feeds)
// bge：取 last_hidden_state[:, 0, :]（CLS）→ normalize
```

**踩坑清单**
1. `int64` 张量在 `onnxruntime-node` 中必须用 `BigInt64Array`——**这是最常见的报错来源**。
2. 输入张量的名字（`input_ids` / `attention_mask` / `token_type_ids`）必须从 `session.inputNames` 读取，不要硬编码。
3. 池化方式必须从模型信息读（bge = CLS，text2vec / sentence-transformers 常见为 mean）→ 在 `models.json` 中登记 `pooling` 字段。
4. 批大小：16 起步；若 OOM 则降到 8/4/1。**必须能优雅降级**，不能崩。
5. 首次加载模型约 1~3 s，**预热**（跑一次空推理）可避免首句判定异常慢。

### 4.3 批量推理的吞吐与让路

```ts
async function embedBatch(texts: string[], ctx: TaskContext): Promise<Float32Array[]> {
  const out: Float32Array[] = []
  const BATCH = settings.embedding.batchSize      // 默认 16
  for (let i = 0; i < texts.length; i += BATCH) {
    ctx.throwIfAborted()
    const slice = texts.slice(i, i + BATCH)
    const vectors = await session.runWith(slice)  // 同步阻塞点
    out.push(...vectors)
    ctx.report(0.3 + 0.7 * (i / texts.length), `向量化 ${i}/${texts.length}`)
    await yieldToLoop()                            // 让主进程能响应 IPC（关键！）
  }
  return out
}
```
> **`yieldToLoop()` 不可省**：ONNX 推理是同步阻塞的（`session.run` 返回 Promise 但内部占满线程），不加让路会导致 UI 完全卡死。

## 5. 说话人判定算法（核心）

### 5.1 总流程

```
输入：一个章节的文本
──────────────────────────────────────────────────────────────
Step 1  分句 → 画本行初稿
        · 按换行 + 句末标点（。！？…；）切
        · 过长句（> maxLineChars）再按逗号/分号二次切
        · 保留 charStart/charEnd

Step 2  粗筛 kind（规则，L1）
        · 有引号包裹 → dialogue（并剥离引号存为 text）
        · **引号外的文字各自成行 narration**（`疑惑的看向无畏：“什么意思？”` → 旁白 + 台词）
        · 行内短引号（≤ 4 字且前后都有叙述）→ 整句 narration（拟声/强调，不是台词）
        · 纯说话人标签（`萧炎说道：`/`无畏：`/`我：`）不单独成行，已写进 cue
        · 心理描写标志（想/心想/暗忖/心中一动）→ inner
        · 其余 → narration

Step 3  角色名抽取（规则 + 词频，L1）
        · 引导语前 2~6 字窗口内的人名
        · **剧本体行首主语**（`无畏：“你瞎啊…”` / `无畏翻了个白眼：“…”`）——
          这类写法没有引导语动词，只有这条信号能抽到
        · 高频称谓（老X/小X/X儿/X兄/X老/X长老/X大人…）
        · **人名形态证据**：候选还必须像人——姓氏开头（含异体归一）/ 音译名形态 /
          角色称谓 / 行首说话人位置 / 分词器 nr，并且至少有 5% 的出现在句首。
          没有这道门，`开始(343) / 上面(354) / 尽管(245) / 躬身(106) / 随口(74)`
          会比真角色的出现次数还高（docs/91 §5.2.32）
        · jieba 分词后取高频专有名词（nr 词性）
        · 输出候选角色 + 出现次数 → 生成角色表初稿（人工确认）

Step 4  上下文拼装
        · context = [前 2 行, 当前行, 后 2 行] 拼接（可配）
        · 对 dialogue：优先拼接「最近的引导语」与「上一个说话人」

Step 5  向量判定（L2）
        · embed(context) → v
        · 对每个角色 c：score(c) = cos(v, centroid(c))
        · 排序取 Top-3
        · 若 best.score ≥ threshold 且 (best - second) ≥ margin → 归属 best
        · 否则 → needsReview=1，candidates 存 Top-3，speakerType 暂定 narration（或保持规则结果）

Step 6  规则后处理（关键，能救很多错误）
        · 「引导语明确指名」→ 直接覆盖向量结果（规则优先，因为引导语是强信号）
        · 「连续对白」：若上一行是角色 A 的台词，当前行无引导语且是 dialogue → 偏向 A
          （**同一句原文**切出的旁白行不打断这条链：它们与那句台词的字符区间是包含关系）
        · 「场景内角色过滤」：只在本节已出场角色中判定（避免把全书的角色都拿来比）
        · 短句保护：长度 < 6 字的行，向量不可靠 → 强制依赖上下文与规则

Step 7  低置信复核（L3，可选）
        · 仅对 needsReview 行调用 LLM，一次提交一批（默认 20 行）以省 token
        · LLM 返回 {lineId, character, confidence, reason}
        · 采纳条件：LLM 置信度 ≥ 阈值；否则仍标为待人工

Step 8  落库
        · 写 canvas_lines + line_embeddings
        · 更新 character_centroids（增量）
        · 统计：各角色行数、低置信比例、规则覆盖比例
```

### 5.2 相似度与阈值

```ts
function cosine(a: Float32Array, b: Float32Array): number {
  let s = 0
  for (let i = 0; i < a.length; i++) s += a[i] * b[i]
  return s                      // 已 L2 归一化，点积即余弦
}
```

| 参数 | 默认 | 说明 |
|------|------|------|
| `attributionThreshold` | **0.62** | 低于此值不归属任何角色 |
| `attributionMargin` | **0.06** | Top1 与 Top2 的差值下限（避免「两个都差不多」时瞎猜） |
| `contextWindow` | 2 | 上下文行数 |
| `autoAcceptConfidence` | 0.85 | 高于此值可「一键确认」 |
| 短句阈值 | 6 字 | 低于此值跳过向量，直接用规则/上下文 |

> **阈值必须可调且能实测**：不同作品、不同角色数量下最优阈值不同。提供一个「判定质量评估」工具：人工确认 100 行后，系统扫描阈值 0.5~0.8，显示每个阈值下的准确率与覆盖率曲线，让用户自己选（这是**最容易被忽略但价值极高**的功能）。

### 5.3 规则层细节（L1，必须扎实）

引号族（中文小说极多写法）：
```
成对： “ ”  「 」  『 』  ‘ ’  " "  ' '  《 》（书名，不算对白）
单边： — 后接对白（破折号对白）
嵌套： “他说：‘我不去。’”  → 需按最内层优先切割
```
引导语模式（需覆盖常见变体，含中间插入）：
```
[name] + (说|道|问|答|喊|叫|笑|哼|叹|嘟囔|喃喃|冷笑|怒道|沉声|低声|开口|接着) + (道|着|：|,|。)
(说|道) 在句末： “别过来。”他冷冷地说道。
插入式： “我……” 他顿了顿，“……不去了。”   ← 需按引号对切分
剧本体： 无畏：“你瞎啊？” / 无畏翻了个白眼：“你瞎啊？”   ← 无引导语动词，按「行首主语」处理
```

> **引号外的话一个字都不能丢**：`疑惑的看向无畏：“什么意思？”` 里的「疑惑的看向无畏：」不是台词，
> 但它是有声书要念的正文。所以 Step 2 除了产出 dialogue，还要把引号外的文字交出来各自成行；
> 只有**纯说话人标签**例外（已经写进 cue，念出来只是噪音）。真机事故见 docs/91 §5.2.29。
> 同理，Step 3 的抽取必须覆盖「剧本体」—— 通篇 `名字：“台词”` 的书一个引导语动词都没有，
> 只认引导语动词会让「自动抽取」抽出 0 个候选（docs/91 §5.2.30）。
**实现建议**：把引号与引导语规则做成**可配置的规则集**（JSON），而不是硬编码。因为不同作品、不同站的文本风格差异很大，用户需要能调。规则集也要有测试样例（从真实小说里摘 50 段做回归测试）。

### 5.4 判定质量的度量（核心指标）

```
人工修改率 = 用户手动改过的行数 / 总行数
```
- 这是**产品核心指标**：它直接反映 AI 是否真的省了用户时间。
- 埋点到 `metrics` 表，按作品/章节统计；若某章修改率 > 40%，说明该章判定质量差，UI 应主动建议「本章建议人工过一遍」。
- 目标：常见中文小说上 **修改率 ≤ 15%**（即准确率 ≥ 85%，对应 AC-2）。

### 5.5 重算与增量

| 触发 | 行为 |
|------|------|
| 文本被人工编辑 | `content_hash` 变化 → 该行向量作废 → **仅重算该行** |
| 人工改了说话人 | 该行加 `decidedBy='human'`，**永不自动覆盖**；同时增量更新两个角色的 centroid |
| 新建/合并角色 | 全章重算（合并时先迁移台词，再重算 centroid） |
| 换 embedding 模型 | **全项目重算**（向量空间不可比）；UI 必须给出明确警告与预计耗时 |
| 调阈值 | 只需重跑「判定」步骤，**不需要重新 embedding**（向量的复用是关键优化） |

> 因此 `line_embeddings` 与「判定结果」必须**分离存储**：向量只依赖文本+模型，判定依赖向量+阈值+角色表。这样调阈值是秒级的。

## 6. Prompt 模板

### 6.1 模板管理

```ts
interface PromptTemplate {
  id: string
  version: number              // 每次修改递增；与结果一起记录，便于回溯
  purpose: 'attribution_review' | 'emotion_tag' | 'canvas_struct' | 'character_extract'
  system: string
  userTemplate: string         // 含 {{变量}} 占位
  outputSchema: JsonSchema
  examples?: Array<{ input: string; output: string }>   // 少样本
}
```
调用时记录 `prompt_id + version`，使得「同样的输入为什么结果不同」可追溯。

### 6.2 说话人复核（`attribution_review`）

```
System:
你是一个中文有声书制作助手。你的任务是判断一句台词/旁白归属于哪个角色。
只依据给定的上下文与角色列表判断，不要编造角色。
必须只输出 JSON，不要输出任何解释性文字。

User:
## 角色列表
{{#each characters}}
- {{name}}（别名：{{aliases}}）；性格：{{desc}}
{{/each}}

## 上下文（{{#each context}}{{index}}: {{text}}\n{{/each}}）
## 待判定行
行号：{{lineIndex}}
内容：{{text}}

## 输出格式
{"lineId":"{{lineId}}","speaker":"角色名或 narration","confidence":0.0,"reason":"不超过20字"}
```

### 6.3 情绪与语速标注（`emotion_tag`）

```
System:
你是中文有声书的配音指导。为给定句子标注情绪与语速，用于指导配音演员。
情绪只能从给定列表中选择；语速只能是 slow/normal/fast。
必须只输出 JSON 数组。

User:
## 可选情绪
```

### 6.4 结构化输出校验与修复（必做）

LLM 返回的 JSON 经常有瑕疵：带 markdown 代码围栏、多余文字、字段缺失、枚举越界、ID 幻觉。

```ts
async function callStructured<T>(provider, msgs, schema: ZodSchema<T>, opts): Promise<T> {
  for (let attempt = 0; attempt < 3; attempt++) {
    const raw = await provider.chat(msgs, { ...opts, jsonSchema: toJsonSchema(schema) })
    const cleaned = stripCodeFence(raw.text)                 // 去 ```json ... ```
    const parsed = tryJsonParse(cleaned)                     // 尝试提取第一个 {...} 或 [...]
    const result = schema.safeParse(parsed)
    if (result.success) {
      // 额外校验：lineId 必须存在于本次请求的输入集合中（防幻觉 ID）
      if (allIdsValid(result.data, opts.expectedIds)) return result.data
    }
    // 修复轮：把错误回传给模型
    msgs = [...msgs,
      { role: 'assistant', content: raw.text },
      { role: 'user', content: `你的输出不符合要求，错误：${formatErrors(result.error)}\n请只输出合法 JSON。` }
    ]
  }
  throw new AppError('AI_INVALID_OUTPUT')
}
```

**三层防护**
1. **提示层**：明确要求「只输出 JSON」+ 给出 schema 示例 + 少样本。
2. **解析层**：容忍代码围栏、前后废话、尾随逗号；提取首个合法 JSON 结构。
3. **语义层**：Zod 校验 + 枚举白名单 + **ID 存在性校验**（拒绝模型编造的 `lineId`）+ 长度限制。

**失败处理**：3 次失败 → 该批次标记「AI 不可用」，退回规则结果，**不阻塞用户**，并在报告里说明。

## 7. 缓存与成本控制

### 7.1 缓存键

| 调用 | 缓存键 | 存储 |
|------|--------|------|
| Embedding | `sha256(modelId + '|' + text)` | `line_embeddings`（按 content_hash 命中） |
| 说话人复核 | `sha256(promptId + version + model + 输入集合的稳定哈希)` | `ai_cache` 表 |
| 情绪标注 | 同上 | `ai_cache` 表 |
| ASR | `sha256(audioFile)` | `cache/asr/{hash}.json` |

```sql
ai_cache(
  cache_key TEXT PRIMARY KEY,
  purpose TEXT, model TEXT, provider TEXT,
  response TEXT,            -- 原始返回
  created_at INTEGER, hits INTEGER DEFAULT 0
)
```
**TTL**：30 天；命中时 `hits++`（用于分析哪些提示词值得固化）。

### 7.2 成本控制策略

| 策略 | 说明 |
|------|------|
| 只送低置信 | LLM 只处理 `needsReview=1` 的行（通常占 10~20%），token 消耗降一个量级 |
| 批量提交 | 一次 20 行，而不是 20 次调用 |
| 只送必要上下文 | 上下文行数默认 2；发送前对白文本做长度截断（单行 > 200 字截断并标注） |
| 本地优先 | 情绪标注可先用 L1 词表命中（"冷笑/怒吼/喃喃"等），只对未命中的调 LLM |
| 预算上限 | 设置项：单次任务最大调用次数 / 最大 token（默认不限制但**显示预估消耗**） |
| 明确告知 | 首次调用云端前弹窗：「本次将发送约 N 行、约 M 字到 <域名>，是否继续？」并记住选择 |

### 7.3 用量记录

```ts
interface AiUsageRecord {
```

## 8. 降级矩阵（任何一层的失败都不能阻断流程）

| 失败项 | 影响 | 降级行为 |
|--------|------|----------|
| embedding 模型缺失/损坏 | 无向量判定 | 退化为「引号 + 引导语 + 连续对白」规则判定；UI 提示「向量判定不可用，请放置模型或改用人工」 |
| ONNX 推理 OOM | 大章节失败 | 减小 batch → 逐行推理 → 仍失败则该章标记「未判定」，进人工队列 |
| LLM Provider 不可达 | 无情绪标注、无复核 | 用规则词表标注情绪；低置信行全部进人工队列 |
| 云端被禁用（`allowCloud=false`） | 无 L3 | 同「不可达」，且不弹任何网络请求 |
| 角色表为空 | 无法判定归属 | 先跑角色抽取（L1）生成候选，提示用户「请先确认角色表」 |
| 章节文本异常（全对话无引导语） | 判定质量低 | 报告「本章引导语极少，建议人工校对」，并降低 autoAccept 阈值 |

## 9. 隐私与合规

| 项 | 规则 |
|----|------|
| 默认不外发 | 安装后 `ai.provider='mock'` 或 `'local'`，且 `allowSendTextToCloud=false` |
| 显式同意 | 切到云端 Provider 时弹窗说明「作品文本将发送至第三方」，需勾选确认 |
| 发送最小化 | 只发当前批次需要的文本，不发全书、不发文件路径、不发用户名 |
| 日志 | AI 请求/响应体**不写日志**（只记长度、耗时、状态码）；诊断包同样不含正文 |
| 本地模型优先 | 文档与 UI 均把本地方案作为推荐路径 |
| 版权提示 | 首次导入时提示「请确认你拥有该作品的制作与分发权利」（合规提示，不做强制） |

## 10. 测试策略（这一层必须重点测）

| 测试 | 方法 |
|------|------|
| 规则层单元测试 | 从 5 部不同类型小说抽取 200 段真实文本，人工标注期望结果，作为回归集 |
| 引号解析 | 覆盖嵌套引号、破折号对白、跨段对白、引号不配对等边界 |
| 判定准确率 | 在回归集上跑判定，对比人工标注，输出准确率/召回率/混淆矩阵 |
| 阈值敏感度 | 扫描阈值，输出「准确率-覆盖率」曲线，验证默认 0.62 合理 |
| Embedding 一致性 | 同文本两次推理结果完全一致；批量与单条结果一致（验证 padding 未污染） |
| 结构化输出校验 | 用 20 种「坏 JSON」（围栏、尾随逗号、缺字段、幻觉 ID、枚举越界）验证修复逻辑 |
| Provider 适配 | MockProvider 契约测试；用一个本地 Ollama 做集成测试；Dify 用录制回放（录下真实响应再回放）测解析 |
| 降级路径 | 删除模型文件、断开网络、设置 `allowCloud=false`，验证流程不崩且提示清晰 |
| 性能 | 5000 行章节的 embedding + 判定耗时；内存峰值；确认无 UI 卡死 |
