## 1. 环境限制与**已解除**的限制

### 1.1 最初的硬限制（已解除一条，另一条仍部分存在）

| 限制 | 证据 | 当时后果 | **现状** |
|------|------|----------|----------|
| **无外网** | `Invoke-WebRequest` 全部超时；DNS 无法解析 `registry.npmmirror.com` | 无法 `npm install`，因此 `tsc` / `vue-tsc` / `electron` / `vue` 全部不可用 | **已解除**：`npm install` 成功（530 个顶层包，32 个关键依赖齐备）。注意 `Invoke-WebRequest` 的 TLS 在此环境仍然坏，**不要用它判断连通性**；npm 自己走的是通的 |
| **沙箱限制** | `npm install` 默认缓存报 `EPERM`；`node --test` 报 `spawn EPERM` | npm 缓存在工作区外被拦；子进程管道通信受限 | **部分存在**：必须设 `npm_config_cache=<repo>/.npm-cache`；`node --test` 仍不可用（已改为 Worker 线程方案，见 §5.0） |

### 1.2 当前的验证策略（已包含真实类型检查）

```
能做的：  npm install（依赖到位）
          → tsc --noEmit -p tsconfig.node.json      主进程/共享/脚本/测试
          → vue-tsc --noEmit -p tsconfig.web.json  渲染进程（含 .vue 模板表达式）

做不到：  electron-vite 打包、Electron 运行时、真实麦克风/ffmpeg/ONNX 推理
```

**当前状态（实测）**：


> **关于 `--ignore-scripts`（已不再需要）**：本沙箱禁止 `spawn` 子进程，所以
> `electron-rebuild` 跑不了。而这曾导致两个连锁问题（详见 §4.2）：
> `package.json` 里的 `postinstall` 钩子让**整个 `npm install` 非零退出**，
> 而为了绕开它改用 `--ignore-scripts` 又会**连带跳过 electron 自己的 postinstall**，
> 于是 Electron 二进制根本没下载。

> `npm run fetch:native-prebuild` 显式执行。影响面是「Electron 里能否 `require('better-sqlite3')`」，

### 4.1 为什么 `npm run dev` 在本环境必然失败（两个独立阻塞点）

这两个都不是代码问题，但也**都不能靠改代码绕过** —— 记下来免得后来者重复排查。

**阻塞点 1：esbuild 需要 spawn 子进程**

```
failed to load config from electron.vite.config.ts
Error: spawn EPERM
    at ChildProcess.spawn (node:internal/child_process:420:11)
    at ensureServiceIsRunning (node_modules\esbuild\lib\main.js:1975:29)
```

`electron-vite` 启动时先让 esbuild 把 `electron.vite.config.ts` 打成一个临时 bundle，
esbuild 的原生实现会 fork 一个常驻进程与 JS 侧通信。本沙箱**禁止一切 spawn**：

```
node -e "require('node:child_process').spawnSync(process.execPath,['-e','0'])"
  → error: EPERM
```

`@esbuild/win32-x64/esbuild.exe`（9.9 MB）**在位** —— 缺的不是文件。
这与 `electron-rebuild` 失败是同一个根因：**本沙箱禁止一切 spawn**。

**阻塞点 2：`electron.exe` 尚未下载**

```
node_modules/electron/   →  checksums.json, cli.js, index.js, install.js, package.json …
                            （**没有 dist/electron.exe**，也没有 path.txt）
```

`electron` 包自己的 `postinstall` 是 `node install.js`（下载平台二进制）。
它被跳过是因为**本仓库曾经在 `package.json` 里声明了 `postinstall: electron-rebuild …`**，
而那条命令在受限环境里失败 → `npm install` 整体非零退出 → 只能用
`npm install --ignore-scripts` 装依赖 → **连带把 electron 的 postinstall 也跳过了**。

**这个问题已经修掉了**（见 §4.2）：`postinstall` 钩子已从 `package.json` 移除，
`npm install` 现在只装依赖，electron 自己的 postinstall 会正常下载二进制。

**因此：`npm run dev` 在本沙箱仍然跑不了（阻塞点 1 无解），在你机器上可以。** 步骤见 §7。

### 4.2 一个被 `postinstall` 掩盖的安装问题（已修）

这是本轮从你机器上那份 `npm install` 日志里发现的 —— **光看代码看不出来**。

```log
321 error code 4294967295
322 error path C:\projectText\cloudproject\musicproject\novel-studio
323 error command failed
324 error command C:\WINDOWS\system32\cmd.exe /d /s /c electron-rebuild -f -w better-sqlite3,onnxruntime-node
329 verbose exit -1
```

依赖其实**全都装好了**（日志里 500+ 个包都 reify 成功），但最后那一步让
`npm install` 以非零码结束。这里有两个层次的错误，第二个才是真正的坑：

**层次一：把可选步骤做成了必过门槛。**
`electron-rebuild` 只在「要在 Electron 里 `require('better-sqlite3')`」时才需要，
属于**环境相关的可选步骤**，不该阻塞 `npm install`。

**层次二（更严重）：它掩盖了「Electron 二进制没下载」。**
`npm install --ignore-scripts` 是「绕过 electron-rebuild 失败」的常用做法，
但它会跳过**所有**包的 postinstall —— 包括 `electron` 自己的 `node install.js`。
于是：

- 表面现象：装完了，`node_modules/electron` 也在
- 真实状态：`dist/electron.exe` 与 `path.txt` **都不存在** → `npm run dev` 无从启动

而日志里那一行只有 `command failed`，**完全看不出 Electron 二进制缺失**。

**修法**（`package.json`）：

```diff
- "postinstall": "electron-rebuild -f -w better-sqlite3,onnxruntime-node",
  "rebuild":     "electron-rebuild -f -w better-sqlite3,onnxruntime-node",
```

- `npm install` 只装依赖 → 成功，且 electron 的 postinstall 正常下载二进制
- 需要 Electron ABI 二进制的人**显式**跑 `npm run fetch:native-prebuild`（取预编译包，不需编译工具链）
- 并在 `package.json` 的 `comments.no-postinstall-rebuild` 里写清原因，防止后来者加回去

**给你的操作顺序**（`node_modules` 已存在时，electron 的 postinstall 不会自动重跑）：

```bash
npm install                      # 本次应该干净成功（postinstall 已移除）
node node_modules/electron/install.js   # 补下载 Electron 二进制（因为之前被 --ignore-scripts 跳过了）
npm run fetch:native-prebuild    # 取 Electron ABI 的预编译二进制（不需编译工具链）
npm run dev
```

验收：`node_modules/electron/dist/electron.exe`（Windows）存在，且 `path.txt` 存在。

```html
     参数类型由命名函数显式声明；子组件的事件类型由 defineEmits 推断。 -->
<el-slider @update:model-value="onPauseSliderInput" />
```

删掉标注后，`vue-tsc` 立刻暴露出 **137 个此前被掩盖的真实类型错误**（隐式 any、
可空 props、`retryFn` 返回值不兼容、`Record<CleanOptionKey, boolean>` 的键退化等）。
**这就是「跳过整个文件」的代价：不是少报几个错，而是整片区域无人看守。**
现在这条由 `check:template-types` 门禁守住。

### 5.0.2 测试计数教训：**静默少算用例比测试失败更危险**

`npm test` 的用例总数曾经**每次运行都不一样**：有时 1333、有时 1347、有时 1351，
而每一轮都照样打印「全部通过 ✓」。根因是统计方式：

| 阶段 | 做法 | 结果 |
|------|------|------|
| 最初 | 替换 `process.stdout` 抓 TAP，`setTimeout(150)` 后找汇总行 `# pass N`；找不到就退化成「数 `ok <n> -` 行」 | 汇总行常来不及写完 → 走退路 → **把 `describe` 套件也算成用例**，数字虚高且随机器负载漂移 |
| 第二阶段 | 改成**轮询等待**汇总行，15s 超时 | 全部文件都超时：汇总行的输出**绕过了被替换的 `process.stdout.write`**（等到 1s 静默、或等进程该退出，捕获文本里始终没有 `# pass`） |
| 第三阶段 | 用 `run({ reporter: 'spec' })` 的返回流 | Worker 里 `for await` 拿不到任何 chunk；`spec(stream)` 二次转换会挂住；裸 `run()` 发出的是**测试事件对象**而非文本 |
| 第四阶段 | 裸 `run()` 逐条消费事件 | `run()` 不带参会按 Node 默认 glob **把仓库里所有 `*.test.ts` 都 spawn 一遍** → 42 个 `test:fail`，错误全是 `spawn EPERM`（当时仓库里正好 42 个测试文件） |
| **现在** | **逐行分类 TAP 结果行**：`ok N - 名称` 后的诊断块里 `type: 'test'` 是用例、`type: 'suite'` 是 `describe` 套件 | 完全确定：**43 文件 / 1183 用例**，连跑 5 次一致 |

同时加了两道防线：
1. 出现**无法分类**的结果行（缺 `type:`）→ 整轮判失败，绝不静默放过；
2. `scripts/tap-parse.ts` 是纯函数并带 8 个单测（`tests/main/tap-parse.test.ts`），
   钉住「套件不算用例」「未分类必须暴露」「`套件+用例+失败+跳过 == 全部结果行`」这些不变式。

**为什么值得单独记一笔**：少算的用例不会让任何断言失败，只会安静地给出一个漂亮数字。
如果没注意，后续只会看到「测试全绿」而不知道有 200 个用例从没被计入。

### 5.4 错误信息把根因吃掉的三层原因（真实事故，首次真机启动时暴露）

第一次在真机上跑起来时，`open-database` 失败，日志里只有：

```
{"level":"error","event":"app.boot.stepFailed","step":"open-database","error":"AppError: 发生了未预期的错误"}
```

「数据库打不开」这个最关键的事实，以及**为什么打不开**，全都不见了。
三层原因叠在一起，修任何一层都不够：

**第 1 层：用了未登记的消息键。**
`src/main/db.ts` 里写了 `AppError('DB_OPEN_FAILED')` 与 `AppError('DB_NOT_OPEN')`，
但这两个键**从来没加进 `messages.ts`**。而 `getMessage()` 对未登记的键是
**静默回退**到 `INTERNAL`（这是刻意的设计：错误处理路径本身不能抛错）。

后果有两重：
- 用户看到的标题变成 `INTERNAL` 的「发生了未预期的错误」；
- 回退信息（`dev: '未登记的语义键 "DB_OPEN_FAILED"…'`）**只进 `dev` 字段**，
  而启动日志走的是 `event` + 结构化字段，根本不会打印 `dev`。

于是「键名拼错」这件事本身也被完美隐藏了。
**修法**：把两条补进 `messages.ts`，并且**追加在 7 段末尾**（编号纪律），
`DB_OPEN_FAILED = E70009`、`DB_NOT_OPEN = E70010`，已发布编号一位不动。

> 这里差点犯第二个错：第一次我是插在 `DB_CORRUPT` 后面的「语义位置」，
> 结果 `AUDIO_FILE_MISSING` 从 `E70008` 漂到 `E70009`，
> 被 `errors.test.ts` 的**编号快照测试**当场拦下。
> 那条测试的价值就在这里 —— 编号漂移对用户是「历史报错对不上文档」，平时完全看不出来。

**第 2 层：`AppError.message` 是给用户看的标题，不是诊断信息。**
真正能定位的是 `cause` / `causeChain`（例如
`NODE_MODULE_VERSION 115 ... requires 125` 这种原生模块 ABI 不匹配）。
而 `bootstrap/index.ts` 的启动报告只存 `name: message`：

```ts
error: e instanceof Error ? `${e.name}: ${e.message}` : String(e)
```

**修法**：在**知道原始错误的地方**（`openDatabase` 的每个 throw 点）先记一次
`log.errorFields(e, ...)` 再抛。做法是 `logAndRethrow()` —— 返回 AppError 让调用方
必须写成 `throw logAndRethrow(err, log)`，语法上强制「必须抛」，避免有人顺手吞掉。
日志里现在会带上 `code` / `numericCode` / `cause` / `causeChain` / `stack` / `details`。

**第 3 层：只记字符串，丢掉了结构化字段。**
`main/index.ts` 的 `onStepFinish` 原本记的是 `error: r.error`（一个字符串）。
改为 `errorFields(new AppError('INTERNAL', { details: { step, stepError } }), ...)`，
让日志带上完整的错误对象；`app.boot.aborted` 也补上了 `logDir` 与 `dbPath` ——
这两个是这类启动故障最先要看的东西，之前要用户自己去找。

**一句话教训**：错误处理链路上，**每一层「顺手简化一下」都会吃掉一层根因**。
未登记的键会被静默回退、`message` 不是诊断信息、字符串化会丢字段 ——
三个都是「看起来更整洁」的写法，合起来让一个 ABI 不匹配变成了「发生了未预期的错误」。

### 5.6 静默故障两例：SQL 没进产物、协议权限时机错（已修）

这两条的共同特征：**应用能起来一部分，功能静默缺失，报错指不到地方**。
都是首次真机启动时暴露的。

#### (1) 迁移 SQL 没进构建产物 → 库开了但一张表都没有

```
db.opened                    applied: 7, schemaVersion: 0
db.migrate.failed.readOnly   reason: DB_MIGRATION_FAILED
```

`applied: 7` 说明 7 条 PRAGMA 全部成功、**数据库确实打开了**；
但 `schemaVersion: 0` 说明**迁移一条都没跑**。查 `out/` 才发现：

```
out/main/index.js       269,680 B
out/preload/index.cjs     7,015 B
out/ 里的 .sql 文件数：0        ← out/main/infra/db/migrations/ 目录根本不存在
```

根因：迁移 SQL 是**运行时用 `readFileSync(join(dirname(import.meta.url), file))` 读**的
（打包器不认识 `.sql`，不会带进 bundle），而 `electron.vite.config.ts` 只配了入口、
没有把 SQL 复制进产物目录。

值得一提的是：`src/main/infra/db/migrations/index.ts` 的注释里**早就写明了这个前置条件**
（「打包时需把 … 复制到 out 目录」），但被当成「打包配置的事，不在本次范围」而没实现 ——
而 `npm run dev` 走的也是这条路，**所以它在开发期就会炸，不是打包才炸**。

**修法**：在 `electron.vite.config.ts` 的 `main` 段挂一个 `writeBundle` 插件复制 SQL。
三个设计取舍都写在配置文件注释里：

| 选择 | 理由 |
|------|------|
| **vite 插件**，不是 postbuild 脚本 | `dev` 与 `build` 都会走 vite 插件；postbuild 只覆盖 `build`，`npm run dev` 依然会踩同一个坑 |
| **内联在配置文件里**，不抽成 `vite-plugins/*.ts` | electron-vite 启动时先用 esbuild 把配置打成临时 bundle；跨文件 import 多一个解析环节，而本环境禁止 spawn（跑不了 esbuild）**无法预先验证它**。不引入无法验证的风险 |
| `writeBundle`，不是 `buildEnd` | 要等文件真的落盘之后再写进同一棵目录树 |

**验证方式**（纯 `node:fs`，不需要 esbuild）：复刻复制逻辑跑一次，再模拟
`out/main/index.js` 的 `migrationsDir` 去读并比对 hash：

```
✓ 001_init.sql  30559 字符   hash 与清单一致
✓ 002_seed.sql  23024 字符   hash 与清单一致
```

#### (2) `registerSchemesAsPrivileged` 在 ready 之后调用 → 立即抛错

```
[FAIL] register-media-protocol   0ms   AppError: 发生了未预期的错误
** 启动在中止于：register-media-protocol **
```

`0ms` 就失败，说明是**立即抛错**。把可能原因逐条排除：

- **权限字段名不合法？** 对照 `electron.d.ts` 的 `Privileges` 定义，
  `standard / secure / supportFetchAPI / stream / bypassCSP` 全是合法字段 → 排除
- **`protocol` 对象缺失？** 代码里有 `if (!electron?.protocol)` 守卫 → 排除
- **剩下唯一解释：调用时机。** `protocol.registerSchemesAsPrivileged` 是 Electron 的
  **ready 前** API，而我把「声明权限」和「注册 handler」一起放在了启动流程第 11 步 ——
  那一步在 `await app.whenReady()` 之后。

**修法**：权限声明移到 `src/main/index.ts` 的 `whenReady()` **之前**；
第 11 步只保留 ready 之后才允许的 handler 注册。

这里的关键认识是：**这两件事的时机约束不同，必须拆开**
（`registerSchemesAsPrivileged` 要在 ready 前，`protocol.handle` 要在 ready 后）。
失败处理上，权限声明用 try/catch 包住且**不致命** ——
没有媒体协议时「播放项目内音频」不可用，但书籍/画本/设置仍能用，不该把整个应用挡住。

#### 用测试锁住

两条都属于「不报错但功能静默缺失」，所以在
`tests/main/bootstrap-wiring.test.ts` 加了 4 条断言：

- 协议权限声明必须出现在 `whenReady` **之前**（按代码行判断，忽略注释里的提及）
- `bootstrap-steps.ts`（ready 之后执行）**不得**再调用 `registerMediaSchemePrivileges`
- `electron.vite.config.ts` 必须挂 `writeBundle`，且配置里有 migrations 目录
- 迁移 SQL 必须已按 LF 归一化（CRLF 会让 hash 校验失败，
  而那条报错看起来像「有人改了已发布的迁移」，根因却是换行符）

### 5.0 测试隔离：为什么用 Worker 线程

三种方案都试过，结论写在这里免得后来者重走：

| 方案 | 结果 |
|------|------|
| **同进程** import 各测试文件 | ❌ 模块级状态互相污染，表现为「单独跑都过、一起跑有 8 项失败」 |
| **子进程**（`node --test` 的官方做法） | ❌ 本环境禁止 spawn：`spawnSync ... EPERM`；实测 `node --test` 41/41 全挂 |
| **Worker 线程** | ✅ 可用。每个 Worker 有独立模块注册表，等价文件级隔离，且在无沙箱限制的机器上同样有效 |

**顺带修掉的两个真实缺陷**（由测试抓出，都在基础设施层）：

1. **`TaskQueue.dispose()` 不等在跑任务落终态**：`cancel()` 对 running 任务只设 abort 信号就返回，`dispose` 直接 `await` 它就以为完成了 —— 调用方随后查状态会看到 `running`，而这些任务会以 `running` 留在库里（应用已退出，只能等下次启动才被标为 interrupted）。已改为等待 `RunningEntry.done`，带**可清除的超时**兜底。
   - 附带教训：第一版兜底用了裸 `setTimeout` 做 race，任务早已完成后事件循环仍等到超时才退出，**把一个 300ms 的测试拖成 30 秒**。现在超时计时器在 `finally` 里清除。
2. **`queue.test.ts` 的 `createHarness` 参数错位**：4 处调用把选项当第一个参数传（`createHarness({ retryDelaysMs: [...] })`），specs 收到对象 → `opts.specs is not iterable`。已在 harness 内归一化参数，两种调用方式都支持。

### 5.1 一个代价很大的教训：注释里的 `/*` 会毁掉解析

**现象**：`src/main/bootstrap/cleanup.ts` 无法被 import，报
`Expected '{', got 'interface'` —— 报错位置指向的 `interface` 完全合法。
最终定位到该文件第 31 行的 JSDoc：

```ts
/** 要清理的临时目录根（如 `<userData>/cache/tmp`、`<projects>/*/.tmp`、任务临时根） */
//                                          ^^^^^^^^^^^^^^^^
```

`/*` 让类型剥离解析器**重新进入嵌套块注释**，注释永不闭合，后续内容全被吞掉。
排查期间我反复怀疑 "interface 有问题"、怀疑文件被并发写入、怀疑有隐藏字符，
浪费了大量时间 —— 因为报错位置与根因无关。

**更糟的是我的修复过程**：为了消除这个隐患，我用脚本把注释里所有 `/*` 批量改写成
`* /`。该脚本**没有正确区分注释边界与 glob 写法**，把 `src/shared/*.ts` 改成了
`src/shared* /.ts`（可读性破坏），并在若干文件里**提前闭合了注释块**，
使注释文本变成代码（`app-lifecycle.ts` 因此报 `ReferenceError: recordings is not defined`），
一度让测试通过数从 1100+ 掉到 46。

**修复**：逐处按原文精确还原（不改语义、不改路径示例），并新增 `check:syntax` 的
隐患检测 —— **但判据收紧为「起始符之后本行没有结束符」**，因为
`src/shared/*.ts` 这类 glob 其实无害（注释会在本行正常闭合），
一律报警只会让检查失去可信度。

**给后来者的规矩**：写注释时不要直接写出「斜杠紧跟星号」的两字符注释起始符。
需要表达 glob 时用 `**` 或「星号与斜杠之间留空格」。

**两个容易踩且症状隐蔽的点，已用测试钉住**（`tests/main/bootstrap-wiring.test.ts`，34 个用例）：

   **窗口能开但渲染进程没有 `window.api`**，而且主进程日志里没有明显报错。
2. **preload 产物必须是 `.cjs`**：`package.json` 是 `"type": "module"`，
   `.js` 会被按 ESM 解析，而 `sandbox: true` 的 preload 只有受限的 CJS `require`。
   `electron.vite.config.ts` 因此把 preload 产物定为 `[name].cjs`，
   入口里的 `resolvePreloadPath()` 与它保持一致，并有测试守着。
3. **主进程入口不用 `__dirname`**：主进程产物是 ESM，`__dirname` 能否用取决于
   electron-vite 是否注入 CommonJS shim（我们读了它的 dist，发现只在部分路径注入）。
   改用 `import.meta.url` 换算 —— 这条也有测试守着（只检查代码行，注释里提到不算）。

**`HandlerDeps` 各端口的实现程度（如实标注）**：

| 端口 | 实现 |
|------|------|
| `log` / `env` / `settings` / `db` / `events` / `sends` | 完整实现 |
| `tasks` | 用真实 `TaskQueue`，但存储是**内存实现**（SQLite 任务存储未实现）→ 重启后任务列表为空 |
| `capabilities` | ffmpeg 与模型来自启动期真实探测；`embedding.available` 恒为 false（无 ONNX 推理实现） |
| `diagnostics` | **明确未实现**，调用即抛 `NOT_IMPLEMENTED`（诊断包需要 zip 写入适配层） |
| `provider` | **明确未实现**，调用即抛 `NOT_IMPLEMENTED`（真实连通性测试需要按 provider 发最小请求） |

未实现的端口**不返回假数据** —— 返回空对象会让 UI 显示「导出成功 / 测试通过」
这种真假难辨的状态，与 `handlers/placeholders.ts` 的纪律一致。

## 7. 验收顺序（当前可直接执行）

```bash
# 1. 依赖（postinstall 钩子已移除，这一步应干净成功）
npm install

# 2. 补下载 Electron 二进制
#    仅当 node_modules 已经存在时必需（npm 不会重跑已装包的 postinstall）：
npm run ensure:electron

# 3. 获取 Electron ABI 的原生模块二进制
#    **不要**先试 npm run rebuild —— 它在 Windows 上会调 node-gyp **编译 C++ 源码**，
#    需要 Visual Studio Build Tools + Python，而这不是必须的：
#    better-sqlite3 为 Electron 发布了预编译包，取来即可（见 docs/02 §4）
npm run fetch:native-prebuild

# 4. 在 Electron 里真的 require 一次 —— ABI 的唯一权威验证
npm run check:native

# 5. 类型检查（当前应为 0 错误）
npm run typecheck

# 6. 全套自动防线（当前应为 exit 0）
npm run verify

# 7. 覆盖率与契约报告（会重新生成 docs/90）
npm run check:coverage

# 8. 开发模式
npm run dev
#    期望看到的日志（写到 <userData>/logs/YYYY-MM-DD.log）：
#      app.boot.start → 15 步逐步 ok → app.boot.report
#      ipc.registered  implemented 28 / placeholders 129 / registered 157
#      window.renderer.loaded
#      app.ready
#    窗口起来后：F12 打开 DevTools，在 Console 里执行 `window.api` 应返回一个对象
#    （若它是 undefined → preload 没加载上，检查 out/preload/index.cjs 是否存在）

# 9. 最后才是打包
npm run build
```

**第 3 步为什么不是 `npm run rebuild`**

`rebuild` 走的是 `electron-rebuild` → `node-gyp` **从源码编译**，需要
Visual Studio Build Tools（C++ 工作负载）+ Python，而且会失败在构建期而不是运行期。

`fetch:native-prebuild` 改成从镜像取**现成的 Electron 预编译包**：

```
https://registry.npmmirror.com/-/binary/better-sqlite3/v11.3.0/
  better-sqlite3-v11.3.0-electron-v125-win32-x64.tar.gz      (922 KB)
```

（`v125` 是 Electron 31.7.0 的 ABI 版本，由 `node-abi` 给出。）

再强调一次第 4 步的作用：**ABI 是否匹配没有离线判据**。
实测两个「看起来能行」的办法都是错的 ——
读 PE 头的 `MajorImageVersion`（那里根本没有 ABI 信息），
以及在 Node 里 `require()`（Node ABI 127 能成功加载 Electron ABI 125 的二进制，
因为 better-sqlite3 入口带降级逻辑）。只有**在真 Electron 进程里加载**才算数。

**关于 `--ignore-scripts`**：现在**不需要**它了。
之前需要它，是因为本仓库自己声明了 `postinstall: electron-rebuild …`，
而那一步在受限环境会失败。那个钩子已经移除（原因见 §4.2），
所以 `npm install` 会正常结束，`electron` 自己的 postinstall 也会正常下载二进制。

万一你机器上 `npm install` 仍然失败，**先看它失败在哪一步**，不要直接加 `--ignore-scripts` ——
那会连带跳过 electron 的二进制下载，把「安装失败」变成「安装成功但跑不起来」，更难查。

**下一步的开发优先级**（按收益从高到低）：

1. `src/main/features/audio/`（recorder / processor / mixer / exporter 四个编排层）
   —— 算法都已在 `src/shared/audio/**` 里写好且测过，这是打通「录音 → 处理 → 成品」的关键路径
2. 上述四域对应的 IPC handler（录音/对轨/音频处理/混音导出共 129 个通道里的大头）
3. `src/main/features/book/alignment/`（对轨编排：录制片段 ↔ 画本行的匹配与落库）
