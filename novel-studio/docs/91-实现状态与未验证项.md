## 1. 环境限制与**已解除**的限制

### 1.1 最初的硬限制（已解除一条，另一条仍部分存在）

| 限制 | 证据 | 当时后果 | **现状** |
|------|------|----------|----------|
| **无外网** | `Invoke-WebRequest` 全部超时；DNS 无法解析 `registry.npmmirror.com` | 无法 `npm install`，因此 `tsc` / `vue-tsc` / `electron` / `vue` 全部不可用 | **已解除**：`npm install` 成功（530 个顶层包，32 个关键依赖齐备）。注意 `Invoke-WebRequest` 的 TLS 在此环境仍然坏，**不要用它判断连通性**；npm 自己走的是通的 |

### 1.2 当前的验证策略（已包含真实类型检查）

```
能做的：  npm install（依赖到位）
          → tsc --noEmit -p tsconfig.node.json      主进程/共享/脚本/测试
          → vue-tsc --noEmit -p tsconfig.web.json  渲染进程（含 .vue 模板表达式）
```

**当前状态（实测）**：


> **关于 `--ignore-scripts`（已不再需要）**：本沙箱禁止 `spawn` 子进程，所以
> `electron-rebuild` 跑不了。而这曾导致两个连锁问题（详见 §4.2）：
> `package.json` 里的 `postinstall` 钩子让**整个 `npm install` 非零退出**，
> 而为了绕开它改用 `--ignore-scripts` 又会**连带跳过 electron 自己的 postinstall**，

### 4.1 为什么 `npm run dev` 在本环境必然失败（两个独立阻塞点）

这两个都不是代码问题，但也**都不能靠改代码绕过** —— 记下来免得后来者重复排查。

**阻塞点 1：esbuild 需要 spawn 子进程**

```
failed to load config from electron.vite.config.ts
Error: spawn EPERM
    at ChildProcess.spawn (node:internal/child_process:420:11)
    at ensureServiceIsRunning (node_modules\esbuild\lib\main.js:1975:29)
```

`electron-vite` 启动时先让 esbuild 把 `electron.vite.config.ts` 打成一个临时 bundle，
esbuild 的原生实现会 fork 一个常驻进程与 JS 侧通信。本沙箱**禁止一切 spawn**：

```
node -e "require('node:child_process').spawnSync(process.execPath,['-e','0'])"
  → error: EPERM
```

`@esbuild/win32-x64/esbuild.exe`（9.9 MB）**在位** —— 缺的不是文件。
这与 `electron-rebuild` 失败是同一个根因：**本沙箱禁止一切 spawn**。

**阻塞点 2：`electron.exe` 尚未下载**

```
node_modules/electron/   →  checksums.json, cli.js, index.js, install.js, package.json …
                            （**没有 dist/electron.exe**，也没有 path.txt）
```

`electron` 包自己的 `postinstall` 是 `node install.js`（下载平台二进制）。
它被跳过是因为**本仓库曾经在 `package.json` 里声明了 `postinstall: electron-rebuild …`**，
而那条命令在受限环境里失败 → `npm install` 整体非零退出 → 只能用
`npm install --ignore-scripts` 装依赖 → **连带把 electron 的 postinstall 也跳过了**。

**这个问题已经修掉了**（见 §4.2）：`postinstall` 钩子已从 `package.json` 移除，
`npm install` 现在只装依赖，electron 自己的 postinstall 会正常下载二进制。

**因此：`npm run dev` 在本沙箱仍然跑不了（阻塞点 1 无解），在你机器上可以。** 步骤见 §7。

### 4.2 一个被 `postinstall` 掩盖的安装问题（已修）

这是本轮从你机器上那份 `npm install` 日志里发现的 —— **光看代码看不出来**。

```log
321 error code 4294967295
322 error path C:\projectText\cloudproject\musicproject\novel-studio
323 error command failed
324 error command C:\WINDOWS\system32\cmd.exe /d /s /c electron-rebuild -f -w better-sqlite3,onnxruntime-node
329 verbose exit -1
```

依赖其实**全都装好了**（日志里 500+ 个包都 reify 成功），但最后那一步让
`npm install` 以非零码结束。这里有两个层次的错误，第二个才是真正的坑：

**层次一：把可选步骤做成了必过门槛。**
`electron-rebuild` 只在「要在 Electron 里 `require('better-sqlite3')`」时才需要，
属于**环境相关的可选步骤**，不该阻塞 `npm install`。

**层次二（更严重）：它掩盖了「Electron 二进制没下载」。**
`npm install --ignore-scripts` 是「绕过 electron-rebuild 失败」的常用做法，
但它会跳过**所有**包的 postinstall —— 包括 `electron` 自己的 `node install.js`。
于是：

- 表面现象：装完了，`node_modules/electron` 也在
- 真实状态：`dist/electron.exe` 与 `path.txt` **都不存在** → `npm run dev` 无从启动

而日志里那一行只有 `command failed`，**完全看不出 Electron 二进制缺失**。

**修法**（`package.json`）：

```diff
- "postinstall": "electron-rebuild -f -w better-sqlite3,onnxruntime-node",
  "rebuild":     "electron-rebuild -f -w better-sqlite3,onnxruntime-node",
```

- `npm install` 只装依赖 → 成功，且 electron 的 postinstall 正常下载二进制
- 需要 Electron ABI 二进制的人**显式**跑 `npm run fetch:native-prebuild`（取预编译包，不需编译工具链）
- 并在 `package.json` 的 `comments.no-postinstall-rebuild` 里写清原因，防止后来者加回去

**给你的操作顺序**（`node_modules` 已存在时，electron 的 postinstall 不会自动重跑）：

```bash
npm install                      # 本次应该干净成功（postinstall 已移除）
node node_modules/electron/install.js   # 补下载 Electron 二进制（因为之前被 --ignore-scripts 跳过了）
npm run fetch:native-prebuild    # 取 Electron ABI 的预编译二进制（不需编译工具链）
npm run dev
```

验收：`node_modules/electron/dist/electron.exe`（Windows）存在，且 `path.txt` 存在。

```html
<el-slider @update:model-value="(value: number | number[]) => setPause(Number(value))" />

<!-- ✅ 把处理逻辑搬进 <script setup lang="ts">，模板只引用函数名。
     参数类型由命名函数显式声明；子组件的事件类型由 defineEmits 推断。 -->
<el-slider @update:model-value="onPauseSliderInput" />
```

删掉标注后，`vue-tsc` 立刻暴露出 **137 个此前被掩盖的真实类型错误**（隐式 any、
可空 props、`retryFn` 返回值不兼容、`Record<CleanOptionKey, boolean>` 的键退化等）。
**这就是「跳过整个文件」的代价：不是少报几个错，而是整片区域无人看守。**
现在这条由 `check:template-types` 门禁守住。

### 5.0.2 测试计数教训：**静默少算用例比测试失败更危险**

`npm test` 的用例总数曾经**每次运行都不一样**：有时 1333、有时 1347、有时 1351，
而每一轮都照样打印「全部通过 ✓」。根因是统计方式：

| 阶段 | 做法 | 结果 |
|------|------|------|
| 最初 | 替换 `process.stdout` 抓 TAP，`setTimeout(150)` 后找汇总行 `# pass N`；找不到就退化成「数 `ok <n> -` 行」 | 汇总行常来不及写完 → 走退路 → **把 `describe` 套件也算成用例**，数字虚高且随机器负载漂移 |
| 第二阶段 | 改成**轮询等待**汇总行，15s 超时 | 全部文件都超时：汇总行的输出**绕过了被替换的 `process.stdout.write`**（等到 1s 静默、或等进程该退出，捕获文本里始终没有 `# pass`） |
| 第三阶段 | 用 `run({ reporter: 'spec' })` 的返回流 | Worker 里 `for await` 拿不到任何 chunk；`spec(stream)` 二次转换会挂住；裸 `run()` 发出的是**测试事件对象**而非文本 |
| 第四阶段 | 裸 `run()` 逐条消费事件 | `run()` 不带参会按 Node 默认 glob **把仓库里所有 `*.test.ts` 都 spawn 一遍** → 42 个 `test:fail`，错误全是 `spawn EPERM`（当时仓库里正好 42 个测试文件） |
| **现在** | **逐行分类 TAP 结果行**：`ok N - 名称` 后的诊断块里 `type: 'test'` 是用例、`type: 'suite'` 是 `describe` 套件 | 完全确定：**44 文件 / 1212 用例**，连跑 5 次一致 |

同时加了两道防线：
1. 出现**无法分类**的结果行（缺 `type:`）→ 整轮判失败，绝不静默放过；
2. `scripts/tap-parse.ts` 是纯函数并带 8 个单测（`tests/main/tap-parse.test.ts`），
   钉住「套件不算用例」「未分类必须暴露」「`套件+用例+失败+跳过 == 全部结果行`」这些不变式。

**为什么值得单独记一笔**：少算的用例不会让任何断言失败，只会安静地给出一个漂亮数字。
如果没注意，后续只会看到「测试全绿」而不知道有 200 个用例从没被计入。

### 5.4 错误信息把根因吃掉的三层原因（真实事故，首次真机启动时暴露）

第一次在真机上跑起来时，`open-database` 失败，日志里只有：

```
{"level":"error","event":"app.boot.stepFailed","step":"open-database","error":"AppError: 发生了未预期的错误"}
```

「数据库打不开」这个最关键的事实，以及**为什么打不开**，全都不见了。
三层原因叠在一起，修任何一层都不够：

**第 1 层：用了未登记的消息键。**
`src/main/db.ts` 里写了 `AppError('DB_OPEN_FAILED')` 与 `AppError('DB_NOT_OPEN')`，
但这两个键**从来没加进 `messages.ts`**。而 `getMessage()` 对未登记的键是
**静默回退**到 `INTERNAL`（这是刻意的设计：错误处理路径本身不能抛错）。

后果有两重：
- 用户看到的标题变成 `INTERNAL` 的「发生了未预期的错误」；
- 回退信息（`dev: '未登记的语义键 "DB_OPEN_FAILED"…'`）**只进 `dev` 字段**，
  而启动日志走的是 `event` + 结构化字段，根本不会打印 `dev`。

于是「键名拼错」这件事本身也被完美隐藏了。
**修法**：把两条补进 `messages.ts`，并且**追加在 7 段末尾**（编号纪律），
`DB_OPEN_FAILED = E70009`、`DB_NOT_OPEN = E70010`，已发布编号一位不动。

> 这里差点犯第二个错：第一次我是插在 `DB_CORRUPT` 后面的「语义位置」，
> 结果 `AUDIO_FILE_MISSING` 从 `E70008` 漂到 `E70009`，
> 被 `errors.test.ts` 的**编号快照测试**当场拦下。
> 那条测试的价值就在这里 —— 编号漂移对用户是「历史报错对不上文档」，平时完全看不出来。

**第 2 层：`AppError.message` 是给用户看的标题，不是诊断信息。**
真正能定位的是 `cause` / `causeChain`（例如
`NODE_MODULE_VERSION 115 ... requires 125` 这种原生模块 ABI 不匹配）。
而 `bootstrap/index.ts` 的启动报告只存 `name: message`：

```ts
error: e instanceof Error ? `${e.name}: ${e.message}` : String(e)
```

**修法**：在**知道原始错误的地方**（`openDatabase` 的每个 throw 点）先记一次
`log.errorFields(e, ...)` 再抛。做法是 `logAndRethrow()` —— 返回 AppError 让调用方
必须写成 `throw logAndRethrow(err, log)`，语法上强制「必须抛」，避免有人顺手吞掉。
日志里现在会带上 `code` / `numericCode` / `cause` / `causeChain` / `stack` / `details`。

**第 3 层：只记字符串，丢掉了结构化字段。**
`main/index.ts` 的 `onStepFinish` 原本记的是 `error: r.error`（一个字符串）。
改为 `errorFields(new AppError('INTERNAL', { details: { step, stepError } }), ...)`，
让日志带上完整的错误对象；`app.boot.aborted` 也补上了 `logDir` 与 `dbPath` ——
这两个是这类启动故障最先要看的东西，之前要用户自己去找。

**一句话教训**：错误处理链路上，**每一层「顺手简化一下」都会吃掉一层根因**。
未登记的键会被静默回退、`message` 不是诊断信息、字符串化会丢字段 ——
三个都是「看起来更整洁」的写法，合起来让一个 ABI 不匹配变成了「发生了未预期的错误」。

### 5.6 静默故障两例：SQL 没进产物、协议权限时机错（已修）

这两条的共同特征：**应用能起来一部分，功能静默缺失，报错指不到地方**。
都是首次真机启动时暴露的。

#### (1) 迁移 SQL 没进构建产物 → 库开了但一张表都没有

```
db.opened                    applied: 7, schemaVersion: 0
db.migrate.failed.readOnly   reason: DB_MIGRATION_FAILED
```

`applied: 7` 说明 7 条 PRAGMA 全部成功、**数据库确实打开了**；
但 `schemaVersion: 0` 说明**迁移一条都没跑**。查 `out/` 才发现：

```
out/main/index.js       269,680 B
out/preload/index.cjs     7,015 B
out/ 里的 .sql 文件数：0        ← out/main/infra/db/migrations/ 目录根本不存在
```

根因：迁移 SQL 是**运行时用 `readFileSync(join(dirname(import.meta.url), file))` 读**的
（打包器不认识 `.sql`，不会带进 bundle），而 `electron.vite.config.ts` 只配了入口、
没有把 SQL 复制进产物目录。

值得一提的是：`src/main/infra/db/migrations/index.ts` 的注释里**早就写明了这个前置条件**
（「打包时需把 … 复制到 out 目录」），但被当成「打包配置的事，不在本次范围」而没实现 ——
而 `npm run dev` 走的也是这条路，**所以它在开发期就会炸，不是打包才炸**。

**修法**：在 `electron.vite.config.ts` 的 `main` 段挂一个 `writeBundle` 插件复制 SQL。
三个设计取舍都写在配置文件注释里：

| 选择 | 理由 |
|------|------|
| **vite 插件**，不是 postbuild 脚本 | `dev` 与 `build` 都会走 vite 插件；postbuild 只覆盖 `build`，`npm run dev` 依然会踩同一个坑 |
| **内联在配置文件里**，不抽成 `vite-plugins/*.ts` | electron-vite 启动时先用 esbuild 把配置打成临时 bundle；跨文件 import 多一个解析环节，而本环境禁止 spawn（跑不了 esbuild）**无法预先验证它**。不引入无法验证的风险 |
| `writeBundle`，不是 `buildEnd` | 要等文件真的落盘之后再写进同一棵目录树 |

**验证方式**（纯 `node:fs`，不需要 esbuild）：复刻复制逻辑跑一次，再模拟
`out/main/index.js` 的 `migrationsDir` 去读并比对 hash：

```
✓ 001_init.sql  30559 字符   hash 与清单一致
✓ 002_seed.sql  23024 字符   hash 与清单一致
```

#### (2) `registerSchemesAsPrivileged` 在 ready 之后调用 → 立即抛错

```
[FAIL] register-media-protocol   0ms   AppError: 发生了未预期的错误
** 启动在中止于：register-media-protocol **
```

`0ms` 就失败，说明是**立即抛错**。把可能原因逐条排除：

- **权限字段名不合法？** 对照 `electron.d.ts` 的 `Privileges` 定义，
  `standard / secure / supportFetchAPI / stream / bypassCSP` 全是合法字段 → 排除
- **`protocol` 对象缺失？** 代码里有 `if (!electron?.protocol)` 守卫 → 排除
- **剩下唯一解释：调用时机。** `protocol.registerSchemesAsPrivileged` 是 Electron 的
  **ready 前** API，而我把「声明权限」和「注册 handler」一起放在了启动流程第 11 步 ——
  那一步在 `await app.whenReady()` 之后。

**修法**：权限声明移到 `src/main/index.ts` 的 `whenReady()` **之前**；
第 11 步只保留 ready 之后才允许的 handler 注册。

这里的关键认识是：**这两件事的时机约束不同，必须拆开**
（`registerSchemesAsPrivileged` 要在 ready 前，`protocol.handle` 要在 ready 后）。
失败处理上，权限声明用 try/catch 包住且**不致命** ——
没有媒体协议时「播放项目内音频」不可用，但书籍/画本/设置仍能用，不该把整个应用挡住。

#### 用测试锁住

两条都属于「不报错但功能静默缺失」，所以在
`tests/main/bootstrap-wiring.test.ts` 加了 4 条断言：

- 协议权限声明必须出现在 `whenReady` **之前**（按代码行判断，忽略注释里的提及）
- `bootstrap-steps.ts`（ready 之后执行）**不得**再调用 `registerMediaSchemePrivileges`
- `electron.vite.config.ts` 必须挂 `writeBundle`，且配置里有 migrations 目录
- 迁移 SQL 必须已按 LF 归一化（CRLF 会让 hash 校验失败，
  而那条报错看起来像「有人改了已发布的迁移」，根因却是换行符）

### 5.7 preload 只导出不调用 → `window.api` 恒为 undefined（已修）

第三个首次真机启动暴露的问题，也是**最难定位的一个**。

界面显示的是错误边界的安全视图：

```
页面显示出现异常
已切换到一个安全视图，你的数据没有受到影响。
原因链：TypeError: Cannot read properties of undefined (reading 'on')
```

`reading 'on'` 指向 `window.api.on(...)` —— 所以 `window.api` 是 `undefined`。
但**这个报错把排查方向指错了三层**：

1. 看起来像「渲染进程某个组件的 bug」，实际不是
2. **类型检查完全通过** —— `src/renderer/src/env.d.ts` 里声明了 `window.api` 的形状，
   `tsc` 认为它必然存在，所以编译期一点提示都没有
3. preload **加载是成功的**，产物也在、格式也对（CJS）
4. `npm run check:native` 也全绿（那是原生模块的事，与 preload 无关）

查产物才发现真相：

```js
// out/preload/index.cjs 末尾
exports.createPreloadApi = createPreloadApi;
exports.installPreload = installPreload;          // ← 只是「导出」
exports.preloadWhitelistSizes = preloadWhitelistSizes;
// （整个文件里没有任何 installPreload() 调用）
```

**`installPreload` 被导出、被打进产物，但没有任何地方调用它。**
preload 是「加载即生效」的脚本，不是库 —— 不调用就没有 `contextBridge.exposeInMainWorld`，
`window.api` 自然是 undefined。

排除过程（这次是**真靠排除**，不是猜）：

| 检查 | 结果 |
|------|------|
| preload 路径对不对？ | `resolvePreloadPath()` 产出 `out/preload/index.cjs`，与实际产物一致 ✓ |
| 产物格式对不对？ | 行首 `import`/`export` 数为 0、有 `require(` → 是 CJS ✓（sandbox preload 需要 CJS） |
| 产物里有没有 `exposeInMainWorld`？ | 出现 1 次（在 `installPreload` 函数体内）✓ |
| **那为什么没生效？** | **`installPreload` 只被导出，从未被调用** ✗ |

**修法**：在 `src/preload/index.ts` 末尾自执行 `installPreload()`，并用 try/catch 包住：

- Electron preload 环境里：正常执行，`contextBridge` 挂上 `window.api`
- Node 里被 import（`tests/main/preload.test.ts` 正是如此）：`require('electron')` 会失败。
  这时**不能让它裸抛** —— 那会让测试文件整片加载失败，而那些测试验证的恰恰是
  `createPreloadApi` 的白名单逻辑，不该因为「不在 Electron 里」而跑不了。
  所以捕获 + `console.error` **明确报出原因**（不是静默吞掉）。

**第二道防线**：在渲染侧唯一的 IPC 出口加 `requireWindowApi()`，把
`Cannot read properties of undefined (reading 'on')` 换成可操作的错误：

```
[ipc] window.api 不存在 —— preload 脚本没有生效，渲染进程无法访问主进程。
排查顺序：
  1. out/preload/index.cjs 是否存在（缺 → 构建没产出 preload）
  2. 它是否为 CJS（行首若有 import/export → sandbox preload 无法加载）
  3. src/preload/index.ts 末尾是否调用了 installPreload()
  4. 主进程窗口创建时的 preloadPath 是否指向上面那个文件
```

同一个守卫也加到了 `error-bus.ts` 的两处 `window.api.invoke`
（「打开文件夹」与「导出诊断包」按钮）。那两处是**错误提示里的按钮处理函数** ——
在最需要解释问题的地方再抛一个看不懂的 TypeError，是最糟的体验。

> `error-bus.ts` 里**故意重复实现**了这个守卫，而不是从 `ipc.ts` import：
> `ipc.ts` 会 import `error-bus.ts` 的 `reportError`，反向 import 会形成循环依赖，
> 而循环依赖在运行期的表现是「某个导出在特定加载顺序下是 undefined」——
> 那是比原 bug 更难查的一类问题。宁可重复 9 行。

**回归测试**（2 条）：`src/preload/index.ts` 必须存在**带括号的调用**
（`installPreload()`，而不是只有函数定义）；`error-bus.ts` 不得出现裸的 `window.api.invoke`。

#### 三个启动期故障的共性
5.6 与 5.7 三条合起来能看出一个模式：**「东西都在，但没接上」。**

| 问题 | 缺的是什么 |
|------|-----------|
| 迁移 SQL 没进产物 | 文件在源码里，但没被复制到运行位置 |
| 协议权限时机错 | 代码是对的，但调用时机不对（ready 前 vs ready 后） |
| preload 只导出不调用 | 函数写好了，但没有任何地方调用它 |

三个都不会让构建失败、不会让类型检查失败、也不会有明显的报错 ——
**只有真机跑起来才会暴露**，而且每个的第一层报错都指向错误的方向。
这也是「必须先跑起来再谈功能」的最直接论据。

### 5.9 依赖版本漂移：精确类型标注反而成了负担（已修）

修完 preload 之后 `npm run typecheck` **突然冒出 15 个渲染进程类型错误**。
它们**不是新代码引入的**，而是依赖装到了更高的次版本：

```
element-plus   声明 ^2.8.8     实际安装 2.14.5
```

Element Plus 2.14 把 `el-radio-group` 的 `change` / `update:model-value`
参数类型定为 **`string | number | boolean | undefined`**（比早期更宽）。
而**函数参数是逆变的**，于是精确联合类型的 handler 不再可赋值：

```ts
// 旧版本能过，2.14 起报 TS2322
function onModeChange(value: 'sidechain' | 'envelope'): void
// Type '(value: "sidechain" | "envelope") => void' is not assignable to
// type '(val: string | number | boolean | undefined) => any'
```

**讽刺的是**：这些精确类型标注正是之前修 `TS7006`（隐式 any）时特意加的 ——
在旧版本上完全正确，版本一升就全部失效。

**修法**：handler 参数**收宽 + 体内收窄**，收窄后依然类型安全：

```ts
function onModeChange(value: string | number | boolean | undefined): void {
  patch({ mode: String(value) === 'envelope' ? 'envelope' : 'sidechain' })
}
```

另有两处 `:model-value` 收 `null` 而组件只接受 `undefined`：
`CharacterMergeDialog` 的 `targetId`、`ExportWizardView` 的 `store.mixProjectId`。
改成显式绑定 + `?? undefined`（语义相同：都表示「没有选中」）。

同类还有 `SettingsView` 的三处键盘捕获：`$event` 在 vue-tsc 下推断为
`Event | KeyboardEvent`，声明成 `KeyboardEvent` 会报 TS2345 —— 同样收宽 + 体内收窄。

#### 值得记下两点

1. **`^` 范围在真实环境里会漂。** `^2.8.8` 装到了 `2.14.5`（跨 6 个次版本）。
   写「按 X 版本的类型对齐」时必须同时记录**实际安装版本**，否则下次装依赖就漂。
2. **对第三方事件签名做「精确匹配」是脆的。** 上游每次调整签名都会变成自己的编译错误。
   稳妥做法是**收宽 + 收窄**：接受上游给的宽类型，在自己的边界上收窄成业务类型。

### 5.0 测试隔离：为什么用 Worker 线程

三种方案都试过，结论写在这里免得后来者重走：

| 方案 | 结果 |
|------|------|
| **同进程** import 各测试文件 | ❌ 模块级状态互相污染，表现为「单独跑都过、一起跑有 8 项失败」 |
| **子进程**（`node --test` 的官方做法） | ❌ 本环境禁止 spawn：`spawnSync ... EPERM`；实测 `node --test` 41/41 全挂 |
| **Worker 线程** | ✅ 可用。每个 Worker 有独立模块注册表，等价文件级隔离，且在无沙箱限制的机器上同样有效 |

**顺带修掉的两个真实缺陷**（由测试抓出，都在基础设施层）：

1. **`TaskQueue.dispose()` 不等在跑任务落终态**：`cancel()` 对 running 任务只设 abort 信号就返回，`dispose` 直接 `await` 它就以为完成了 —— 调用方随后查状态会看到 `running`，而这些任务会以 `running` 留在库里（应用已退出，只能等下次启动才被标为 interrupted）。已改为等待 `RunningEntry.done`，带**可清除的超时**兜底。
   - 附带教训：第一版兜底用了裸 `setTimeout` 做 race，任务早已完成后事件循环仍等到超时才退出，**把一个 300ms 的测试拖成 30 秒**。现在超时计时器在 `finally` 里清除。
2. **`queue.test.ts` 的 `createHarness` 参数错位**：4 处调用把选项当第一个参数传（`createHarness({ retryDelaysMs: [...] })`），specs 收到对象 → `opts.specs is not iterable`。已在 harness 内归一化参数，两种调用方式都支持。

### 5.1 一个代价很大的教训：注释里的 `/*` 会毁掉解析

**现象**：`src/main/bootstrap/cleanup.ts` 无法被 import，报
`Expected '{', got 'interface'` —— 报错位置指向的 `interface` 完全合法。
最终定位到该文件第 31 行的 JSDoc：

```ts
/** 要清理的临时目录根（如 `<userData>/cache/tmp`、`<projects>/*/.tmp`、任务临时根） */
//                                          ^^^^^^^^^^^^^^^^
```

`/*` 让类型剥离解析器**重新进入嵌套块注释**，注释永不闭合，后续内容全被吞掉。
排查期间我反复怀疑 "interface 有问题"、怀疑文件被并发写入、怀疑有隐藏字符，
浪费了大量时间 —— 因为报错位置与根因无关。

**更糟的是我的修复过程**：为了消除这个隐患，我用脚本把注释里所有 `/*` 批量改写成
`* /`。该脚本**没有正确区分注释边界与 glob 写法**，把 `src/shared/*.ts` 改成了
`src/shared* /.ts`（可读性破坏），并在若干文件里**提前闭合了注释块**，
使注释文本变成代码（`app-lifecycle.ts` 因此报 `ReferenceError: recordings is not defined`），
一度让测试通过数从 1100+ 掉到 46。

**修复**：逐处按原文精确还原（不改语义、不改路径示例），并新增 `check:syntax` 的
隐患检测 —— **但判据收紧为「起始符之后本行没有结束符」**，因为
`src/shared/*.ts` 这类 glob 其实无害（注释会在本行正常闭合），
一律报警只会让检查失去可信度。

**给后来者的规矩**：写注释时不要直接写出「斜杠紧跟星号」的两字符注释起始符。
需要表达 glob 时用 `**` 或「星号与斜杠之间留空格」。

### 5.2.1 真机事故：`no such table: books`（迁移 SQL 没进产物）

**现象**（用户真机第一次成功启动后点「导入」）：

```
发生了未预期的错误
错误编号：「-」
原因链：[SQLITE_ERROR] SqliteError: no such table: books
```

两个问题叠在一起：**① 表根本没建；② 真实原因没被包装，UI 只显示兜底码「-」。**

#### 根因链（每一段都有实证，不是推测）

> ⚠️ **这一节我改过两次，第一次的结论是错的**，两次错误都保留在下面 ——
> 因为它们恰好演示了「配置看着对、运行时读不到」这类问题的典型误判路径。

| # | 事实 | 证据 |
|---|------|------|
| 1 | 迁移**整体失败** | 日志 `db.migrate.failed.readOnly reason:DB_MIGRATION_FAILED`；修完包装后变成 `app.boot.stepFailed` + `app.boot.aborted` |
| 2 | 库里**只有** `settings` 一张表，`books`/`projects`/`chapters`/`meta` 全都不存在 | 在真 Electron 里查 `sqlite_master`（见下「怎么查的」） |
| 3 | `settings` 是 `createSettingsStore` 自己建的，**恰好掩盖了故障** | `src/main/settings.ts:204` 有 `CREATE TABLE IF NOT EXISTS settings` |
| 4 | 迁移失败的直接原因是**读不到 SQL 文件**（ENOENT） | `readMigrationSql` 用 `join(dirname(import.meta.url), file)` 读取 |
| 5 | 运行时**实际查找的路径**是 `out/main/001_init.sql` | 修完包装后真机日志 `causeChain: ["[ENOENT] Error: ENOENT: no such file or directory, open '…\\out\\main\\001_init.sql'"]` |
| 6 | **`dirname(import.meta.url)` 在产物里就是 outDir 本身** | 产物 `out/main/index.js:3796` 保留 `const migrationsDir = dirname(fileURLToPath(import.meta.url))`，而 `index.js` 位于 `out/main/` 顶层 ⇒ `migrationsDir = out/main/` |
| 7 | 而 SQL 被复制到了**子目录** ⇒ 与查找位置差一层 | 磁盘实证 |

**为什么 `migrationsDir` 会等于 outDir** —— 关键在于**别把源码树的形状当成 bundle 后的形状**：

- 源码里 `infra/db/migrations/index.ts` 与 `.sql` **同目录**
- 但 electron-vite 把整个主进程**内联成单个 bundle** `out/main/index.js`，
  `infra/db/migrations/` 这一层在产物里**根本不存在**
- `dirname(import.meta.url)` 被内联后指向 `out/main/index.js` ⇒ **就是 outDir**

#### 两次修错的过程（都保留了，因为极具代表性）

| 尝试 | `to` 的写法 | 实际落点 | 为什么错 |
|------|------------|---------|---------|
| ① | `'main/infra/db/migrations'` | `out/main/**main**/infra/db/migrations/` | `outDir` 已是 `out/main`，多套了一层 |
| ② | `'infra/db/migrations'` | `out/main/infra/db/migrations/` | 路径**看着像源码树**（与 `src/main/infra/db/migrations` 形状一致），所以显得"对" —— 但产物里没有这一层 |
| ③ ✅ | `'.'` | `out/main/` | SQL 与 `index.js` **同级**，与 `dirname(import.meta.url)` 一致 |

② 是最危险的一种错误：**它满足「路径看起来合理」这个直觉**，
而且在 `npm run build` 的产物里确实存在（文件真的复制过去了），
只有到运行时 `readFileSync` 那一刻才暴露。所以我把它写进了纪律：
**改 `to` 之前，先读产物里 `migrationsDir` 的实际取值。**

#### 为什么这么难查（三层掩盖，每层单独看都像正常）

1. **表缺失被 `settings` 表掩盖** —— 库里有表、能连、能读设置，不像「完全没初始化」。
2. **只读模式被当成"优雅降级"** —— 迁移失败本意是「让用户至少能导出数据」，
   但这里降级后**一张业务表都没有**，应用完全不可用，降级毫无意义，只是把错误藏起来。
3. **诊断信息在包装层被逐层丢掉** ——
   - `readMigrationSql` 抛的 `details.reason = 'sql-not-found'`（含路径）
   - 被 `db.ts:215` 的 `new AppError('DB_MIGRATION_FAILED', { details: { from, to, backedUp } })` **整个覆盖**
   - `bootstrap-steps` 又只记 `reason`（= `'DB_MIGRATION_FAILED'` 这个抽象码）
   - ⇒ 日志里看不到 ENOENT、看不到路径、看不到 `reason: 'sql-not-found'`

#### 修法（6 处，每处都配了「故意打破」验证）

| # | 文件 | 改动 |
|---|------|------|
| 1 | `electron.vite.config.ts` | `to` 最终定为 `'.'`（解析后 = outDir 本身，与产物里 `dirname(import.meta.url)` 一致）；源目录不存在 → **抛错**而不是静默 `continue`；一个 `.sql` 都没复制 → **抛错**。注释里完整记下三次踩坑 |
| 2 | `src/main/db.ts` | 迁移失败时**保留内层 `details`**（`...inner` 而非覆盖）；`sql-not-found` 直接向上抛，不再套壳 |
| 3 | `src/main/bootstrap-steps.ts` | 记日志时带上完整 `details` + `causeChain` + `stack`；`details.reason === 'sql-not-found'` → **致命错误**（基础设施残缺不该降级成只读模式）。**正是这一条让第二次真机日志直接给出了 ENOENT 的绝对路径** |
| 4 | `src/shared/errors.ts` | 新增 `detectSqliteSchemaError()`：`SQLITE_ERROR` + `no such table/view/index/column/trigger: X` → `DB_SCHEMA_INCOMPLETE`（带表名 params）。在通用 errno 映射**之前**判定 |
| 5 | `src/shared/messages.ts` | 新增 `DB_SCHEMA_INCOMPLETE`（**E70011**，追加在 7 段末尾，不漂移已有编号） |
| 6 | `scripts/check-runtime-assets.ts`（新，`npm run check:assets`） | 直接 import `electron.vite.config.ts` 取出插件，对着临时 outDir **真跑一次 `writeBundle`**，核对每个 .sql 的落点与内容，并断言「没有多余层级」。已接入 `verify` |

#### 为什么 `no such table` 会显示成「-」

`SQLITE_ERROR` 是 SQLite 的**通用**错误码，而 `SYSTEM_ERRNO_MAP` 里能映射的是
`SQLITE_BUSY` / `SQLITE_CORRUPT` / `SQLITE_READONLY` / `SQLITE_CANTOPEN` 这类**专属**码。
于是 `SQLITE_ERROR` 落进 `wrapUnknown` 的兜底分支 → `INTERNAL` → UI 只显示编号「-」，
配一句「某处缺少精确抛错，应补齐」——**这句话是对的**，它就是提示我应该补这条映射。

#### 「怎么查的」：在真 Electron 里查真库

`better-sqlite3` 是 Electron ABI 125 的原生模块，**在 Node 22（ABI 127）里根本加载不了**
（`NODE_MODULE_VERSION 125 ... requires 127`）。所以离线读库这条路走不通。

唯一可行的做法是**用 Electron 自己跑一个探针**：

```
node_modules\electron\dist\electron.exe --no-sandbox scripts\_probe-db.cjs
```

探针里 `require('better-sqlite3')` 能成功（Electron 的 Node 就是 ABI 125），
然后查 `sqlite_master`。**这一步是整条排查的转折点** —— 在那之前我只能靠
「在 db 文件字节里搜表名」猜测，而那个方法**不可靠**（schema 可能以别的形式落在页里，
WAL 里还有增量），我因此一度得出了错误结论。探针用完即删。

> 教训：**原生模块相关的排查，不要在错误的 ABI 里绕路**。
> 要么用 Electron 跑探针，要么明确记下「无法验证」。

#### 这次新增的回归防线（4 条，全部做过「故意打破」验证）

| 防线 | 防什么 |
|------|--------|
| `复制目标必须正好等于 outDir`（`tests/main/bootstrap-wiring.test.ts`） | 解析 `RUNTIME_ASSET_DIRS` 的 `to`，算出绝对路径，与 outDir **逐字符比对**；并显式断言**两种历史错误写法**（`main/infra/db/migrations`、`infra/db/migrations`）都不等于正确值。还会读产物 chunk 实证 `migrationsDir = dirname(fileURLToPath(import.meta.url))` |
| `真的复制一遍，并用 readMigrationSql 的公式能读回（端到端）` | 真的复制到临时 outDir，再用**与产物相同的读回公式**把 SQL 读出来，校验 hash 与清单一致；同时反证两种错误路径读不到、正路径读得到 |
| `SQLite 表不存在必须被精确识别`（7 个用例） | `no such table/view/index/column/trigger` 全部映射到 `DB_SCHEMA_INCOMPLETE`；`SQLITE_ERROR` 但**不是**缺表时仍老实落兜底（不乱认）；专属码 `SQLITE_CORRUPT` 优先级不变 |
| `npm run check:assets`（`scripts/check-runtime-assets.ts`） | **真的执行插件的 `writeBundle`**（不是读配置文本），核对落点与内容逐字节一致、且无多余层级。它绕开 esbuild 的限制，把 `check:config` 那个「无法自验的盲区」补上了一大块 |

「故意打破」验证结果（两个历史错误写法都试过）：

```
注入 ② 'infra/db/migrations'   → fail 2，报「复制目标必须正好是 outDir（out/main）… 必然 ENOENT」
注入 ① 'main/infra/db/migrations' → fail 2
还原 ③ '.'                      → fail 0
```

**原来那条测试为什么没拦住这个 bug** —— 值得单独记一笔：

```ts
// 原来的写法（一直是绿的，即使 bug 存在）

```

它想断言的是 `to` 的值，但这个子串**恰好被源路径 `src/main/infra/db/migrations` 满足了**。
于是「`to` 写错」这个 bug 在测试里永远通不过失败 ——
**「断言某个字符串出现过」不等于「断言了正确的行为」**。

### 5.2.2 真机事故（第二次，症状一样、根因完全不同）：`settings` 引导期建表「遮蔽」迁移建表

**现象**（用户报告，错误编号 E70011）：

```
数据表不完整
数据库里缺少「books」这张表，说明建表步骤没有完成。
▸ 请重启应用；若表依然缺失，说明安装不完整，请重新安装或导出诊断包反馈。
```

> ⚠️ **这条提示给出的两个办法（重启 / 重装）对这个 bug 永远无效。**
> 它不是环境问题、也不是安装残缺，而是**代码里两处 DDL 不同形**导致的必然失败。

#### 根因链（每一段都有实证）

| # | 事实 | 证据 |
|---|------|------|
| 1 | 库里只有 **1 张表** `settings`，列是 `key, value, updated_at` | Electron 探针只读打开真库查 `sqlite_master` |
| 2 | 启动**第 4 步** `open-database` → `createSettingsStore` 用 `CREATE TABLE IF NOT EXISTS settings (key, value, updated_at)` 先把表建成了**窄表** | `src/main/settings.ts`（修复前） |
| 3 | **第 5 步**迁移跑 `001_init.sql`，其中 `CREATE TABLE IF NOT EXISTS settings (… is_secret …)` 因为表已存在而**变成空操作**（`IF NOT EXISTS` 不会补列） | |
| 4 | 紧接着 `CREATE INDEX IF NOT EXISTS idx_settings_secret ON settings(is_secret)` 报 `no such column: is_secret` | 真机日志 `db.migrate.failed.readOnly` 的 `causeChain` |
| 5 | 单事务回滚 ⇒ **一张业务表都建不出来**（连 `meta` 都没有） | 探针：`tables = settings` |
| 6 | `meta` 不存在 ⇒ `currentSchemaVersion()` 恒为 0 ⇒ **每次启动都重新尝试、每次都撞同一行** | 每次启动日志都出现相同一行 |

因此：**重启无效**（每次都撞同一行）；**重装也无效**（重装不会删
`%APPDATA%\novel-studio\novel-studio.db`）。`books` 只是**最后一个症状**，根因在 `settings`。

顺带一提：`002_seed.sql` 里那 78 条默认设置是
`INSERT … INTO settings(key, value, is_secret, updated_at)` —— **它同样引用 `is_secret`**，
所以窄表会让 init 与 seed **双双**失败。

#### 与 §5.2.1 的关系：同一个症状，两个 bug

| | §5.2.1 | §5.2.2（本节） |
|---|---|---|
| 报错文案 | `no such table: books`，编号显示 `-` | 同一句话，但编号已正确显示 **E70011** |
| 根因 | 迁移 SQL **根本没被复制进产物**（读文件 ENOENT） | SQL 读到了，但**执行**时报 `no such column: is_secret` |
| 触发条件 | 打包配置写错（`to` 多一层 `main/`） | 引导期兜底 DDL 比迁移的 DDL **窄一列**，与打包配置无关 |
| 何时才暴露 | —— | **修完 §5.2.1 之后才露出来**（原来是 ENOENT 先失败，压根没走到执行 SQL 这一步） |

> **教训**：修掉第一层故障后，不要因为「症状一样」就认定是同一个 bug。
> 这次是靠把 `causeChain` 读完（`… SqliteError: no such column: is_secret`）
> 才区分开的 —— 只看到「缺少 books 表」会一路排到环境问题上去。

#### 修法

| # | 文件 | 改动 |
|---|------|------|
| 1 | `src/main/settings.ts` | 兜底 DDL 与 `001_init.sql` 的 `settings` **对齐**（补上 `is_secret`）。注释里写明：这张表的所有权属于迁移，引导期兜底**绝不能比迁移窄** |
| 2 | `src/main/settings.ts` | 新增 `ensureSettingsSchema()`：建表后读 `PRAGMA table_info`，缺列就 `ALTER TABLE … ADD COLUMN is_secret INTEGER NOT NULL DEFAULT 0`。SQLite 没有 `ADD COLUMN IF NOT EXISTS`，所以要逐列判断 |
| 3 | `tests/main/settings-bootstrap-schema.test.ts`（新） | 真 SQLite 引擎回归测试 6 例 |

第 2 条是修**已经坏掉的用户库**必需的：`CREATE TABLE IF NOT EXISTS` 无法把已存在的窄表改回来，
而用户的库里**已经**是窄表了 —— 只改 DDL 只能救新装，救不了存量。
修复发生在启动第 4 步，**正好早于**第 5 步的迁移，所以不需要动 `001_init.sql`，
也就**不需要改它的 hash**（迁移纪律：已发布的迁移不可修改）。

#### 为什么必须用真 SQLite 引擎来测（这条最值得记）

拿它测这个 bug 会得到一条**永远为绿的测试** —— 而本仓库已经吃过三次

```
还原修复                       → pass 6 / fail 0
```

### 5.2.3 真机事故（第三次）：一次设置保存把整棵设置树写成 null，应用再也起不来

**现象**（用户报告）：「设置里选择了书籍保存位置后服务器崩了，无法再启动」。

> 注意：这次崩的**不是数据库，是启动流程本身**。§5.2.2 的修复已经生效
> （日志实证 `db.migrated from:0 to:2 applied:2 schemaVersion:2`，应用正常跑了一段时间）。

#### 根因链（每一段都有实证）

| # | 事实 | 证据 |
|---|------|------|
| 1 | 用户只改了「路径」一个分组 | `ipc.settings.changed` 的 changedKeys 却列出 **17 个键**：6 个 `paths.*` 叶子 + 11 个**分组名** |
| 2 | IPC 校验层会把 shape 里**每一个**键都物化进结果，输入里没出现的分组就成了 `undefined` | `infra/validate/schema.ts` 的 `ObjectSchema._parse`（第 358-362 行） |
| 3 | `applyPatch` 把 `undefined` 当成"给整支赋值" | `setByPath(state.value, 'audio', undefined)` 返回 true |
| 4 | `persist` 把它序列化成 `null` | `JSON.stringify(v ?? null)` → 库里出现 **11 行** `audio = null` 之类 |
| 5 | 下次启动 `loadFromDb` 用这个 `null` 覆盖整棵树 | 「只覆盖默认树里已存在的叶子」这个承诺**对分组键不成立** |
| 6 | `ports.ts` 读 `state.settings?.current().import.maxFileSizeBytes` | `?.` 只护住了 `state.settings`，`.import` 为 null → `TypeError: Cannot read properties of null (reading 'maxFileSizeBytes')` |
| 7 | 启动在第 11 步 `register-ipc-handlers` 中止 | 日志 `app.boot.aborted`，`step: register-ipc-handlers` |

**为什么"重启/重装"救不了**：坏值（`import = null`）就在库里，每次启动都在同一行抛同一个 TypeError。

**为什么这是必然的**：第 2 步的物化行为对**每一次**设置保存都生效，所以任何一次单分组保存
都会把其余 11 个分组写成 `null`。真机上是 01:09:05 那一次写入留下的 17 行
（同一毫秒，可由 `updated_at` 完整重建）：

```
paths.projectRoot=null  paths.exportDir="…\book"  paths.ffmpegPath=null
paths.modelDir=null  paths.cacheDir=null  paths.backupDir=null
audio=null  recording=null  canvas=null  mixing=null  export=null  ai=null
embedding=null  asr=null  import=null  ui=null  advanced=null
```

#### 为什么**没有**改校验层

「把缺失字段物化成 `undefined`」是校验层**故意写的**，并有 4 处测试断言
（`tests/main/validate.test.ts:107 / 132 / 277 / 287`），而且它是全部 158 个通道共用的。
改它等于改所有通道的载荷形状 —— 风险远大于收益。
真正的缺陷是**消费端没有能力处理这种形状的补丁**，所以修消费端。

#### 修法（三条防线 + 启动兜底）

| # | 文件 | 改动 | 防的是哪一环 |
|---|------|------|-------------|
| 1 | `src/main/settings.ts` · `applyPatch` | 分组键**绝不**被 `undefined`/`null` 赋整支（用 `isPlainObject(getByPath(defaults, key))` 判定） | **写**：从源头不再产生 `xxx = null` |
| 2 | `src/main/settings.ts` · `loadFromDb` | 分组行形状不符（非对象）→ 忽略该行，保留默认树 | **读**：库里已有坏值也起得来（自愈） |
| 3 | `src/main/settings.ts` · `reset` | 把分组名展开成叶子键（`SECTIONS.resetKeys` 给的就是 `['paths']` 这类分组名） | 不再往表里写 `paths = {整个对象}` 这种分组行（表语义是「一行一个叶子」） |
| 4 | `src/main/ports.ts` | `import?.maxFileSizeBytes` 取值级兜底 | **启动**：即使前两道都失效，启动路径也不抛 |

#### 故意打破验证

```
撤回 3 处 settings.ts 修改  → pass 1 / fail 5   （唯一通过的是"前提"用例，它只描述校验器行为）
还原                        → pass 6 / fail 0
```

#### 真库处置（这次动了用户的库，说明理由）

坏值是 11 条**非法分组行**，本身不含任何用户数据（值就是 `null`）。处置动作：
先备份原库 → 核对「待删行恰好是那 11 条预期键」（一旦出现预期外的键就**拒绝继续**）
→ 事务内删除 → 校验。结果 `90 → 79` 行，用户选的
`paths.exportDir = …\musicproject\book` **原样保留**。

**更重要的验证**：拿修复前的坏库副本，**不修库、只靠代码修复**跑启动期那一行读取：

| 场景 | 启动期读取 importLimits | 分组损坏 | 用户 exportDir |
|------|------------------------|---------|---------------|
| 修复前的坏库（只靠代码修复） | ✅ `209715200` | 无 | 保留 |
| 修复后的真库 | ✅ `209715200` | 无 | 保留 |

也就是说：**代码修复能独立兜住这个坏值**，手工修库只是顺手把非法行清掉。

#### 新增防线（`tests/main/settings-branch-null.test.ts`，6 例）

| 防线 | 防什么 |
|------|--------|
| `真实补丁（只改 paths）写库后，其余分组完好、库里没有分组行` | 端到端复刻事故。补丁**经真实校验器**产出（不手写模拟）—— 否则校验器一改，测试就假绿 |
| `显式传 { audio: null } 也不清整支` | 挡住任何调用方把分组设成 null |
| `复刻真机的 17 行：分组不被清空、用户路径保留` | 钉死「坏值不得让应用起不来」这条硬要求 |
| `坏行千奇百怪（数组/数字/字符串/非法 JSON）都不能弄坏分组` | 坏法不止 `null` 一种 |
| `reset 传分组名时只写叶子行` | 防止把分组行重新引入 |

> **教训：「补丁的形状」是跨层契约。**
> 校验层有意把缺失字段物化成 `undefined`，下游把 `undefined` 当"整支赋值" ——
> 两层各自看都合理，合起来就把整棵树写成了 `null`。
> 这类 bug 不会在单层测试里暴露：校验层的测试断言了物化行为（绿的），
> settings 的单测只喂"完整"的补丁（也是绿的）。**只有把两层串起来喂真实形状才会红。**

### 5.2.5 真机事故（第五次）：IPC 载荷里带着 Vue 响应式 Proxy，报兜底码「-」

**现象**（用户报告，紧接着 §5.2.4 的修复之后）：

```
发生了未预期的错误
错误编号：「-」
原因链：Error: An object could not be cloned.
```

> 这是 §5.2.4 的**直接后果**：死锁一解开，`book:commitImport` **第一次真正被调用**，
> 于是这条路径上一个潜伏已久、从未被触发的缺陷立刻暴露。

#### 根因：Proxy 不能被结构化克隆

Electron 的 `ipcRenderer.invoke` 用**结构化克隆**序列化参数，而 Vue 的 `reactive` / `ref`
拿到的是 **Proxy** —— Proxy 不能被序列化。用 Node 的 `structuredClone`
（与 Electron IPC 同一套 V8 序列化）实测：

| 值 | 结果 |
|----|------|
| `reactive({...})` | ❌ `DataCloneError: #<Object> could not be cloned.` |
| `ref([...]).value` | ❌ `[object Array] could not be cloned.` |
| `ref([...]).value.filter(...)`（**元素本身也是 Proxy**） | ❌ `#<Object> could not be cloned.` |
| `toRaw(x)` / JSON 往返 | ✅ |

`buildCommitPayload()` 里的 `drafts: drafts.value.filter(d => d.included)`
**正好就是那一行**：数组与元素全是 Proxy。

#### 为什么导出路径没事、导入路径出事

导出路径**早就**踩过这个坑并留了处理（原 `export.store.ts` 的 `cloneForIpc`，
注释写得很清楚：*Vue 的 reactive/Proxy 在跨 IPC 结构化克隆时可能抛 DataCloneError*）。
导入路径没有 —— 而且因为它一直被项目上下文的死锁挡在前面（§5.2.4），
**从没真正调用过 IPC**，所以缺陷一直没暴露。

#### 修法

| # | 文件 | 改动 |
|---|------|------|
| 1 | `src/renderer/src/shared/lib/clone.ts`（新） | 把 `cloneForIpc` 抽成**纯模块**（不 import 任何东西，含 vue），并写清失败机制与实测表 |
| 2 | `export.store.ts` / `useExportFlow.ts` | 改为从新模块取；单一实现，不再只有一个功能域受保护 |
| 3 | `import.store.ts` · `buildCommitPayload` | 返回值经 `cloneForIpc`（病灶） |
| 4 | `import.store.ts` · `buildTaskOptions` | 同样处理（任务路径的 `ruleSet` 里也有 Proxy） |

#### ⚠️ 为什么不把它挪进 `call()` 里统一做

看起来「在 IPC 边界统一拍平」更彻底，但**会静默毁掉音频**：
本仓库的录音路径用 MessagePort **转移 ArrayBuffer** 做零拷贝
（`useRecorder.ts`「硬性约束 2」），而 JSON 往返会把 `Uint8Array` / `Float32Array`
变成 `{"0":…，"1":…}` 这种对象 —— **静默的数据损坏比抛错糟糕得多**。
结论：只在「知道载荷是纯业务数据」的地方做，`clone.ts` 头部已写明这条纪律。

#### 验证

**纯机制**（`tests/renderer/clone-for-ipc.test.ts`，8 例）：用 `structuredClone` 直接断言
「响应式对象/数组/filter 结果必然抛 DataCloneError，拍平后可克隆」，并把
`buildCommitPayload` 的**真实载荷形状**作为一个用例钉住。

**真实 store 端到端**（临时脚本，用模块加载器解析 `@/` 别名后加载真 store，验证后已删）：

| 对象 | 结果 |
|------|------|
| `buildCommitPayload()` 的返回值 | ✅ 可克隆（`projectId = default`） |
| `buildTaskOptions()` 的返回值 | ✅ 可克隆 |
| **反证**：直接拿 `store.drafts` 的元素数组 | ❌ `DataCloneError: #<Object> could not be cloned.` |

> `ruleSet` 那一层还实测纠了一个**我自己写错的注释**：`effectiveRuleSet` 外层是
> **普通对象**（`{ ...set, patterns: … }` 是新字面量），但内嵌的 `patterns` 元素是 Proxy
> （整支 ❌ / 仅 `patterns` ❌ / 拍平后 ✅）。结构化克隆会走遍整个对象图 ——
> **光看外层「是不是 Proxy」会得出错误结论**。

### 5.2.6 真机事故（第六次）：预览不回传 `contentHash`，导入永远提交不了

**现象**（用户报告，紧接着 §5.2.5 的修复之后）：

```
发生了未预期的错误 / 错误编号：「-」     ← §5.2.5 的 DataCloneError（已修）
→ 修完序列化后立刻暴露下一条：
SchemaError: 缺少字段 / source.contentHash 不能为空字符串（第 1 处）
context: { channel: "book:commitImport", projectId: "default" }
```

> 又是「**修掉上一环才露出下一环**」：`projectId` 有了（§5.2.4）、载荷能序列化了（§5.2.5），
> 才轮到 `contentHash` 说话。这也解释了为什么 `books` 表一直是 0 行 —— 这条链**从未走通过**。

#### 根因：契约两端对不上，而且被断言静默掉了

| # | 事实 | 位置 |
|---|------|------|
| 1 | `book:previewSplit` 的 `res` **只声明 3 个字段**（drafts / cleanReport / encoding），**没有 `contentHash`** | `shared/ipc.ts` |
| 2 | 主进程实现同样只回传这 3 个（虽然 `ImportPreview` 里早就算好了 `contentHash = sha256(cleanedText)`） | `book.service.ts::previewSplit` 第 574/593 行 |
| 3 | 渲染进程却按「主进程会回传超集」读它；拿不到就把 `contentHash` 留成 `''` | `import.store.ts::applyPreviewResult` |
| 4 | 而 `book:commitImport` 的 `source.contentHash` 是**非空必填**（`v.string()` 默认 `nonEmpty: true`） | `schemas.ts` / `validate/schema.ts` 第 200 行 |
| 5 | 提交载荷带着 `''` → **必然**被 schema 拒收 | 真机日志 |

**为什么 tsc 没拦住**：渲染进程那边写的是
`await call('book:previewSplit', …) as PreviewSplitResult`，而本地那个 `interface PreviewSplitResult`
把 `contentHash` 声明成**可选** —— **断言正好把契约不一致关掉了**（断言就是用来关类型检查的）。
契约里少一个字段、实现里少一个字段、消费端靠断言兜着，三处各自都"编译通过"。

#### 修法（3 处）

| # | 文件 | 改动 |
|---|------|------|
| 1 | `src/shared/ipc.ts` | `book:previewSplit` 的 `res` 补上 `contentHash: string`（必填），并写明「去重与提交都要它」 |
| 2 | `book.service.ts::previewSplit` | 回传 `contentHash: preview.contentHash`；返回类型显式声明，于是**tsc 强制**实现与契约一致 |
| 3 | `import.store.ts` | 本地 `PreviewSplitResult.contentHash` 由可选改为必填；更新两处已过时的注释 |

> 为什么方向是「预览回传」而不是「放宽 schema 允许空哈希」：docs/10 §9 的流程是
> **导入前**先用同一个哈希 `findByContentHash` 做去重三选一，所以哈希必须在提交之前就可用；
> 而且 `commitImport` 并**不**重算哈希（它不重新解析文本），空哈希还会让 `findByContentHash('')`
> 撞上所有空哈希的书记录。放宽 schema 是错的方向。

#### 新增防线（`tests/shared/ipc-contract.test.ts`）

断言「`book:previewSplit` 的 `res` 声明了 `contentHash`」以及「`book:commitImport` 的 `source`
仍要求它」—— 两端任一被改掉都会红。

#### ⚠️ 这道防线第一版是**假绿**的（值得单独记一笔）

第一版直接匹配源码文本：

```ts
const block = IPC_SRC.match(/'book:previewSplit':\s*\{[\s\S]*?\n  \}/)[0]
assert.match(block, /\bcontentHash\b/)      // ← 假绿
```

而我在同一处补了一条**说明 `contentHash` 必须回传的文档注释** —— 于是「故意打破」时
（把 `contentHash` 从 `res` 里删掉）断言**依然通过**：注释里那两个字把它喂饱了。
这正是 §5.2.1 记过的 **「断言某字符串出现过 ≠ 断言了正确的行为」**，
同一个坑在原地又踩了一次。

修法：先 `stripComments()` 剥掉块注释与行注释，再把断言打在 `res: { … }` / `source: { … }`
**声明体内部**。重做故意打破：

```
契约里删掉 contentHash  → fail 1（「book:previewSplit 的 res 声明了 contentHash」）
还原                     → pass 23 / fail 0
```

> 教训：**新增的防线必须被故意打破过一次才算验证过** —— 这次它当场救回了一条本来会
> 「永远为绿」的测试。

### 5.2.7 真机事故（第七次）：改一个设置项会**清空同组其它项**（§5.2.3 没修干净的那一层）

**现象**（用户报告）：

> 设置里选择了导出位置后，选择备份位置，导出位置会被清空。
> 其他路径是不是也有这种情况？

**答案：不止路径 —— 是「任何局部补丁」的普遍行为。** 改一个音频项会清空同组其它音频项，
改一个快捷键会清空录音分组，改 AI 服务商会清空超时/并发/隐私开关……只是路径那一栏最容易看出来
（每一栏都是独立的一次「选择」）。

#### 根因：与 §5.2.3 同一个机制，只是深了一层

IPC 校验层 `ObjectSchema._parse` 会把 shape 里**每个**字段都物化进结果。所以
`settings:set({patch:{paths:{backupDir:'Y'}}})` 到达 `applyPatch` 时其实是：

```jsonc
{ "paths": { "projectRoot": undefined, "exportDir": undefined, "ffmpegPath": undefined,
             "modelDir": undefined, "cacheDir": undefined, "backupDir": "Y" },
  "audio": undefined, "recording": undefined /* …其余分组同样 undefined */ }
```

| 层 | §5.2.3 的修复 | 结果 |
|----|--------------|------|
| **分组键**为 `undefined`/`null` | 已挡住（`isPlainObject(getByPath(defaults,key))`） | ✅ 启动不再被整支 null 打死 |
| **分组内的叶子**为 `undefined` | **没挡** | ❌ 展开时逐个写进树 → 同组其它项被赋值 `undefined` → `persist` 里 `JSON.stringify(v ?? null)` 写成 **`null`** |

**为什么当时漏了**：§5.2.3 的现场是「整支变成 null → 启动崩」，注意力全在**分组键**上；
叶子级是同一个 bug 的另一半，但症状温和（只是「设置被清空」），没有崩，所以没被看见。
两处的语义其实是同一句话：**补丁里没出现的键 = 不改它**。

#### 修法（1 处，两层一起挡）

`src/main/settings.ts::applyPatch`：

| 改动 | 说明 |
|------|------|
| 顶层 `if (value === undefined) continue` | 补丁没提供的分组/键，直接跳过 |
| 分组展开时 `if (leafValue === undefined) continue` | **本次的关键**：分组内没提供的叶子也不写 |
| 保留 `value === null && isPlainObject(...)` 跳过 | 整支不能是 null（§5.2.3） |
| **`null` 一律不跳过** | 对叶子而言 `null` 是有意义的「用默认值」，见下 |

> 修复的边界必须钉死：**`undefined` 跳过、`null` 生效**。少了后半句，用户就再也无法把某项
> 设回默认值 —— 测试里专门有一组用例守这条（`settings-partial-patch.test.ts` 最后一组）。

#### 真库损害盘点（修复**无法**回填）

| 检查 | 结果 |
|------|------|
| 非法分组行 | 无 ✅（§5.2.3 已清过） |
| 被本 bug 清空的路径 | **4 个**：`paths.projectRoot` / `cacheDir` / `modelDir` / `backupDir` → 都变成 `null` |
| 其它分组被清空的叶子 | **无** ✅（用户只动过路径，所以爆裂半径仅限路径） |
| `paths.exportDir` | 保留（用户最近一次选择） |

`null` 对路径而言等价于「用默认值」，所以**功能上不会坏**（会回落到默认目录），
但用户**曾经的自定义选择已经丢失、无法恢复**（行值被覆盖了，SQLite 不留行历史），
需要重新选一次。

#### 新增防线（`tests/main/settings-partial-patch.test.ts`，17 例）

用真 SQLite + **真实校验器**（`undefined` 是校验层引入的，手写补丁复刻不了这条链路）。

断言方式上做了一个改进：**不写死默认值**（默认值会随 constants/seed 变，写死等于把默认值抄一遍），
而是记录补丁**前**的整组快照，断言补丁**后只有被点名的那一项发生变化** ——
「多改了字段」和「少改了字段」都会红：

```
撤回 2 处修复 → pass 4 / fail 13
还原           → pass 17 / fail 0
```

#### 顺带查清的三件事（都不是本次要修的，如实记录）

| # | 发现 | 证据 |
|---|------|------|
| 1 | **schema 比它校验的类型更窄**：`OptString = v.optional(v.string())` **不接受 `null`**，而 `AppSettings` 类型里 `paths.*` / `audio.defaultInputDeviceId` / `export.coverPath` 都是 `string | null`，UI 也**会**产出 `null`（「跟随系统默认设备」选项、「清除封面」按钮、清空路径输入框＝空串也被 `nonEmpty` 拒） | `schemas.ts` 第 30 行；实测 `patch.paths.ffmpegPath 应为字符串，实际是 null` |
| 2 | **点分键经 IPC 会被剥掉**：`settings:set` 的 shape 是嵌套对象，`{'audio.sampleRate': 44100}` 属未声明键 → 按 strip 丢弃（`applyPatch` 注释里写的「支持两种写法」只在 store 层成立） | 实测 `changed=[]` |
| 3 | **seed 默认值与代码默认值不一致**：seed 写 `recording.maxSessionMinutes=240` / `ai.model='mock'` / `advanced.keepBackups=7`，而 `buildDefaultSettings` 是 120 / `''` / 10 | 实测（新库跑 seed 与不跑 seed 取值不同） |

#### 补上的四个设计缺口（都是「不接上就跑不通」的类型）

**1. `projects` 表的鸡生蛋问题 —— 项目必须自动创建。**
   契约里 `books.project_id` 是 `NOT NULL REFERENCES projects(id)`，
   而 `session.projectId` 又从 `book.projectId` 派生；同时契约里**没有**
   `project:create` 通道。即「要有书才有 projectId，但建书必须有 projectId」。
   而 `book:list` 的 `projectId` 是**可选**的 —— 说明「不给项目也能列书」本来就是预期用法。

   → 结论：项目是**基础设施**、不是用户可见概念。新增 `ProjectRepo.ensureDefault()`，
   启动时（`register-ipc-handlers` 步骤）与每次导入前各调一次，保证至少有一个默认项目
   （固定 id `default`，目录 `{projectRoot}/default`，符合 docs/03 §2 的约定）。

**2. `book:importFile/Text/Url` 返回 `taskId` —— 所以必须真的排队。**
   契约如此，因此这三个通道真的把任务 enqueue 到 `TaskQueue`，
   `task:progress` / 成功的语义都是真的。为此给队列加了 `registerSpec()` ——
   域服务需要「先有队列、再有服务、服务把 spec 注册回来」这个顺序，
   而构造函数一次性传 specs 表达不了（服务又要 queue 引用才能 enqueue）。

**3. `previewSplit` 可以复用 `runImport` 的预览模式。**
   `runImport` 本来就支持 `persist: false` 并在内部返回完整的 `ImportPreview`
   （含 drafts / cleanReport / strategy）。所以预览分章**不需要第二套解析逻辑** ——
   传 `persist: false` 再取出需要的字段即可。这避免了一份必然走样的重复实现。

**4. iconv-lite 必须显式注入。**
   `shared/text/encoding.ts` 的 BOM / 严格 UTF-8 / 打分逻辑是自实现的，
   但 **GBK / GB18030 / Big5 在 small-icu 构建下不可用**（`createDecoder` 返回 null，
   结果会带 `NO_DECODER_NOTE`）。iconv-lite 一直在依赖里，只是没接线 ——
   不接的话用户能看到「检测到 GBK」却看不到任何预览文本。
   接的时候踩了一个类型细节：`Decoder` 是**可调用对象**（`(buf) => string | null`），
   不是 `{ encoding, decode }` 这种普通对象，写成后者直接 TS2353。

#### 测试怎么做的（以及**做不到**什么）

本仓库的测试环境**不能加载 better-sqlite3**（它是按 Electron ABI 编译的，

所以「真开一个库跑 SQL」在测试里做不到。`tests/main/book-repos.test.ts`（17 个用例）改用：

| 手段 | 抓什么 |
|------|--------|

| 断言所有读操作 SQL 都带 `deleted_at IS NULL` | 软删除记录漏过滤（会显示已删的书） |

**两个容易踩且症状隐蔽的点，已用测试钉住**（`tests/main/bootstrap-wiring.test.ts`，36 个用例）：

1. **preload 入口必须在 `src/preload/index.ts`**：放在 `src/main/preload.ts` 时
   electron-vite 完全不会把它当入口（它的解析规则是 `src/<scope>/{index,<scope>}.{js,ts,mjs,cjs}`，
   从 `node_modules/electron-vite/dist` 里读出来的，不是猜的）→ 构建产物里没有 preload →
   **窗口能开但渲染进程没有 `window.api`**，而且主进程日志里没有明显报错。
2. **preload 产物必须是 `.cjs`**：`package.json` 是 `"type": "module"`，
   `.js` 会被按 ESM 解析，而 `sandbox: true` 的 preload 只有受限的 CJS `require`。
   `electron.vite.config.ts` 因此把 preload 产物定为 `[name].cjs`，
   入口里的 `resolvePreloadPath()` 与它保持一致，并有测试守着。
3. **主进程入口不用 `__dirname`**：主进程产物是 ESM，`__dirname` 能否用取决于
   electron-vite 是否注入 CommonJS shim（我们读了它的 dist，发现只在部分路径注入）。
   改用 `import.meta.url` 换算 —— 这条也有测试守着（只检查代码行，注释里提到不算）。

**`HandlerDeps` 各端口的实现程度（如实标注）**：

| 端口 | 实现 |
|------|------|
| `log` / `env` / `settings` / `db` / `events` / `sends` | 完整实现 |
| `tasks` | 用真实 `TaskQueue`，但存储是**内存实现**（SQLite 任务存储未实现）→ 重启后任务列表为空 |
| `capabilities` | ffmpeg 与模型来自启动期真实探测；`embedding.available` 恒为 false（无 ONNX 推理实现） |
| `diagnostics` | **明确未实现**，调用即抛 `NOT_IMPLEMENTED`（诊断包需要 zip 写入适配层） |
| `provider` | **明确未实现**，调用即抛 `NOT_IMPLEMENTED`（真实连通性测试需要按 provider 发最小请求） |

未实现的端口**不返回假数据** —— 返回空对象会让 UI 显示「导出成功 / 测试通过」
这种真假难辨的状态，与 `handlers/placeholders.ts` 的纪律一致。

## 7. 验收顺序（当前可直接执行）

```bash
# 1. 依赖（postinstall 钩子已移除，这一步应干净成功）
npm install

# 2. 补下载 Electron 二进制
#    仅当 node_modules 已经存在时必需（npm 不会重跑已装包的 postinstall）：
npm run ensure:electron

# 3. 获取 Electron ABI 的原生模块二进制
#    **不要**先试 npm run rebuild —— 它在 Windows 上会调 node-gyp **编译 C++ 源码**，
#    需要 Visual Studio Build Tools + Python，而这不是必须的：
#    better-sqlite3 为 Electron 发布了预编译包，取来即可（见 docs/02 §4）
npm run fetch:native-prebuild

# 4. 在 Electron 里真的 require 一次 —— ABI 的唯一权威验证
npm run check:native

# 5. 类型检查（当前应为 0 错误）
npm run typecheck

# 6. 全套自动防线（当前应为 exit 0）
npm run verify

# 7. 覆盖率与契约报告（会重新生成 docs/90）
npm run check:coverage

# 8. 开发模式
npm run dev
#    期望看到的日志（写到 <userData>/logs/YYYY-MM-DD.log）：
#      app.boot.start → 15 步逐步 ok → app.boot.report
#      ipc.registered  implemented 43 / placeholders 115 / registered 158
#      window.renderer.loaded
#      app.ready
#    窗口起来后：F12 打开 DevTools，在 Console 里执行 `window.api` 应返回一个对象
#    （若它是 undefined → preload 没加载上，检查 out/preload/index.cjs 是否存在）

# 9. 最后才是打包
npm run build
```

**第 3 步为什么不是 `npm run rebuild`**

`rebuild` 走的是 `electron-rebuild` → `node-gyp` **从源码编译**，需要
Visual Studio Build Tools（C++ 工作负载）+ Python，而且会失败在构建期而不是运行期。

`fetch:native-prebuild` 改成从镜像取**现成的 Electron 预编译包**：

```
https://registry.npmmirror.com/-/binary/better-sqlite3/v11.3.0/
  better-sqlite3-v11.3.0-electron-v125-win32-x64.tar.gz      (922 KB)
```

（`v125` 是 Electron 31.7.0 的 ABI 版本，由 `node-abi` 给出。）

再强调一次第 4 步的作用：**ABI 是否匹配没有离线判据**。
实测两个「看起来能行」的办法都是错的 ——
读 PE 头的 `MajorImageVersion`（那里根本没有 ABI 信息），
以及在 Node 里 `require()`（Node ABI 127 能成功加载 Electron ABI 125 的二进制，
因为 better-sqlite3 入口带降级逻辑）。只有**在真 Electron 进程里加载**才算数。

**关于 `--ignore-scripts`**：现在**不需要**它了。
之前需要它，是因为本仓库自己声明了 `postinstall: electron-rebuild …`，
而那一步在受限环境会失败。那个钩子已经移除（原因见 §4.2），
所以 `npm install` 会正常结束，`electron` 自己的 postinstall 也会正常下载二进制。

万一你机器上 `npm install` 仍然失败，**先看它失败在哪一步**，不要直接加 `--ignore-scripts` ——
那会连带跳过 electron 的二进制下载，把「安装失败」变成「安装成功但跑不起来」，更难查。

**下一步的开发优先级**（按收益从高到低）：

1. `src/main/features/audio/`（recorder / processor / mixer / exporter 四个编排层）
   —— 算法都已在 `src/shared/audio/**` 里写好且测过，这是打通「录音 → 处理 → 成品」的关键路径
2. 上述四域对应的 IPC handler（录音/对轨/音频处理/混音导出共 115 个通道里的大头）
3. `src/main/features/book/alignment/`（对轨编排：录制片段 ↔ 画本行的匹配与落库）
