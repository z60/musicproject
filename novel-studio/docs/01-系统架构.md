**四个关键边界**

| 边界 | 规则 |
|------|------|
| 渲染进程 ↛ 文件系统 | 渲染进程没有任何 Node 能力，音频样本只能通过 preload 白名单方法交给主进程 |
| 渲染进程 ↛ 数据库 | 画本/角色/片段的读写全部走 IPC，渲染进程只持有内存态与 UI 状态 |
| 实时音频留在渲染进程 | 采集、监听、电平表、波形绘制走 Web Audio（毫秒级）；**落盘与重活走主进程** |
| 重活不阻塞 UI | 导入解析、embedding 推理、ASR、ffmpeg 全部是主进程后台任务，UI 只订阅进度 |

---

## 2. 为什么这样切（三条硬约束）

1. **录音不能丢帧**：Web Audio 的实时回调禁止做任何同步 I/O 或重计算。采集回来的是 float32 块，通过 `MessagePort` 零拷贝传给主进程，由主进程做追加写入 + 定期 fsync。
2. **数据库必须串行**：`better-sqlite3` 是同步 API，多写者会互相阻塞。因此数据库只在主进程持有单例，写操作经 repository 层串行化，渲染进程永远不碰 SQL。
3. **用户文本是资产**：所有业务数据落 SQLite（可查询、可迁移、可备份），音频落文件系统（不走 BLOB，避免数据库膨胀）。二元的边界就是「结构化数据 vs 大二进制」。

## 3. 分层设计

### 3.1 主进程分层

```
src/main/
├── index.ts                  应用入口：单实例锁、窗口、生命周期、优雅退出
├── preload.ts                唯一的桥：白名单方法 + 事件订阅 + 类型约束
├── bootstrap/                启动编排（不写业务）
│   ├── app-lifecycle.ts      启动顺序：迁移 → 崩溃恢复 → 清理临时 → 开窗
│   ├── window-manager.ts     主窗口/子窗口、状态持久化、单例语义
│   └── menu.ts               菜单与全局快捷键
├── ipc/                      「传输层」：只做参数校验 + 路由到 service
│   ├── registry.ts           通道注册表（类型安全）
│   ├── handlers/             按域拆分的 handler
│   └── events.ts             主→渲染 事件推送（进度、电平、日志）
├── features/                 「业务层」：按限界上下文划分
│   ├── book/
│   │   ├── import/           TXT/PDF/DOCX/URL 解析、编码嗅探、分章、清洗
│   │   ├── canvas/           画本生成、说话人判定、标记推断、质检
│   │   ├── alignment/        片段映射、时间线排布、重叠消解
│   │   ├── package/          .nsp 项目包 / .nst 任务包 打包与合并
│   │   └── repositories/     本书域全部 SQL（唯一允许写 SQL 的地方）
│   ├── audio/
│   │   ├── recorder.ts       录音会话管理、WAV 增量写入、头部修复
│   │   ├── processor.ts      ffmpeg 处理链、预设、批量
│   │   ├── mixer.ts          多轨混音、ducking、响度（两遍法）
│   │   ├── exporter.ts       分章导出、M4B 合并、命名与元数据
│   │   └── repositories/
│   ├── ai/
│   │   ├── providers/        mock / local / openai-compatible / dify
│   │   ├── embedding/        ONNX 推理 + 角色原型向量维护
│   │   ├── attribution/      说话人判定算法（规则 + 向量 + LLM 复核）
│   │   ├── prompts/          Prompt 模板与版本
│   │   └── repositories/
│   └── settings/
├── infra/                    「基础设施层」：与业务无关
│   ├── db/                   连接、迁移、事务包装、备份
│   ├── queue/                任务队列、进度、取消、并发限制
│   ├── fs/                   路径解析、原子写、临时文件收口、哈希
│   ├── ffmpeg/               ffmpeg 探测、调用封装、滤镜图构建
│   ├── asr/                  whisper.cpp 封装
│   ├── media/                WAV 头读写、采样、重采样、波形峰值
│   ├── cache/                缓存（embedding、波形、转码）
│   ├── log/                  结构化日志、脱敏
│   └── secure/               safeStorage 封装
└── shared-types.ts           转发 src/shared（主进程侧入口）
```

**依赖方向铁律**：`ipc → features → infra`，禁止反向；`features` 之间只能通过**对方的 service 接口**调用，禁止直接跨域读别人的表。

### 3.2 渲染进程分层

```
src/renderer/src/
├── app/                      App.vue / main.ts / router.ts（应用装配）
├── features/                 功能模块（自包含：views + components + stores + composables）
│   ├── book/                 书架、导入向导、章节管理
│   ├── editor/               画本编辑（表格/剧本双视图）、角色表、标记面板
│   ├── recording/            录音台、连续录制、设备诊断、take 管理
│   ├── alignment/            时间线、片段映射、重叠处理
│   └── mixing/               混音台、处理链、导出向导
├── shared/
│   ├── ui/                   通用组件（虚拟表格、波形条、标签选择器、进度任务卡）
│   ├── lib/                  IPC 客户端封装、格式化、快捷键、波形工具、防抖
│   ├── types/                渲染侧类型（从 src/shared 再导出 + UI 专有类型）
│   └── audio/                Web Audio 封装：AudioWorklet、录音图、监听图、VU
└── assets/
```

**渲染进程约束**
- 只通过 `shared/lib/ipc.ts` 访问主进程，禁止任何组件直接 `window.api.xxx`。
- 大列表（画本行 > 2000）使用虚拟滚动；波形用 `OffscreenCanvas` 绘制。
- 全局状态用 Pinia，按功能域分 store；**跨域共享的状态放到 `app/store`**，禁止 feature 之间互相 import store。
- 长任务进度统一由 `useTaskProgress(taskId)` 订阅，禁止每个功能自己写轮询。

## 4. 核心数据流

### 4.1 主链（Happy Path）

```
[1] 导入
  用户选文件 ─▶ ipc: book.import.file
    主进程: 嗅探编码 → 解析 → 分章 → 清洗 → 事务写 books/chapters
    ◀─ 事件: task.progress  ──▶ UI 进度条
    ◀─ 返回: { bookId, chapterCount }

[2] 画本生成
  用户点「AI 生成画本」─▶ ipc: canvas.generate
    主进程:
      a. 分句 → 画本行初稿（规则初筛 speaker）
      b. 抽取/加载角色表 → 计算角色原型向量
      c. 每行 embedding → 与原型向量余弦 → 归属 + 置信度
      d. （可选）标记情绪/语速：规则词表 + Provider
      e. 事务写 canvas_lines + line_embeddings
    ◀─ 返回: 统计（各角色行数、低置信行数）

[3] 人工校对
  编辑器改一行 ─▶ ipc: canvas.updateLine（乐观 UI + 防抖落库）
  低置信队列 ─▶ 逐行确认 ─▶ 原型向量增量更新（异步，不阻塞编辑）

[4] 录音
  渲染: AudioWorklet 采集 float32 ─▶ MessagePort ─▶ 主进程 recorder
    主进程: 追加写 .tmp WAV + 每秒 fsync + 记录样本数
  用户停止 ─▶ ipc: record.stopSession
    主进程: 定稿头部 → 生成 recording_session 记录 → （逐行模式）生成 voice_segment
    渲染: 立即请求波形缩略（主进程从缓存/重算）

[5] 对轨
  用户点「自动对轨」─▶ ipc: alignment.autoArrange
    主进程: 取片段 → 按画本行顺序 + 留白 → 排布 → 重叠检测 → 写 arrangement_items
    （可选）ASR 校验片段文本
  用户拖动片段 ─▶ ipc: alignment.updateItem（非破坏，只存 offset）

[6] 处理
  用户套预设 ─▶ ipc: process.batchApply
    队列 → ffmpeg 滤镜链 → 派生 processed 文件 → 写 segment 的 processed_path

[7] 混音导出
  用户点导出 ─▶ ipc: export.render  （可 preview / chapter / book）
    队列:
      构建 ffmpeg 滤镜图（amix + sidechaincompress + loudnorm 两遍）
      → 输出章节文件
      → 全部章节完成 → concat + chapter metadata → M4B
    ◀─ 事件: export.progress（每章/每秒）＋ 导出报告
```

### 4.2 状态机（关键三处）

**A. 录音会话状态机**（主进程权威，渲染进程只镜像）

```
idle ──start──▶ preparing ──ready──▶ recording ⇄ paused
                   │                    │
                   └──fail──▶ error     └──stop──▶ finalizing ──▶ done
                                                        │
                                                  崩溃/断电
                                                        ▼
                                        recovered（启动时扫描 .tmp 修复头）
```
约束：`paused` 期间不写盘但不丢已采集缓冲；`finalizing` 必须完成「补头 + 生成片段 + 入库」三件事才算 `done`。

**B. 画本行状态机**

```
draft ──assign(speaker)──▶ assigned ──record──▶ recorded ──align──▶ aligned
  ▲                            │                  │
  └────────── reset ◀──────────┴──── rerecord ◀───┘
  （长态）needs_review：置信度低或质检标记，可与任意状态并存为独立标志位
```
说明：`state` 只表示流程进度，**质量问题用独立标志位**（`flags`），否则状态会爆炸。

**C. 任务状态机**（`infra/queue`）

```
queued ─▶ running ─▶ succeeded
   │         │  └──▶ failed（可重试）
   │         └─────▶ cancelled
   └─(并发满)─▶ waiting
```

### 4.3 数据所有权

| 数据 | 唯一权威位置 | 渲染进程如何拿到 |
|------|--------------|------------------|
| 书籍/章节/画本行/角色 | SQLite（主进程） | IPC 查询 |
| 录音音频文件 | `userData/projects/{id}/recordings/` | 只拿 `file://` 或自定义协议 URL 读取 |
| 片段与对轨位置 | SQLite | IPC 查询 + 局部更新 |
| 处理结果 | 文件系统 + SQLite 指针 | 同录音 |
| 录音中的实时样本 | 渲染进程 → 主进程 | 渲染进程只负责采集，不持久化 |
| UI 选择态/滚动位置 | 渲染进程（Pinia） | 本地 |
| 任务进度 | 主进程队列 | 事件订阅 |

**音频访问协议**：注册自定义协议 `ns-media://<projectId>/<relativePath>`，主进程 handler 做**路径规范化校验**（必须落在该项目目录内，拒绝 `..`），避免直接暴露任意文件读取。

## 5. 进程间通信设计

### 5.1 三种模式

| 模式 | 用途 | 例子 |
|------|------|------|
| **请求-响应**（`invoke`） | 所有查询与命令 | `book.list`、`canvas.updateLine` |
| **单向推送**（`send` → 主进程事件监听） | 高频、可丢弃的数据 | 录音电平 `record.meter`（每 50 ms 一帧） |
| **事件流**（主进程 `webContents.send`） | 任务进度、状态变更、日志 | `task.progress`、`export.progress` |

### 5.2 原则

1. **音频样本走 MessagePort，不走 `ipcRenderer.invoke`**：实时采集块用直连端口传递，避免主线程排队。
   ⚠️ 实测纠正（docs/91 §5.2.42 / §5.2.43）：这条路径上①主进程**必须**调 `MessagePortMain.start()`；
   ②发送侧**不能带 transfer 列表**（带了主进程收到的 `event.data` 恒为 `null`）。所以它**不是**零拷贝：
   每 50 ms 一次结构化克隆拷贝（约 9 KB）—— 换来的是数据真的到得了。
2. **通道命名**：`<域>.<动作>`，全小写、点分层级（`canvas.generate`、`export.render`）。
3. **全部参数运行时校验**：用 Zod（或手写 guard）在 handler 入口校验，防止渲染进程被 XSS 后乱调用。
4. **错误统一形状**：`{ code, message, details?, retryable }`，见 `20-IPC契约.md` 第 5 节。
5. **不传大对象**：画本行列表分页/按章节拉取；波形传**降采样后的峰值数组**（如每 100 ms 一对 min/max），不传原始样本。

## 6. 错误边界与降级策略

| 故障 | 探测方式 | 降级行为 | 用户可见 |
|------|----------|----------|----------|
| ffmpeg 缺失/损坏 | 启动探测 + 首次调用失败 | 禁用处理/导出功能 | 顶部横幅 + 「重新指定路径」 |
| 音频设备被占用 | `getUserMedia` 抛错 | 允许「只读模式」查看已有录音 | 弹窗给出占用原因与重试 |
| 麦克风权限被拒 | 权限状态 | 禁用录音 | 引导到系统设置 |
| 模型文件缺失/校验不符 | 启动校验 SHA-256 | 向量判定降级为规则+人工；ASR 不可用 | 设置页提示，提供「重新放置模型」说明 |
| Embedding 推理 OOM | 捕获异常 | 减小 batch、失败则降级规则 | 任务报告注明降级原因 |
| Provider 不可达 | 超时/网络错误 | 自动重试 2 次 → 降级本地规则 | 画本页提示「AI 增强不可用」 |
| 数据库损坏 | `integrity_check` 失败 | 只读模式 + 引导恢复备份 | 阻止写入，明确提示 |
| 磁盘写满 | 写入抛错 | **立即停止录音并保住已写数据** | 高优先弹窗（这是数据安全事件） |
| 单片段处理失败 | 逐条捕获 | 跳过该片段继续，其他不受影响 | 报告列表 |
| 渲染进程崩溃 | `render-process-gone` | 重建窗口、恢复上次路由与选中章节 | 提示「已恢复」 |
| 主进程崩溃 | Electron 退出 | 启动时扫 `.tmp` 修复 WAV、标记未完成任务为 `interrupted` | 启动报告 |

**核心原则**：**录音链路上任何错误，第一优先是保住已采集数据，其次才是提示用户。**

> **本节与 §13 的分工**：本节回答「**哪种故障降级到什么功能**」（产品决策）；
> §13 回答「**故障怎么变成一句用户看得懂、能行动的话**」（工程机制）。
> 两者互补，任何一条降级行为最终都必须能通过 §13 的通道说给用户听。

## 7. 与外部程序的集成

| 外部 | 调用方式 | 并发策略 | 超时 |
|------|----------|----------|------|
| ffmpeg | `child_process.spawn`，参数以数组传递（不经 shell） | 按 CPU 核数限制（默认 `min(4, cores-1)`） | 无固定超时，靠进度/stall 检测 |
| whisper.cpp | 独立进程/工作线程，模型常驻（按内存决定） | 串行（模型不可并发） | 按音频时长动态计算 |
| ONNX embedding | 主进程内 `onnxruntime-node`，可多线程 | 小批量并发，batch 自适应 | 单批 30 s |
| LLM Provider | HTTP（`fetch`/`undici`） | 默认并发 2，可配置 | 默认 60 s，流式则空闲超时 30 s |

**ffmpeg 进度解析**：统一加 `-progress pipe:1 -nostats`，解析 `out_time_us` / `total_size` / `speed`，换算为百分比；没有总时长的场景（流式）用「已完成片段数 / 总片段数」估算。

## 8. 关键架构决策记录（ADR）

| ID | 决策 | 备选 | 理由 | 代价 |
|----|------|------|------|------|
| ADR-01 | 音频落文件系统，不入库 BLOB | BLOB 存 SQLite | 数据库体积可控、可流式读、可外部工具修复 | 需自管路径与清理 |
| ADR-02 | `better-sqlite3`（同步） | `node-sqlite3`（异步） | 主进程单线程下同步 API 更快更简单，无回调地狱 | 需 electron-rebuild；禁长事务 |
| ADR-03 | 录音采集在渲染进程、落盘在主进程 | 全在主进程（native 采集） | 复用 Web Audio 的设备/监听/处理能力，跨平台一致 | 需设计零拷贝通道与丢帧保护 |
| ADR-04 | 画本行是唯一主轴 | 文本与音频各自为主 | 一处真源，避免对不上号 | 所有功能必须挂 line_id |
| ADR-05 | 说话人判定 = 规则初筛 + 向量判定 + 人工兜底 | 纯 LLM / 纯规则 | 离线、可复算、成本可控；LLM 仅做低置信复核 | 需维护角色原型向量 |
| ADR-06 | 非破坏性处理（派生文件 + 指针） | 就地覆盖 | 可回退、可对比、可换预设 | 占磁盘，需清理策略 |
| ADR-07 | AI 能力抽象为 Provider | 直接调 Dify | 用户暂无 Dify；需可换、可 Mock、可离线 | 多一层适配 |
| ADR-08 | 协作靠文件包（`.nst`），不做服务端 | 自建云服务 | 本地优先、零运维、可离线交换 | 冲突处理要自己做 |
| ADR-09 | 对轨位置独立存储（`offset_ms` + `src_in/out`） | 直接改音频文件 | 可反复调整、可多方案 | 渲染时需正确计算 |
| ADR-10 | 响度用两遍法（measure → apply） | 单遍 `loudnorm` 动态模式 | 单遍是动态的，逐章响度不齐；两遍线性增益才稳 | 渲染耗时 ×2 |

## 9. 对原始目录结构的补充建议

你给的架构是对的，我**完全沿用**，只建议补 4 处（都是「不加会出问题」的）：

### 9.1 画本读写必须在主进程（重要）

原结构中 `editor/` 只在渲染进程。但画本是核心资产，涉及事务、向量计算、批量重算。**建议补 `src/main/features/book/`**（原结构里 `main/features/book` 已存在，正好用它承载）：

```
main/features/book/
├── import/       解析与分章
├── canvas/       画本生成、说话人判定、标记推断、质检
├── alignment/    对轨算法
├── package/      .nsp / .nst 打包
└── repositories/ 画本域全部 SQL
```
渲染进程的 `features/editor/` 只负责**视图与交互**，这不是「多写一层」，而是避免把 SQL 和算法塞进 Vue 组件。

### 9.2 增加 `main/infra/`

原结构 `main/features/` 下塞不下通用能力。数据库、队列、日志、ffmpeg 封装属于基础设施，被多个 feature 复用，混进某个 feature 会导致循环依赖。**建议置于 `src/main/infra/`**（与 `features/` 平级）。

### 9.3 增加 `renderer/src/shared/audio/`

`shared/` 里已有 `ui/lib/types`。录音与监听需要一套跨功能复用的 Web Audio 封装（AudioWorklet 加载、图构建、VU 计算），建议补 `shared/audio/`，否则 `recording/` 与 `mixing/` 会各写一份且不一致。

### 9.4 增加 `main/features/audio/processor.ts`

原结构 audio 下只有 `recorder/mixer/exporter`。但「音频处理」（FR-5：降噪/EQ/压缩/预设/批量）既不属录音也不属混音，是独立域。**建议补 `processor.ts`**（以及 `presets.ts`）。

## 10. 启动顺序（必须严格）

```
1. app.requestSingleInstanceLock()        # 二次启动聚焦已有窗口
2. 解析 userData 与设置（含便携模式判断）
3. 初始化日志（含崩溃捕获）
4. 打开数据库 → 跑迁移 → integrity_check
5. 崩溃恢复：扫描 projects/*/recordings/*.tmp → 修复 WAV 头 → 生成 session 记录
6. 清理过期临时文件与孤儿缓存（带白名单保护）
7. 校验模型文件（异步、不阻塞）
8. 探测 ffmpeg（异步）
9. 注册自定义协议 ns-media://
10. 注册 IPC handlers（幂等）
11. 创建主窗口 → 加载渲染进程 → 就绪
12. 后台：自动备份、缓存清理、更新检查（可关）
```

**顺序理由**：3 必须在 4 之前（数据库出问题要留日志）；5 必须在 6 之前（不能把待修复的 `.tmp` 当垃圾删掉——这会直接导致用户录音丢失）。

## 11. 关闭与崩溃语义

| 场景 | 行为 |
|------|------|
| 正常关闭 | 若有进行中录音 → 阻止关闭并提示；若有导出任务 → 询问「后台完成后退出 / 立即取消并退出」 |
| 强制关闭（任务管理器） | 下次启动走崩溃恢复；未完成任务标记 `interrupted`，UI 提示「上次有 N 个任务被中断，是否重试」 |
| 渲染进程崩溃 | 主进程重建窗口并恢复路由；录音会话若在进行 → 提示素材已保存并可继续 |
| 数据库忙 | 所有写操作带 busy 超时（默认 5 s），超时后报可重试错误，不静默丢数据 |

## 12. 性能关键路径

| 路径 | 风险 | 对策 |
|------|------|------|
| 录音采集 → 落盘 | 丢帧、GC 抖动 | 固定大小环形缓冲 + 无分配写入路径；预分配 ArrayBuffer 池；`--max-semi-space-size` 调优 |
| 画本列表渲染（万行级） | DOM 爆炸 | 虚拟滚动 + 分页查询 + 行内容懒渲染（滚动中降级为纯文本） |
| 波形绘制 | 主线程阻塞 | 峰值预计算入缓存（`waveform_peaks` 表/文件），绘制用 OffscreenCanvas + Worker |
| embedding 批量 | 阻塞主进程 | 放 Worker 或分批 `setImmediate` 让出事件循环；进度可见 |
| ffmpeg 混音 | 磁盘 I/O 与 CPU 争抢 | 限制并发、`-threads` 受控、输出到同盘临时再移动（避免跨盘复制） |
| SQLite 大查询 | 阻塞主进程（同步 API） | 建索引、`EXPLAIN QUERY PLAN` 校验、分页、只 SELECT 需要的列 |

## 13. 错误兜底与消息体系（本次补充）

> **详细设计见 `22-错误码与消息体系.md`**；代码落在 `src/shared/messages.ts`、`src/shared/errors.ts`。
> 本节给出架构级接线点，确保这套机制不是「文档里说说」，而是每个模块都接上了。

### 13.1 要解决的三件事

| 问题 | 机制 |
|------|------|
| 出错时该说什么？ | **消息表集中管理**（`messages.ts`），任何模块不得硬编码用户可见文案 |
| 错误码怎么记、怎么报？ | **双轨编号**：语义键（`RECORD_DEVICE_LOST`）+ 派生数字编号（`E200005`），统一日志字段 |
| 没预料到的异常怎么办？ | **三级兜底**：业务显式抛 → 边界包裹 → 全局钩子/错误边界 |

### 13.2 三级兜底（每级都留痕）

```
第一级 · 业务显式抛出
  业务代码在最清楚上下文处抛出精确业务异常
  throw AppError.of('RECORD_DEVICE_LOST', { params: { device: 'USB Mic' } })

第二级 · 边界包裹（必须装，否则下面全部失效）
  · IPC handler 入口（src/main/ipc/registry.ts）→ 校验 + 执行 + 统一转 {ok,data,error}
  · 后台任务执行器（队列 runner）→ 异常转业务异常 + 任务标记 failed，不中断整批
  · 服务层入口（可选）→ 附加 projectId/chapterId 等上下文

第三级 · 全局钩子 + 错误边界
  主进程：uncaughtException / unhandledRejection → 日志 + 通知渲染 + （生产）优雅退出
  渲染进程：app.config.errorHandler / window.onerror / unhandledrejection /
           router.onError / <ErrorBoundary> → 统一兑现提示
```

### 13.3 关键接线点（这是「有没有真接上」的验收点）

| 位置 | 必须做的事 |
|------|------------|
| `src/main/ipc/registry.ts` | handler **永不 throw**，一律返回 `{ ok, data }` 或 `{ ok: false, error }`。抛出去会让 Electron 丢掉 `code/severity/retryable`，只剩一个字符串 |
| `src/main/infra/errors/install.ts` | 在**创建窗口之前**装配全局钩子；致命错误先执行「录音定稿」再通知再退出 |
| `src/main/ipc/events.ts` | 主进程主动推送的错误走 `app:error` 事件（否则用户永远不知道主进程出了问题） |
| `src/renderer/src/shared/lib/ipc.ts` | 统一解包 `{ok,error}` 并调用 `reportError`；**组件禁止直接 `window.api.invoke`** |
| `src/renderer/src/shared/lib/error-bus.ts` | 唯一出提示的口子：分级展示 + 去重合并 + 日志 |
| `src/renderer/src/app/error-handler.ts` | 挂载前调用；覆盖 Vue / window / promise / 路由四条路径 |
| `src/renderer/src/shared/ui/ErrorBoundary.vue` | 包住 `<router-view>`，让页面级异常只退化该区域而不是白屏 |

### 13.4 三条不可违背的规则

1. **取消不是错误**：`AbortError` → 语义键 `TASK_CANCELLED` → UI 不弹提示、日志写 `info`。用户主动取消却弹一个红框，是很常见但很糟的体验。
2. **不重复包裹**：`wrapUnknown` 遇到已是业务异常的对象必须原样返回，否则用户会看到「发生了未预期的错误」而不是真正的原因。
3. **错误处理路径本身永不抛错**：未知语义键回退到 `INTERNAL`、插值缺参数退化为 `—`、通知窗口失败只记日志。兜底机制自己崩掉是最糟的情况。

### 13.5 与既有设计的关系

| 既有位置 | 关系 |
|----------|------|
| §6 错误边界与降级策略 | 本节是它的下游：§6 决定「降级到哪」，§13 决定「怎么告诉用户」 |
| `04` §5 日志 | §13 为其明确错误日志的**必填字段**（`code` / `numericCode` / `causeChain` / `context`） |
| `20` §5 错误契约 | 语义键沿用 `20` 的 `ErrorCode`；§13 补上编号派生、消息表、三级兜底与 UI 策略 |
| `21` 数据库 | 错误日志入 `app_logs` 表；§13 的字段与其 `event/level/data` 列对应 |

### 13.6 验收标准（可测）

| 项 | 标准 |
|----|------|
| 全覆盖 | 主进程与控制台**零未处理异常**（跑完整 E2E 流程后检查） |
| 不泄露 | 任意错误提示的 UI 文本中不含：绝对路径、`ffmpeg`/`SQLite`/`EACCES`、堆栈、`undefined` |
| 可定位 | 每条错误日志都有 `numericCode` 与非空 `causeChain`（业务显式抛的除外） |
| 不刷屏 | 1.5 s 内同一错误触发 5 次 → 只出现 1 条提示且显示「已发生 5 次」 |
| 不白屏 | 任一路由组件抛错 → 显示兜底区域，导航仍可用 |
| 取消静默 | 取消录音/导出 → 无任何错误提示 |
| 编号稳定 | `listAllCodes()` 快照测试通过（防止段内顺序被破坏导致编号漂移） |
